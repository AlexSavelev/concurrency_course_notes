# Спинлок, атомарные операции и мьютекс «изнутри»

## 1. Спинлок (spinlock)

Мы хотим реализовать примитив взаимного исключения (mutual exclusion), как у мьютекса: в каждый момент в критической секции (critical section, между `lock` и `unlock`) не более одного потока. Поток, не сумевший захватить блокировку, будет активно ждать (spin) в цикле — отсюда название **спинлок**.

Требуемые свойства мьютекса:
- **взаимное исключение (mutual exclusion):** не более одного потока в критической секции;
- **прогресс (progress):** если свободный мьютекс пытаются захватить несколько потоков, кто-то обязан преуспеть;
- ожидание когда-нибудь завершается (нет deadlock и livelock).

### 1.1. Наивная реализация с флагом

`state == false` — свободно, `true` — занято:

```cpp
bool state = false;
void lock()   { while (state) {}   state = true; }
void unlock() { state = false; }
```

На двух и более потоках возникает **состояние гонки (race condition)**. Сценарий с тремя потоками:

1. Поток 1 в `lock` видит `state == false`, выходит из цикла, но **ещё не выполнил** `state = true`.
2. Планировщик переключается на Поток 2: он тоже видит `state == false` и выходит из цикла.
3. Поток 3 — аналогично.
4. Все три выполняют `state = true` и оказываются в критической секции одновременно — взаимное исключение нарушено.

Корень проблемы: проверка и установка — **две отдельные операции**, между которыми вклинивается другой поток. Нужна неделимая операция «проверить-и-установить» (test-and-set).

### 1.2. Попытка через обмен (swap)

Идея: локальная `local = true`, атомарно обменять её со `state`. Если после обмена `local == false` — мы захватили (раньше `state` был `false`, мы записали `true`, забрали `false`).

```cpp
bool state = false;
void lock() {
    bool local = true;
    while (local) swap(state, local);   // если swap не атомарен — та же беда
}
void unlock() { state = false; }
```

Если `swap` раскладывается на три отдельных действия (читать `state`, писать `local` в `state`, писать временное в `local`), атомарности снова нет. **Вывод:** нужна аппаратная атомарная операция чтения-записи за один неделимый шаг.

### 1.3. Safety и liveness; виды прогресса

Свойства мьютекса полезно разнести по двум классам, введённым Лесли Лэмпортом (его «Science of Concurrent Programs», TLA+, темпоральная логика дают для них строгий формализм).

- **Safety («никогда не происходит ничего плохого»)** — инвариант. Для мьютекса это **взаимное исключение**. Нарушение safety видно уже на **конечном** исполнении (вот прямо сейчас два потока в критической секции). Критически важно: safety должно держаться при **любом** поведении планировщика, даже намеренно враждебном и нечестном.
- **Liveness («когда-нибудь происходит что-то хорошее»)** — для мьютекса это **прогресс** (вызов `lock` завершается). Нарушить liveness можно только на **бесконечном** исполнении (прогресса нет никогда). В отличие от safety, liveness **требует честности (fairness) планировщика**: если планировщик может бесконечно не давать потоку процессор, никакой примитив завершения не гарантирует.

Прогресс бывает двух сортов:
- **глобальный прогресс (deadlock-freedom):** хотя бы **один** из претендующих потоков преуспевает (система в целом движется);
- **локальный прогресс (starvation-freedom):** **каждый** поток рано или поздно преуспевает (нет голодания, starvation).

Глобальный прогресс не исключает голодания одного невезучего потока, пока другие захватывают блокировку снова и снова. Эта пара (глобальный/локальный) ниже отличает test-and-set спинлок (только глобальный) от ticket lock (локальный, FIFO).

**Замечание про игрушечные мьютексы.** Из store/load (без RMW) можно построить взаимное исключение лишь для двух потоков, и поучительно, что отдельные «половинки» решения дают safety, но ломают liveness в противоположных сценариях: «оба выставили флаг „хочу“ и ждут друг друга» (взаимная блокировка) против «робко уступаю — и не могу войти в одиночку». Их комбинация — **lock Петерсона** — даёт оба свойства для двух потоков. Обобщение на N потоков (турнирное дерево из таких локов) требует N ячеек и компактных id потоков — это непрактично и как раз мотивирует «настоящий» спинлок на RMW (без id и без N ячеек). Сам lock Петерсона и то, **почему он ломается на реальном x86** (store buffering), разобраны в файле про модель памяти (часть 1).

## 2. Атомарные операции в C++ (`std::atomic`)

Шаблон `std::atomic` компилируется в инструкции, гарантирующие атомарность на уровне процессора. Основные методы:

- `store()` — атомарная запись; `load()` — атомарное чтение;
- `exchange()` — атомарно записать и вернуть старое значение (swap для одной переменной);
- `compare_exchange_weak/strong()` — условная замена (CAS, compare-and-swap);
- `fetch_add`/`fetch_sub`/`fetch_or`/… — атомарные арифметика и побитовые операции.

Спинлок через `exchange`:

```cpp
std::atomic<bool> state{false};
void lock()   { while (state.exchange(true)) ; }   // спин
void unlock() { state.store(false); }
```

`exchange(true)` атомарно пишет `true` и возвращает прежнее. `false` → мы захватили; `true` → держит кто-то, крутимся. На x86 это инструкция `xchg`, у которой подразумевается lock-семантика (барьер). На других архитектурах нужен явный барьер, но `std::atomic` даёт необходимые гарантии.

**Что значит «атомарно».** Атомарность — не свойство самой инструкции, а **наблюдаемость относительно других операций**: физически и `exchange`, и `++` на уровне процессора не мгновенны (шины, кэши, провода). Мы называем операцию атомарной, если в любом сценарии конкуренции можно считать, что она произошла **целиком до или целиком после** другой — как операции `push`/`pop` потокобезопасного контейнера атомарны друг относительно друга. Как это достигается на уровне железа — отдельный вопрос (см. §2–§4 и файл про когерентность кэшей); на **использование** атомика это почти не влияет.

`exchange`/`fetch_add`/CAS — это **read-modify-write (RMW)** операции: они за один неделимый шаг читают, изменяют и пишут. Именно их «выразительной силы» хватает для взаимного исключения на любом числе потоков (в отличие от пары store/load, см. §1.3). Помимо `std::atomic<T>` в стандарте есть `std::atomic_flag` с операцией `test_and_set()` — минимальный булев атомик, который на некоторых архитектурах реализуется эффективнее обобщённого; на практике различие редко ощутимо, и обычно достаточно `std::atomic<bool>`.

### 2.1. `compare_exchange_weak` против `strong`

CAS «если значение равно ожидаемому — заменить»:

```cpp
bool compare_exchange_strong(T& expected, T desired);
bool compare_exchange_weak(T& expected, T desired);
```

`weak` может дать **ложный отказ (spurious failure)** — вернуть `false`, даже когда `*expected == value`. Это не баг: на архитектурах с LL/SC (load-linked / store-conditional, ARM, POWER) store-conditional срывается при любом «возмущении» кэш-линии. Правило: `weak` кладут **в цикл** (где повтор и так предусмотрен), `strong` — для одиночной попытки вне цикла. Типичный lock-free паттерн:

```cpp
T expected = head.load();
while (!head.compare_exchange_weak(expected, new_value)) { /* expected обновлён, повтор */ }
```

### 2.2. Гонка данных: инкремент общего счётчика

```cpp
size_t counter = 0;
for (int i = 0; i < iterations; ++i) ++counter;   // из нескольких потоков
```

Ожидаем `threads * iterations`, получаем меньше. `++counter` не атомарен: читать → инкремент в регистре → записать. Между чтением и записью другой поток меняет значение, и одна запись теряется. Замена на `std::atomic<size_t>` с `fetch_add(1)` (или `++` для атомика, компилируется в `lock xadd` на x86) исключает гонку.

### 2.3. Store buffering: почему «простые» присваивания не упорядочены

Классический литмус-тест (litmus test) ослабленной модели памяти. Общие `x = y = 0`, локальные `a`, `b`:

```cpp
// Поток 1:        // Поток 2:
x = 1;             y = 1;
a = y;             b = x;
```

Интуиция говорит: исход `a == 0 && b == 0` невозможен. На практике он **возможен**. Механизм — **буфер записи (store buffer)**: процессор откладывает запись в кэш/память, продолжая исполнять следующие инструкции.

1. Поток 1 (ядро A): `x = 1` уходит в store buffer ядра A — в память пока не попало.
2. Поток 1: `a = y` читает `y == 0` → `a = 0`.
3. Поток 2 (ядро B): `y = 1` уходит в store buffer ядра B.
4. Поток 2: `b = x` читает `x` из памяти — запись Потока 1 ещё в его буфере, не видна → `b = 0`.

Оба чтения видят старые значения. Если бы тот же поток сразу читал свою же переменную, он увидел бы своё значение через **store forwarding** (чтение подхватывает значение из собственного store buffer), но в другом ядре этого не происходит.

#### Уточнение про x86

x86 реализует модель **TSO (Total Store Order)** — почти последовательная согласованность с **единственным** допустимым переупорядочиванием: **load может обогнать более ранний store по другому адресу** (потому что store «висит» в store buffer, пока load читает из памяти). Именно это переупорядочивание store→load и порождает исход `(0,0)` в тесте выше. Все прочие перестановки (store→store, load→load, load→store) на x86 запрещены.

Отсюда важное следствие для эксперимента: **компиляторный барьер не лечит** этот тест.

```cpp
void TurnOffCompilerReordering() { asm volatile("" ::: "memory"); }  // только компилятор
```

`asm volatile("" ::: "memory")` запрещает переупорядочивание **компилятору**, но не трогает store buffer процессора — тест продолжает давать `(0,0)`. Чинит ситуацию **аппаратный барьер памяти** между `store` и `load` в каждом потоке: на x86 это инструкция `mfence` (она сбрасывает store buffer), либо использование `std::atomic` с `memory_order_seq_cst`, который такой барьер вставляет автоматически. Полный механизм барьеров и `mfence` — тема про модель памяти; здесь важно лишь, что проблема **аппаратная**, и снимается аппаратным барьером, а не компиляторным.

#### Полный код эксперимента

```cpp
#include <iostream>
#include <thread>
#include <cstdint>

void barrier() { asm volatile("" ::: "memory"); }  // компиляторный барьер

int main() {
    const uint64_t N = 1'000'000;
    uint64_t c00 = 0, c01 = 0, c10 = 0, c11 = 0;
    for (uint64_t i = 0; i < N; ++i) {
        int x = 0, y = 0, a = 0, b = 0;
        std::thread t1([&] { x = 1; barrier(); a = y; });
        std::thread t2([&] { y = 1; barrier(); b = x; });
        t1.join(); t2.join();
        if (a == 0 && b == 0) ++c00;
        else if (a == 0 && b == 1) ++c01;
        else if (a == 1 && b == 0) ++c10;
        else ++c11;
    }
    std::cout << "(0,0)=" << c00 << " (0,1)=" << c01
              << " (1,0)=" << c10 << " (1,1)=" << c11 << "\n";
}
```

На x86 строка `(0,0)` будет ненулевой. Заменив `x`, `y` на `std::atomic<int>` со `store`/`load` (по умолчанию `seq_cst`), исход `(0,0)` становится невозможным: атомики дают и неделимость, и барьеры, синхронизирующие store buffer'ы и кэши.

#### Data race — формальное определение и UB

**Data race (гонка данных)** — два потока обращаются к одной ячейке памяти без упорядочивающего отношения happens-before, и хотя бы одно обращение — запись. В C/C++ это **неопределённое поведение (undefined behavior, UB)**: программа вправе делать что угодно. Если все одновременные обращения — только чтения, гонки нет (но гарантии видимости слабые). В нашем тесте есть и записи, и чтения одновременно — классический data race. Формальное определение happens-before — в теме про модель памяти.

## 3. Возврат к спинлокам

Поток, не захвативший блокировку, «крутится» (spin), повторяя `exchange` — активное ожидание (busy waiting).

**Плюсы:** нет системных вызовов → низкая задержка при захвате только что освободившейся блокировки; идеален для очень коротких секций (десятки тактов).
**Минусы:** жжёт процессорное время (планировщик видит поток активным и не вытеснит); создаёт лишний трафик когерентности кэшей (каждый `exchange` — запись, инвалидирующая линию у других ядер).

### 3.1. Оптимизации цикла ожидания

- `sleep(1)` — фиксированный сон. Плохо: слишком грубо, проспим освобождение.
- `yield()` — сисколл «уступаю процессор»; стоит сотни наносекунд, при быстром освобождении невыгоден.
- `pause` (x86, интринсик `_mm_pause()`) — подсказка процессору «я в спин-цикле»: экономит энергию, снижает конкуренцию за конвейер, улучшает поведение hyper-threading; не сисколл, выполняется быстро.
- Комбинированная практика: несколько итераций с `pause`, при затягивании — `yield`. В C++ есть `std::this_thread::yield()`.

### 3.2. Test-and-test-and-set и справедливые спинлоки

Наивный `exchange`-спин при конкуренции устраивает «шторм»: каждый ждущий поток на каждой итерации делает запись (RMW), инвалидируя кэш-линию у всех остальных — **cache ping-pong**. Улучшения:

- **TTAS (test-and-test-and-set):** сначала крутимся на **чтении** (`load`) — линия остаётся в состоянии Shared, никто никого не инвалидирует, — и только увидев «свободно», пробуем `exchange`. Резко снижает трафик когерентности.

```cpp
void lock() {
    while (true) {
        while (state.load(std::memory_order_relaxed)) _mm_pause();  // только чтение
        if (!state.exchange(true, std::memory_order_acquire)) return;
    }
}
```

- **Экспоненциальный backoff:** при неудаче увеличивать паузу — снижает контеншн под высокой нагрузкой.
- **Справедливость.** Простой спинлок **несправедлив (unfair)**: освободившуюся блокировку может бесконечно перехватывать «ближнее» ядро, остальные голодают, растёт хвостовая задержка (tail latency). **Ticket lock** даёт FIFO-порядок двумя счётчиками (билет на входе, текущий обслуживаемый). **MCS-lock** строит очередь узлов, где каждый поток спинит на **своём локальном** флаге → нет cache-bouncing и хорошо масштабируется на NUMA. Для low-latency систем предсказуемость хвоста часто важнее средней задержки, поэтому ticket/MCS предпочитают наивному спинлоку.

### 3.3. Memory order и `is_lock_free`

Идиоматичный спинлок использует `exchange(true, std::memory_order_acquire)` на захвате и `store(false, std::memory_order_release)` на освобождении — это дешевле, чем `seq_cst` по умолчанию (особенно на ARM), и достаточно для корректности критической секции. Полный разбор `memory_order` — тема про модель памяти.

Замечание: `std::atomic<T>` для крупных `T` может быть реализован через **скрытый внутренний замок** — тогда «атомик» на деле блокирующий. Проверяется `obj.is_lock_free()` (или `std::atomic<T>::is_always_lock_free`).

### 3.4. Контеншн: две разные проблемы и адаптивное ожидание

Когда много ядер интенсивно бьются за один атомик (спинлок, защищающий горячее состояние), возникает **контеншн (contention)**. Полезно видеть **две** проблемы сразу:

1. **Проблема дизайна.** Программа, в которой есть сильный контеншн на одном мьютексе, плохо масштабируется (см. гранулярность в файле про многопоточный сервер) — её часто стоит **переписать**, а не «ускорять» спинлок.
2. **Проблема самого спинлока.** Ждущие потоки грузят свои ядра бесполезными `exchange`, не дают исполняться полезной работе и греют процессор. Здесь и нужна правильная стратегия ожидания.

Диапазон стратегий (от дешёвых к дорогим): `pause`/spin-loop-hint → `sched_yield` (уступить ядро другому потоку ОС, сисколл) → блокирующее ожидание (park) через futex (§4). Хороший спинлок **адаптивен**: сначала оптимистично крутится (короткая секция вот-вот освободится — спинлок ровно на это и рассчитан), затем уступает, затем паркуется. Конкретные пороги — это **магические константы**, которые тюнятся под связку «процессор + ОС + нагрузка». Промышленные реализации такого ожидания: `Sleeper`/`spin` в folly, `SpinWait` в YDB, `Backoff` в crossbeam (Rust), `SpinWait` в .NET — у каждой свои константы. Поучительная история: после переезда .NET на Skylake одна программа замедлилась в ~50 раз, потому что инженеры подняли латентность инструкции `pause` примерно в 10 раз, а константы spin-wait были подобраны под старое значение. Вывод: захардкоженные константы непереносимы; в учебном коде их не подбирают руками, а берут готовый компонент (в нашем курсе — `SpinWait` из twist, который ещё и умеет работать под детерминированной симуляцией).

**Спинлок — это замкнутая распределённая система.** За «магией» констант стоит фундаментальная логика: спинлок, защищающий состояние, — это та же задача, что сервис, обслуживающий запросы от множества клиентов. Когда сервис перегружен, наивные клиенты делают ретраи волнами и добивают его (retry storm). Лечение в распределённых системах — **экспоненциальный backoff + рандомизация (jitter):** растить паузу и размазывать попытки во времени, чтобы независимые участники без знания друг о друге пришли к глобально удачной координации (Marc Brooker, AWS, об этом пишет подробно). Ровно тот же рандомизированный backoff мы видим в промышленных spin-wait. Иначе говоря: **чтобы по-настоящему понимать спинлоки, нужно понимать распределённые системы** — процессор и есть маленькая замкнутая распределённая система.

## 4. Futex — эффективное ожидание в Linux

Если критическая секция долгая (rehash хеш-таблицы, ввод-вывод), активное ожидание катастрофически расточительно. Нужен механизм усыпить поток до освобождения. В Linux это системный вызов **futex (fast userspace mutex)**:

- **`FUTEX_WAIT(addr, val)`** — проверяет, что по адресу `addr` (32-битное слово) всё ещё лежит `val`; если да — поток засыпает в очереди ожидания этого адреса; если значение уже изменилось — возврат немедленный (`EAGAIN`).
- **`FUTEX_WAKE(addr, n)`** — будит до `n` потоков, ждущих на `addr`.

Ключевое: проверка значения и засыпание **атомарны относительно `FUTEX_WAKE`** — между «решил спать» и «уснул» потеря пробуждения невозможна (если значение поменялось, не заснём). Это решает гонку «проверка условия → переход в сон».

### 4.1. Идея реализации futex в ядре

Ядро **не разыменовывает** пользовательский адрес как указатель на данные — оно использует его лишь как **ключ**. Адрес хешируется в один из **futex hash buckets**; в каждом бакете — очередь ожидания (wait queue) и спин-замок ядра. `FUTEX_WAIT` под замком бакета **ещё раз** атомарно сверяет значение по адресу с `val` и, если совпало, ставит поток в очередь и усыпляет; `FUTEX_WAKE` берёт замок бакета и снимает с очереди до `n` потоков. Поскольку адрес — только ключ, futex одинаково работает с памятью процесса (приватный futex) и разделяемой памятью между процессами (`FUTEX_PRIVATE_FLAG` лишь оптимизирует первый случай). Это объясняет, почему `FUTEX_WAKE` по уже освобождённому адресу не падает (ядро не читает там данные) — но формально это всё равно UB на уровне C++ (см. §6).

Тонкость проверки значения. Сравнение `*addr == val` в `FUTEX_WAIT` атомарно лишь **относительно `FUTEX_WAKE`** на том же ключе; оно не атомарно относительно произвольной записи в `addr` с другого ядра. Между «прочитали значение в ядре» и реальной парковкой другой поток мог записать ячейку, не сделав `wake`, — поэтому проверка значения **не гарантия**, а защита от одной конкретной гонки (потерянного пробуждения), и пользоваться futex нужно так, чтобы перепроверять условие в цикле. Понять все комбинации можно, только держа в уме реализацию, — поэтому правильный способ разобраться с futex не туториал, а **чтение кода и комментариев в ядре Linux**.

Замечание про API. Поверх futex стандарт даёт `std::atomic::wait/notify` (Linux-обёртка), но это спорный дизайн: поддержаны 64-битные типы (реализация тяжёлая, лишний уровень косвенности) и возможны spurious-пробуждения — разумные приложения этим почти не пользуются. В курсе вместо этого используется futex-обёртка twist: **только 32-битный** атомик и **двухфазный** wake (сначала получить ключ, затем `wake`), причём API намекает, что `wake` сразу после `prepare` писать как раз **не** нужно. Три «ингредиента» для любой синхронизации — **thread, atomic, futex**; почти всё прочее в `<...>`-заголовках стандартной библиотеки про синхронизацию избыточно или неудачно спроектировано.

### 4.2. Мьютекс на futex (двухсостояниевый, с проблемой)

`state`: 0 — свободно, 1 — занято.

```cpp
struct Mutex {
    std::atomic<int> state{0};
    void lock() {
        if (state.exchange(1) == 0) return;       // быстрый путь: без сисколла
        do {
            futex_wait(&state, 1);                 // заснуть, если state == 1
        } while (state.exchange(1) != 0);
    }
    void unlock() {
        state.store(0);
        futex_wake(&state, 1);
    }
};
```

Свойство, ради которого всё затевалось: **незанятый мьютекс не делает сисколлов** (только `exchange`), futex включается лишь при конкуренции.

### 4.3. Спинлок против futex-мьютекса

| Характеристика | Спинлок | Мьютекс (futex) |
|---|---|---|
| Ожидание | активное (busy-wait) | поток спит |
| Оверхед захвата | нет сисколлов | высокий при конкуренции (syscall) |
| Реактивность | очень высокая (наносекунды) | зависит от планировщика (микросекунды) |
| CPU при ожидании | 100% одного ядра | почти 0 |
| Когда применять | очень короткие секции | длинные секции или когда нельзя жечь CPU |

На практике — **адаптивный мьютекс (adaptive mutex):** сначала покрутиться (как спинлок) ограниченное число итераций в расчёте на быстрое освобождение, и только потом уйти в futex. Сочетает низкую задержку спинлока без конкуренции и экономию CPU при долгом ожидании. Так устроены многие реализации `pthread_mutex` (атрибут `PTHREAD_MUTEX_ADAPTIVE_NP`).

> RAII-обёртки `std::lock_guard`/`std::unique_lock`/`std::scoped_lock` и их различия разобраны в файле про многопоточный сервер; здесь не повторяем. Напомним лишь, что `unique_lock` умеет ручные `lock()`/`unlock()` (полезно отпустить мьютекс на время долгой операции), но повторный захват — потенциально сисколл, и для коротких операций оверхед перевесит выгоду.

## 5. Серьёзная проблема двухсостояниевого мьютекса

В реализации §4.2 есть две беды.

### 5.1. Use-after-free в деструкторе (пример `OneShot`)

`unlock` обращается к памяти мьютекса (`futex_wake`) **после** того, как `store(0)` сделал его свободным. Между этими действиями другой поток может захватить мьютекс, завершить работу и **уничтожить объект**.

```cpp
class OneShot {                 // выполнить функцию ровно один раз
    std::mutex mtx;
    bool called = false;
public:
    void call() {
        std::lock_guard lk(mtx);
        if (!called) { called = true; func(); }
    }
};

auto os = std::make_shared<OneShot>();
std::thread t1([os] { os->call(); });
std::thread t2([os] { /* дождались call */ os.reset(); /* уничтожаем */ });
```

Переключение внутри futex-мьютекса:
1. Поток 1 в `call` захватывает мьютекс, выполняет `func`, выходит из `lock_guard` → `unlock`.
2. В `unlock`: `state.store(0)` — мьютекс свободен.
3. Планировщик → Поток 2: видит, что `call` выполнен, и уничтожает `os`. Деструктор `shared_ptr` сносит объект вместе с полем `mtx`.
4. Планировщик → Поток 1: продолжает `unlock`, вызывает `futex_wake(&state, 1)` — но `state` уже часть удалённого объекта. **Use-after-free, UB.**

### 5.2. Почему нельзя переставить `wake` и `store`

```cpp
void unlock() { futex_wake(&state, 1); state.store(0); }   // плохо
```
- Поток 1 делает `futex_wake`, но никто ещё не ждёт — холостой выстрел.
- `store(0)` освобождает.
- Поток 2, который как раз собирался уснуть (сделал `exchange(1)`, увидел 1, готовится к `futex_wait`), уже вызвал `futex_wait` со значением 1 — он уснёт, а будить уже некому. **Lost wakeup.**

Значит, `store` обязан идти **до** `wake` (чтобы спящие через перепроверку увидели изменение) — но тогда мы возвращаемся к use-after-free.

### 5.3. Попытка со счётчиком ожидающих и почему она ломается

Чтобы не делать лишний `futex_wake`, добавим счётчик `waiting`:

```cpp
void lock() {
    if (state.exchange(1) == 0) return;
    waiting.fetch_add(1);
    while (state.exchange(1) == 1) futex_wait(&state, 1);
    waiting.fetch_sub(1);
}
void unlock() {
    state.store(0);
    if (waiting.load() > 0) futex_wake(&state, 1);
}
```

Гонка: Поток 1 делает `store(0)` и **проверяет `waiting` (ещё 0)** → `futex_wake` не зовёт. А Поток 2 в этот момент инкрементирует `waiting`, видит занятость и уходит в `futex_wait` — и засыпает навсегда (**lost wakeup**), потому что проверка `waiting` у Потока 1 случилась раньше инкремента. Вывод: счётчик и состояние нужно объединить в **одно атомарное слово** и менять согласованно. Это подводит нас к мьютексу на трёх состояниях.

## 6. Мьютекс на трёх состояниях

**Мотивировка:** (1) **сократить число сисколлов** — не звать `futex_wake`, когда ждущих нет; (2) снять «проезд по памяти» в деструкторе (use-after-free из §5.1) в общем случае.

Состояния одного атомарного слова `state`:
- **0** — свободно;
- **1** — занято, ждущих нет;
- **2** — занято, есть (возможно) ждущие.

```cpp
struct Mutex3 {
    std::atomic<int> state{0};

    void lock() {
        int c = 0;
        // быстрый путь: 0 -> 1 без сисколла
        if (state.compare_exchange_strong(c, 1)) return;
        // медленный путь
        do {
            // пометить как "есть ждущие": если было 2 — уже помечено,
            // иначе сделать 1->2 (или подхватить текущее значение)
            if (c == 2 || state.exchange(2) != 0)
                futex_wait(&state, 2);          // спим, пока state == 2
            c = 0;                               // пробуем снова 0 -> 2
        } while (!state.compare_exchange_strong(c, 2));
    }

    void unlock() {
        // если было 2 (ждущие) — после освобождения будим одного
        if (state.fetch_sub(1) != 1) {           // вернулось не 1 => было 2
            state.store(0);
            futex_wake(&state, 1);
        }
        // если было 1 (ждущих нет) — fetch_sub сделал 1->0 и НИКАКОГО futex_wake
    }
};
```

Как это работает и что решает:

- **Сокращение сисколлов.** В неконкурентном случае `lock` делает CAS `0→1` (без сисколла), `unlock` — `fetch_sub` `1→0`, и `futex_wake` **не вызывается вовсе**. Сисколл происходит только при реальной конкуренции (state доходит до 2). Ждущий поток сам переводит state в 2 (`exchange(2)`), сигнализируя владельцу «меня надо будить».
- **Снятие use-after-free в `OneShot`.** В типичном (неконкурентном) использовании `OneShot` `unlock` идёт по ветке «было 1» и **не обращается к памяти после освобождения** — объект можно безопасно уничтожать. Проезд по памяти (`futex_wake`) остаётся только в ветке «было 2», но там **гарантированно есть другой поток, заблокированный внутри `lock`**, поэтому объект ещё жив и не может быть разрушен. Так трёхсостояниевая схема устраняет UAF в практически значимом случае.

Существует ещё более экономная форма (Drepper, «Futexes Are Tricky»), где быстрый путь `unlock` укладывается в один атомарный декремент; идея та же. На этой схеме (счётчик-в-слове + три состояния) построены реальные `pthread_mutex`/glibc.

## 7. Реализация `condition_variable` через futex

Condition variable нужно «уснуть до уведомления». Прямолинейная попытка — усыпить поток на `futex_wait(&flag, ...)` — натыкается на ту же гонку: между «проверил предикат и отпустил мьютекс» и «уснул» другой поток может послать уведомление, и оно потеряется. Решение — **счётчик поколений (generation counter)**.

```cpp
class cond_var {
    std::atomic<uint32_t> seq{0};   // номер поколения = «сколько было уведомлений»
public:
    // mtx — внешний мьютекс, защищающий предикат
    void wait(Mutex3& mtx) {
        uint32_t s = seq.load();    // СНИМОК поколения, пока ещё держим mtx
        mtx.unlock();
        futex_wait(&seq, s);        // спать, пока seq == s
        mtx.lock();
    }
    void notify_one() {
        seq.fetch_add(1);           // сменили поколение
        futex_wake(&seq, 1);
    }
    void notify_all() {
        seq.fetch_add(1);
        futex_wake(&seq, INT_MAX);  // на практике — FUTEX_REQUEUE, см. ниже
    }
};
```

Почему счётчик поколений снимает lost wakeup. Снимок `s` берётся **до** `mtx.unlock()`, то есть пока предикат ещё стабилен. Если между `unlock` и `futex_wait` другой поток успеет `notify` (сделает `seq → s+1`), то `futex_wait(&seq, s)` увидит `seq != s` и **вернётся немедленно**, не заснув. Уведомление не теряется. В этом и состоит роль поколения: оно превращает «потерянный» сигнал в «значение уже изменилось».

Почему spurious wakeups здесь неизбежны и зачем цикл `while`. `seq` — **грубый** сигнал «было хоть одно уведомление», не привязанный к конкретному предикату:
- `notify_one` будит один поток, но другой поток мог уже забрать ресурс (предикат снова ложен) — разбуженный обязан перепроверить;
- `notify_all` инкрементирует `seq` один раз и будит всех — все возвращаются из `wait` и все перепроверяют;
- futex может вернуться по сигналу ОС.

Поэтому пользователь `condition_variable` обязан перепроверять предикат в цикле `while (!pred) cv.wait(...)` — spurious wakeup не дефект реализации, а прямое следствие конструкции на поколениях. (Семантика самого `std::condition_variable` и корректное использование разобраны в файле про condition variable и thread pool; здесь мы показали, что у него внутри.)

**Оптимизация против грохочущего стада (thundering herd).** `notify_all` через `futex_wake(INT_MAX)` будит всех сразу, и они штурмуют мьютекс. Правильнее **`FUTEX_REQUEUE`**: разбудить одного, а остальных **перевесить** из очереди ожидания condition variable в очередь ожидания связанного мьютекса — тогда они проснутся по очереди, по мере освобождения мьютекса, без шторма.

## 8. Итог темы

- Атомарность нужна, потому что «проверить-и-установить» и даже `++` — несколько шагов; `std::atomic` даёт неделимость плюс барьеры.
- Store buffer и x86-TSO разрешают переупорядочивание store→load; лечит аппаратный `mfence`/`seq_cst`, а не компиляторный барьер.
- Спинлок хорош для коротких секций; TTAS/ticket/MCS снимают cache-bouncing и дают справедливость.
- Futex усыпляет поток без сисколла на быстром пути; в ядре адрес — лишь ключ к хеш-бакету с очередью ожидания.
- Двухсостояниевый futex-мьютекс страдает от лишних `wake` и use-after-free; **три состояния** сокращают сисколлы и снимают UAF в общем случае.
- `condition_variable` на futex строится через **счётчик поколений**, который устраняет lost wakeup ценой неизбежных spurious wakeups (отсюда обязательный цикл `while`).
