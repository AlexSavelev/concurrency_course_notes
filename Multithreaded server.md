# Многопоточный TCP-сервер и примитивы синхронизации

Последовательный сервер из прошлой темы обрабатывает клиентов по одному. Чтобы обслуживать их одновременно, нужны потоки — а с потоками сразу возникает проблема разделяемого состояния. Эта тема о том и о другом.

## 1. Экскурс: UDP и Unix-сокеты

Чтобы понимать место TCP, полезно сравнить его с соседями.

**UDP (`SOCK_DGRAM`)** — без установления соединения, без гарантий доставки и порядка; данные идут **датаграммами (datagrams)**. Нет `listen`/`accept`/`connect`; вместо `read`/`write` — `recvfrom`/`sendto` с явным указанием адреса при каждой операции. Размер датаграммы ограничен (практически — меньше MTU (Maximum Transmission Unit)). Применяется там, где задержка важнее надёжности (игры, телеметрия, QUIC поверх UDP).

**Unix-сокеты (`AF_UNIX`)** — межпроцессное взаимодействие на одной машине через файл в ФС. Поддерживают потоковый и датаграммный режимы, быстрее сетевых (нет сетевого стека) и умеют передавать дескрипторы между процессами через `sendmsg`/`SCM_RIGHTS` — этого не умеют ни pipe, ни TCP.

## 2. Многопоточный сервер: поток на клиента

Простейшая модель параллелизма — на каждое принятое соединение создавать поток.

```cpp
#include <arpa/inet.h>
#include <thread>
#include <iostream>
#include <unistd.h>

void handle_client(int client_fd, int client_id) {
    char buffer[1024];
    while (true) {
        ssize_t n = read(client_fd, buffer, sizeof(buffer));
        if (n <= 0) break;                 // EOF или ошибка
        ssize_t written = 0;
        while (written < n) {              // частичная запись
            ssize_t r = write(client_fd, buffer + written, n - written);
            if (r <= 0) break;
            written += r;
        }
    }
    close(client_fd);
    std::cout << "Client " << client_id << " disconnected\n";
}

int main() {
    int server_fd = socket(AF_INET, SOCK_STREAM, 0);
    int opt = 1;
    setsockopt(server_fd, SOL_SOCKET, SO_REUSEADDR, &opt, sizeof(opt));

    sockaddr_in addr{};
    addr.sin_family = AF_INET;
    addr.sin_port = htons(11000);
    addr.sin_addr.s_addr = INADDR_ANY;
    bind(server_fd, (sockaddr*)&addr, sizeof(addr));
    listen(server_fd, 128);

    int id = 0;
    while (true) {
        int client_fd = accept(server_fd, nullptr, nullptr);
        if (client_fd < 0) { if (errno == EINTR) continue; perror("accept"); continue; }
        std::thread(handle_client, client_fd, id++).detach();
    }
}
```

`detach()` делает поток автономным: главный поток не ждёт его завершения. Альтернатива — `std::jthread` (C++20, см. §11), который сам делает `join` в деструкторе и поддерживает отмену.

### 2.1. Проблема C10k

Поток на клиента прост, но плохо масштабируется. **C10k** — задача обслужить 10 000 одновременных соединений. Почему потоки тут проигрывают:

- **Память.** Стек потока по умолчанию ~8 МБ виртуально; 10 000 потоков — десятки гигабайт адресного пространства (резидентно меньше, но переключения дороги).
- **Переключения контекста.** Планировщик тасует тысячи потоков, кэши «остывают», падает пропускная способность.
- **Ресурсы ядра.** Дескрипторы и структуры потоков ограничены.

Выходы: **пул потоков**, **неблокирующий ввод-вывод + мультиплексирование** (`select`/`poll`/`epoll`), **файберы/корутины**.

### 2.2. Масштабирование `accept`: `SO_REUSEPORT` и thundering herd

Когда несколько потоков пытаются принимать соединения с **одного** слушающего сокета, возникают два смежных вопроса.

**Thundering herd на `accept`.** Исторически при пробуждении одного события просыпались все ожидающие потоки, конкурировали за `accept`, и все, кроме одного, снова засыпали. Современное ядро Linux будит на `accept` только один поток, так что для прямого `accept` проблема в основном решена. Но она **возвращается** в epoll-архитектуре, где много потоков делают `epoll_wait` на одном слушающем fd: тогда нужен флаг `EPOLLEXCLUSIVE` (Linux 4.5+), будящий лишь одного.

**`SO_REUSEPORT` (Linux 3.9+)** — современный способ масштабировать приём по ядрам. Несколько сокетов (по одному на поток/процесс) биндятся на **один и тот же** порт; ядро само хешированием по 4-tuple распределяет входящие соединения по их **отдельным** accept-очередям. Это убирает contention на единственной очереди и thundering herd, даёт линейное масштабирование приёма. Так устроены nginx (`reuseport`), высокопроизводительные шлюзы.

```c
int opt = 1;
setsockopt(fd, SOL_SOCKET, SO_REUSEPORT, &opt, sizeof(opt));  // ДО bind, в каждом потоке свой fd
```

Не путать с `SO_REUSEADDR`: тот лишь разрешает rebind поверх `TIME_WAIT`, а `SO_REUSEPORT` — про балансировку нагрузки между сокетами.

## 3. Проблема разделяемых данных: сервер-кэш простоты

Содержательный пример: клиенты шлют числа, сервер отвечает, простое ли число, кэшируя результаты в общем `unordered_map`.

### 3.1. Без синхронизации — гонка данных

```cpp
std::unordered_map<long long, bool> cache;   // общий на все потоки

void handle_client(int fd, int id) {
    long long num = /* читаем из сокета */;
    auto it = cache.find(num);               // ЧТЕНИЕ
    bool result;
    if (it != cache.end()) result = it->second;
    else { result = is_prime(num); cache[num] = result; }  // ЗАПИСЬ
    /* отправляем result */
}
```

Несколько потоков одновременно читают и пишут `cache` без упорядочивания — это **гонка данных (data race)** и, как следствие, неопределённое поведение: от тихо испорченных данных до падения (rehash во время чужого `find`). Формальное определение гонки через отношение happens-before — в теме про модель памяти; пока достаточно интуиции «два потока, общая ячейка, хотя бы одна запись, нет упорядочивания».

#### Race condition ≠ data race — два разных класса ошибок

Важно с самого начала различать две **разные** гонки, у которых даже разные «детекторы»:

- **Data race (гонка данных)** — низкоуровневая, на уровне **одной ячейки памяти**: два потока обращаются к ней без упорядочивающей синхронизации, и хотя бы одно обращение — запись. Это формальное свойство кода и **неопределённое поведение** по стандарту C/C++. Его можно обнаружить инструментом (TSan), потому что он не знает вашей логики, но знает правило «общая ячейка + запись + нет упорядочивания». Если все одновременные обращения — только чтения, data race не бывает **никогда**.
- **Race condition (состояние гонки)** — высокоуровневая, на уровне **ваших инвариантов**: существует сценарий планирования потоков, при котором нарушается какой-то инвариант *вашей* структуры данных или логики (узел освободился дважды, потерялась вставка). Что считать нарушением, знаете **только вы** — отвлечённый инструмент это определить не может.

Эти классы связаны, но не совпадают: бывает data race без видимого race condition и race condition без data race (например, на корректно атомарных операциях с неверной логикой). Симптомы вроде use-after-free и double-free — это **проявления** на уровне памяти, по которым косвенно судят об ошибке синхронизации; см. также мотивирующий пример со связным списком в файле про lock-free структуры.

### 3.2. `std::mutex` — взаимное исключение

```cpp
std::unordered_map<long long, bool> cache;
std::mutex cache_mutex;

void handle_client(int fd, int id) {
    long long num = /* ... */;
    bool result;
    {
        std::lock_guard<std::mutex> lock(cache_mutex);   // RAII: захват в ctor, освобождение в dtor
        auto it = cache.find(num);
        if (it != cache.end()) result = it->second;
        else { result = is_prime(num); cache[num] = result; }
    }   // мьютекс освобождается здесь, в т. ч. при исключении
    /* отправка вне критической секции, чтобы не держать мьютекс на время I/O */
}
```

`std::lock_guard` — минимальная RAII-обёртка: захватывает мьютекс в конструкторе, освобождает в деструкторе. Ручные `lock()`/`unlock()` опасны: исключение или ранний `return` оставят мьютекс захваченным навсегда (deadlock).

### 3.3. Стоимостная модель блокировок

Чтобы совет «держите критическую секцию короткой» был не ритуалом, а инженерным расчётом, нужно понимать цену:

- **Незанятый мьютекс (uncontended).** Захват — это один атомарный read-modify-write (по сути CAS) **в пространстве пользователя**, без сисколла. Десятки тактов.
- **Занятый мьютекс (contended).** Поток паркуется в ядре через `futex` — это сисколл плюс переключение контекста: сотни–тысячи тактов и остывший кэш.

Отсюда правило: внутри критической секции не должно быть ни ввода-вывода, ни тяжёлых вычислений, ни тем более ожиданий. Реализация `std::mutex` через `futex` — отдельная тема; здесь важно лишь, что **дорожает не сам мьютекс, а конкуренция за него**, и борьба за масштабируемость — это борьба с contention.

### 3.4. Дедлок и одновременный захват: `std::lock`, `std::scoped_lock`

Захват двух мьютексов в разном порядке разными потоками — классический дедлок:

```cpp
std::mutex m1, m2;
void t1() { std::lock_guard l1(m1); /*...*/ std::lock_guard l2(m2); }  // m1, затем m2
void t2() { std::lock_guard l2(m2); /*...*/ std::lock_guard l1(m1); }  // m2, затем m1 — deadlock
```

`std::lock(a, b, ...)` захватывает несколько мьютексов сразу по алгоритму «всё или ничего» (с откатами), исключая дедлок независимо от порядка аргументов:

```cpp
void t1() {
    std::unique_lock l1(m1, std::defer_lock);   // не захватывать сейчас
    std::unique_lock l2(m2, std::defer_lock);
    std::lock(l1, l2);                           // атомарный захват обоих
}
```

С C++17 короче — `std::scoped_lock` (вариадичен, deadlock-free):

```cpp
void t1() { std::scoped_lock lock(m1, m2); /* ... */ }
```

### 3.5. RAII-обёртки: что когда применять

| Обёртка | Версия | Назначение |
|---|---|---|
| `std::lock_guard` | C++11 | Один мьютекс, простейший захват на область видимости. Не двигается, не разблокируется вручную. |
| `std::unique_lock` | C++11 | Один мьютекс, гибко: `defer_lock` / `try_to_lock` / `adopt_lock`, ручные `lock`/`unlock`, перемещаемость. **Обязателен для `condition_variable`.** |
| `std::shared_lock` | C++14 | Разделяемый (read) захват `shared_mutex`. |
| `std::scoped_lock` | C++17 | Несколько мьютексов сразу, deadlock-free. Замена `lock_guard` по умолчанию. |

Теги: `std::defer_lock` (создать, не захватывая), `std::try_to_lock` (попытаться без блокировки), `std::adopt_lock` (взять уже захваченный мьютекс под управление RAII).

### 3.6. `std::recursive_mutex`

Обычный мьютекс нельзя захватить дважды из одного потока — это самоблокировка. **Рекурсивный мьютекс** ведёт счётчик: каждый `lock` увеличивает, каждый `unlock` уменьшает, освобождение — по достижении нуля. Нужен, когда функция под мьютексом косвенно вызывает другую, берущую тот же мьютекс (рекурсия по структуре, колбэки):

```cpp
class Tree {
    std::recursive_mutex m;
    void traverse(Node* n) {
        std::lock_guard<std::recursive_mutex> lock(m);
        process(n);
        for (auto* child : n->children) traverse(child);  // повторный захват тем же потоком
    }
};
```

Замечание: рекурсивный мьютекс дороже обычного и часто указывает на нечёткие границы владения. Обычно его можно убрать, выделив приватную функцию-«ядро», которая предполагает, что мьютекс уже захвачен.

### 3.7. `std::shared_mutex` — много читателей, редкие записи

Паттерн «много читателей, редкие записи» (как наш кэш) обслуживает **`std::shared_mutex`** (C++17) с двумя режимами: разделяемый (`shared_lock`, читатели не мешают друг другу) и эксклюзивный (`unique_lock`, писатель один и блокирует всех).

```cpp
std::shared_mutex cache_mutex;
std::unordered_map<long long, bool> cache;

// читатель
{
    std::shared_lock lock(cache_mutex);
    auto it = cache.find(num);
    if (it != cache.end()) return it->second;
}
// промах: вычисляем без блокировки, затем пишем эксклюзивно
bool result = is_prime(num);
{
    std::unique_lock lock(cache_mutex);
    cache[num] = result;   // повторная запись тем же значением безопасна
}
```

**Голодание (starvation).** Если читатели идут непрерывно, писатель может никогда не получить эксклюзив. Стандарт не фиксирует политику приоритета; разные реализации ведут себя по-разному (часть отдаёт приоритет читателям → голодание писателей). Для критичных случаев пишут свой RW-lock с приоритетом писателя.

**Проверка реальностью.** `shared_mutex` **дороже** обычного мьютекса: ему нужно атомарно вести счётчик читателей. Он выигрывает, только если (а) чтения подавляюще доминируют и (б) критическая секция достаточно длинная, чтобы окупить накладные расходы. Для очень коротких секций обычный `std::mutex` нередко быстрее. В read-mostly hot-path (таблица котировок/символов) часто применяют **seqlock**: читатель не берёт блокировку вовсе, а читает данные между двумя проверками счётчика версий и перечитывает, если писатель вмешался. Это даёт читателям нулевую стоимость синхронизации ценой ограничений на тип данных (тривиально копируемые, никаких указателей внутрь).

### 3.8. Мьютексы с таймаутом

`std::timed_mutex` и `std::shared_timed_mutex` добавляют `try_lock_for(duration)` / `try_lock_until(time_point)`. Применение: в условиях высокой конкуренции попытаться захватить, скажем, 50 мс, и, не дождавшись, пойти по запасному пути (например, посчитать без кэша) — отзывчивость важнее оптимальности.

### 3.9. Безопасная ленивая инициализация: `std::call_once` и magic statics

Отдельный класс задач с разделяемыми данными — **однократная инициализация** (создать соединение/конфиг ровно один раз, даже если первыми обратились несколько потоков). Соблазн написать «двойную проверку» (double-checked locking) руками почти всегда даёт тонкий баг в модели памяти. Стандартные корректные решения:

```cpp
// 1) std::call_once + std::once_flag
std::once_flag flag;
Config* config = nullptr;
Config& get_config() {
    std::call_once(flag, [] { config = new Config(load()); });
    return *config;
}

// 2) Function-local static ("magic static"): инициализация потокобезопасна с C++11
Config& get_config2() {
    static Config config(load());   // компилятор сам ставит барьер и одноразовую защёлку
    return config;
}
```

Второй вариант обычно предпочтительнее: короче и так же безопасен.

### 3.10. Когда мьютекс не нужен: атомарный счётчик

Для простого разделяемого счётчика запросов мьютекс избыточен — достаточно `std::atomic`:

```cpp
std::atomic<long long> request_count{0};
request_count.fetch_add(1, std::memory_order_relaxed);   // без блокировки
```

Это первый шаг к lock-free структурам; устройство `std::atomic`, memory order и спинлоки — отдельные темы.

### 3.11. Гранулярность блокировки и масштабируемость

«Держите критическую секцию короткой» имеет и второе измерение — **что именно** защищает мьютекс. Если один мьютекс лочит **всю** структуру (например, весь список или весь кэш), это **крупногранулярная блокировка (coarse-grained locking)**: операции сериализуются целиком, и с ростом числа ядер пропускная способность **не растёт** — более того, становится хуже однопоточной (платим ещё и за синхронизацию). Масштабируемость такой структуры **отрицательная**.

Полезно смотреть на это с ракурса распределённых систем. Распределённые системы строят по двум причинам: **отказоустойчивость** (отказ одной машины не виден пользователю) и **масштабируемость** (вдвое больше серверов → вдвое больше обслуженных запросов). Многоядерный процессор — это маленький «кластер», и мы хотим того же: больше ядер → больше операций в секунду на структуре данных. Один большой мьютекс этого не даёт.

Лекарство — **мелкогранулярная блокировка (fine-grained locking):** блокировать только нужную часть состояния, оставляя остальное свободным (отдельные замки на бакеты хеш-таблицы, на участки списка и т. п.). Это поднимает масштабируемость, но резко усложняет дизайн (та самая половина «The Art of Multiprocessor Programming» с рецептами тонких блокировок для списков, хеш-таблиц и пр.). Поэтому **не оптимизируйте раньше времени**: чтобы вообще решать, нужна ли мелкая гранулярность, нужна модель стоимостей (когда и какая коммуникация между ядрами происходит — см. файл про когерентность кэшей), а привычная алгоритмическая сложность (O-нотация, число операций) здесь почти не работает. Первая цель — **корректность** (без race condition, data race, утечек, use-after-free), а не скорость.

Сюда же — простейшая локальная оптимизация: выносить из критической секции всё, что можно. В §3.2 отправка ответа и даже `is_prime` сделаны **вне** блокировки; если бы вызов `new`/тяжёлое вычисление были под мьютексом, мы зря держали бы его, мешая остальным.

### 3.12. Синхронизация — особый код: имя мьютекса, связь с данными, немувабельность

Несколько практик, специфичных именно для кода синхронизации.

**Мьютекс обычно называют просто `mutex`.** Это один из редких случаев, когда имя переменной совпадает с именем типа: у мьютекса нет «прикладного» смысла помимо «защищать вот это состояние», и лучшего имени не подобрать. Но связь «какой мьютекс какие данные защищает» живёт в голове разработчика и неявно — в коде; читателю приходится её декодировать. Способы сделать связь явной: держать мьютекс и данные рядом в одной структуре; в Rust стандартный `Mutex<T>` **оборачивает** данные, и доступ возможен только захватив блокировку; в Clang есть аннотации thread-safety (`guarded_by`), которые статически проверяют, что к полю не обращаются без нужного мьютекса. На практике в C++ чаще ограничиваются дисциплиной именования и расположения.

**Мьютексы не должны протекать к высокоуровневым пользователям.** Обёртки вроде «`synchronized`-контейнера» выглядят безопасно, но это, как правило, оверкилл: примитивы синхронизации — забота инфраструктурного кода (фреймворк, рантайм), а в прикладной бизнес-логике мьютексов в идеале быть не должно. Если мьютекс «дотёк» до прикладного слоя — проблема обычно в дизайне, а не в том, что нужна ещё более «безопасная» обёртка.

**Move бессмыслен для разделяемого состояния.** Мьютекс, атомик и защищаемая ими структура — **некопируемы и неперемещаемы**, и это следует не из реализации, а из **использования**. Если несколько потоков держат ссылку на состояние и обращаются к нему, у него фиксированный адрес — переместить его «из-под» работающих с ним потоков бессмысленно (что значит переместить объект, на который прямо сейчас ссылаются другие потоки?). Важный сдвиг мышления: эти структуры (очереди, стеки) — **не контейнеры для хранения данных, а инструменты коммуникации** между потоками. Желание «и разделять между потоками, и перемещать» обычно означает программу «в вакууме»: по отдельности и то, и другое нужно, вместе — нет.

## 4. Ограничение нагрузки: семафор как защита от наплыва

Если сервер создаёт поток на клиента, злоумышленник, открыв 10 000 соединений, исчерпает память. Ограничить число одновременно обслуживаемых клиентов помогает **счётный семафор (counting semaphore)** — счётчик разрешений; полная реализация и стандартный класс `std::counting_semaphore` разобраны в теме про condition variable.

```cpp
#include <semaphore>
std::counting_semaphore<> slots(100);   // не более 100 клиентов одновременно

// ВАЖНО — RAII, иначе разрешение утечёт при исключении в конструкторе потока:
struct SlotGuard {
    std::counting_semaphore<>& s;
    explicit SlotGuard(std::counting_semaphore<>& s) : s(s) { s.acquire(); }
    ~SlotGuard() { s.release(); }
};

while (true) {
    int fd = accept(server_fd, nullptr, nullptr);
    std::thread([fd, &slots] {
        SlotGuard guard(slots);          // acquire внутри потока, release гарантирован dtor
        handle_client(fd);
    }).detach();
}
```

Нюанс корректности: если делать `slots.acquire()` в главном потоке **до** создания `std::thread`, а конструктор потока бросит исключение, разрешение никогда не вернётся (утечка). Поэтому `acquire`/`release` оборачивают в RAII и держат на стороне рабочего потока. Не дождались слота — можно `try_acquire_for()` и вернуть клиенту «сервер перегружен» (это и есть **обратное давление, backpressure**).

## 5. Синхронизация вывода в `std::cout`

Отдельные вызовы `operator<<` потокобезопасны с C++11, но **последовательность** вызовов из разных потоков перемежается. Два решения:

```cpp
// 1) общий мьютекс на всё сообщение
std::mutex cout_mutex;
void log(const std::string& m) { std::lock_guard l(cout_mutex); std::cout << m << '\n'; }

// 2) std::osyncstream (C++20): буферизует вывод и сбрасывает атомарно в деструкторе
#include <syncstream>
std::osyncstream(std::cout) << "Client " << id << " sent " << num << '\n';
```

`osyncstream` под капотом — тот же общий мьютекс плюс буфер; просто аккуратнее в использовании.

## 6. Тестирование многопоточного кода

Недетерминизм делает баги трудновоспроизводимыми. Инструменты:

- **AddressSanitizer (ASan)** — `g++ -fsanitize=address -g`. Ловит ошибки **памяти**: heap-use-after-free, double-free, выход за границы. Прямо гонок он не ищет, но в многопоточном коде их **симптомы** часто проявляются именно как use-after-free/double-free (например, два конкурентных `pop` из связного списка освобождают один узел дважды). Поэтому инструмент «про память» косвенно вскрывает баги синхронизации. Та же идея в другом обличье — инвариант заимствования Rust (одна мутабельная ссылка либо много немутабельных): он одновременно помогает и управлению памятью, и синхронизации, потому что это связанные задачи.
- **ThreadSanitizer (TSan)** — динамический детектор гонок: `g++ -fsanitize=thread -g -O1 -pthread`. Ловит **data race** по факту наблюдённого исполнения (помнит, что́ упорядочено по happens-before). ASan и TSan **взаимодополняющи** — поэтому код собирают и тестируют несколькими сборками с разными санитайзерами.
- **Детерминированное тестирование** — управляемая инъекция переключений/задержек для провокации редких порядков (тема про файберы и fault injection); умеет находить и data race, и утечки на аннотированных фрагментах.
- **Стресс-тесты** под нагрузкой и статический анализ потенциальных дедлоков.
