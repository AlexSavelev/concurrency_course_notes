# Приложение A1. Work-Stealing планировщик: эффективный рантайм

> Это приложение — для тех, кто хочет углубиться. Оно опирается на файлы про пул потоков, файберы и их планировщик, lock-free, когерентность кэшей и модель памяти, и показывает, **как сделать рантайм не просто корректным, а эффективным**. Ничто из основного чтения дальше от этого материала не зависит — читать можно отдельно, после основной части.

## A1.1. Поворот: от корректного кода к эффективному

До сих пор рантайм (пул потоков, на котором живут файберы и каналы) писался **максимально просто**, лишь бы работал: одна очередь задач под общим мьютексом. Этого хватало, чтобы запускать файберы, переключать их, синхронизировать через мьютексы/каналы/`select`, — но не для производительности. Чтобы оптимизировать код, его сначала нужно **иметь** и **профилировать**: накопив кодовую базу, мы можем посмотреть, где она тормозит, и применить ранее изученные инструменты — минимизацию межъядерной коммуникации (когерентность кэшей), слабые модели памяти, lock-free. Узкое место здесь — **не файберы, а рантайм**, в котором они исполняются.

## A1.2. Эффективный API планировщика

Прежде чем чинить реализацию, чинят **API**: производительность теряется уже на входе.

### A1.2.1. `unique_function`: стирание типа и владение

Задача в пуле — произвольная лямбда. Компилятор переписывает лямбду в класс (поля-захваты + `operator()`), так что разные лямбды — **разные типы**, а очередь хочет хранить объекты одного типа. `unique_function` решает это, делая две вещи:
- **стирание типа (type erasure):** хранит указатель на гетерогенный функциональный объект за общим интерфейсом, так что её собственный тип от типа лямбды не зависит;
- **владение (ownership):** владеет функцией и разрушает её (в отличие от копируемого `std::function`).

Но за это платят: лямбда боксируется на куче (динамическая аллокация), а очередь хранит указатели на function-state — лишняя косвенность.

### A1.2.2. Нужно ли владение? Интрузивная задача

Посмотрим, какие у нас задачи. Для файберов они **однотипные и простые** — захватывают, по сути, один `Fiber*`. И — ключевой вопрос — **нужно ли планировщику владеть задачей?**

- `submit_task(lambda)` (внешний пользовательский API): да, пул обязан **продлить время жизни** лямбды до её исполнения — здесь динамическая аллокация неизбежна.
- Служебная задача **файбера**: нет. Задача лишь делает `coroutine.resume()`; пока задача не выполнилась, файбер не завершился и не разрушился, то есть **сам файбер гарантирует время жизни** задачи. Владение избыточно.

Основное применение — файберы, поэтому приоритизируем **отсутствие владения**. Отсюда правильная форма задачи: **интрузивная** база `TaskBase` с методом `Run()` и служебными ссылками (узел встроен в саму задачу, чтобы связывать её в очереди **без аллокации**), а **сам `Fiber` реализует** интерфейс `IRunnable`/`TaskBase`. Файбер планируется передачей `this` — ни боксинга, ни аллокации, ни двойной косвенности.

```cpp
struct TaskBase {                 // интрузивный узел задачи
    virtual void Run() = 0;
    TaskBase* next_in_queue = nullptr;   // связывание в очередях планировщика — без аллокаций
};
class Fiber : public TaskBase {   // файбер сам является задачей
    void Run() override { /* coroutine_.Resume(); */ }
};
// submit_task — единственное место, где владение нужно: одна аллокация в Box<...>
void ThreadPool::Submit(std::function<void()> f) { Schedule(new BoxTask{std::move(f)}); }
```

Итог: когда файберы уже запущены, синхронизируются и рекультивируются, рантайм делает **ноль** динамических аллокаций, не нагружает аллокатор (его мьютексы, разделяемое состояние), и всё работает быстрее. Аллокации остаются только там, где без них нельзя (`submit_task`, создание файбера). Это та оптимизация, которая на практике важнее «забавных `memory_order`».

### A1.2.3. Почему задача обязана быть указателем

Есть и более жёсткая причина для интрузивных **указателей** (`atomic<TaskBase*>`), которая прояснится в A1.7: в work-stealing воркер-вор **читает** массив задач чужой очереди **конкурентно** с тем, как владелец в него пишет. Атомарно читать/писать ячейку `unique_function` (большой объект с small-object optimization) **нельзя** — это data race. А указатель читать/писать атомарно **можно** (`atomic<T*>`). Поэтому без указателя хороший планировщик не написать в принципе.

## A1.3. Профилирование: контеншн на единой очереди

Запустив рантайм под нагрузкой (сотни файберов, обмен по каналам) и сняв **flame graph** (много раз фиксируем стеки потоков, склеиваем по общему префиксу; ширина «башни» — доля времени в этом стеке), видим большие плато в `ThreadPool::Submit` → `mutex lock/unlock`. Рантайм занимается почти **только** захватом мьютекса очереди задач: единый мьютекс берётся и отпускается на **каждой** операции — сплошная точка **контеншна**.

> Интерпретируйте профиль осмысленно. В синтетическом сценарии, где полезная работа = само переключение контекста, цель — чтобы доля рантайма падала, а доля переключений росла; «много» или «мало» само по себе ничего не значит — сравнивайте профили до/после.

Единая очередь — хороший, честный балансировщик (FIFO), но она **не масштабируется**: добавляя ядра (десятки–сотни на сервере), мы заставляем их спотыкаться об один мьютекс. И **lock-free очередь не спасёт**: CAS на одной ячейке всё равно сериализует потоки — на аппаратном уровне это тот же «замок» на кэш-линию (см. когерентность кэшей). Чтобы масштабироваться, на быстром пути у файберов **не должно быть общего разделяемого состояния**.

## A1.4. Шардирование как в распределённых системах

Дизайн повторяет распределённые системы: состояние (очередь задач) **шардируют**. У каждого воркера — **своя локальная очередь**. Файбер, делающий `Yield`/порождающий работу, кладёт её в локальную очередь, и воркеры работают физически параллельно с минимумом межъядерной коммуникации.

Две крайние точки дизайна:
- **Share-nothing** — много независимых однопоточных рантаймов, никакой коммуникации; максимальный параллелизм, ноль контеншна. Так устроен **Seastar** (ScyllaDB). Работает, когда нагрузка **однородна** (KV-хранилище: все запросы примерно равны по стоимости) — сбалансировал на входе один раз, и дальше воркеры загружены ровно. Не универсален.
- **Work-stealing** — локальные очереди + балансировка **воровством**. Для **неоднородной** нагрузки (один запрос дороже другого) локальные очереди разбалансируются, и простаивающий воркер должен забрать работу у занятого. Так устроен **Tokio**.

Линус Торвальдс саркастически замечал, что «написать планировщик с локальными очередями и балансировкой нагрузки несложно». Шардировать очередь — действительно просто; **по-настоящему сложна** балансировка с парковкой потоков (A1.8) — её он и не видит.

## A1.5. Модель Go: G-M-P

Канонический пример — планировщик **Go** (доклад Дмитрия Вьюкова, 2019). В нём больше сущностей, чем «поток + файбер»:
- **G (goroutine)** — единица логики пользователя.
- **M (machine)** — поток ОС, ресурс CPU; может **владеть** P и исполнять задачи, а может уйти в **блокирующий системный вызов** (Go это позволяет, в отличие от наших файберов, которым блокировки запрещены).
- **P (processor)** — ресурс планирования: держит **локальную очередь** задач (+ кэши аллокатора и пр.).

Mов может быть больше аппаратного параллелизма (лишние спят). В нашем коде P и M обычно слиты в один класс `Worker`. Структура планировщика: на каждый P — локальная очередь (**кольцевой буфер на 256**, два индекса head/tail) + одна **глобальная очередь** под мьютексом (неограниченная, интрузивный список). Глобальная очередь — это и буфер переполнения локальных, и точка приёма **внешних** задач (`submit_task` снаружи), и средство балансировки.

## A1.6. Планирование новой работы (`runqput`)

Куда попадает задача — зависит от сценария:
- **новая** горутина (`go`) и **разбуженная** (на канале/мьютексе через `goready`→`ready`→`runqput`) → в **локальную** очередь текущего P;
- горутина, сделавшая **`Gosched` (yield)** → в **глобальную** очередь: она сама сказала, что уступает процессор, поэтому её можно «отослать подальше» (пессимизация; сценарий редкий).

`runqput` читает head/tail; если в кольцевом буфере (256) есть место — кладёт и двигает tail. Здесь первая неожиданность: **head/tail — атомарные**, хотя очередь «локальная». Причина — воровство (A1.7): другие P **читают** наш буфер конкурентно. (В рантайме Go атомики ещё и с `acquire`/`release`, хотя модель памяти Go таких порядков не выражает — рантайм написан на «подпольном» Go.)

**Переполнение.** Если буфер полон, половину локальной очереди **выгружают в глобальную** (амортизация: чтобы не ходить туда часто). Чтобы критическая секция под глобальным мьютексом была **O(1)**, выгружаемые горутины сперва связывают интрузивными ссылками в список **без** мьютекса, а под мьютексом за константу прицепляют список к глобальной очереди.

## A1.7. Поиск работы (`findRunnable`) и воровство

Когда текущая задача останавливается, воркер ищет следующую (`findRunnable`) по порядку:
1. **локальная очередь** P (извлечение головы — через **CAS**, т. к. забирать могут и воры);
2. **глобальная очередь** (под мьютексом; забираем сразу пачку ≈ `size/GOMAXPROCS`, чтобы реже туда ходить);
3. **netpoll** — воркеры **сами** полят `epoll` (нет выделенного потока-поллера: «таймер-тред» из вашего планировщика на деле полит и очередь таймеров, и `epoll`);
4. **воровство** из чужих P.

**Воровство.** Простаивающий M («spinning» M) обходит другие P (≈4 раза) и забирает у жертвы **половину** её локальной очереди: читает head/tail, проходит буфер, копирует пачку, затем CAS на `head += n`. Число одновременно ворующих Mов **ограничено** — иначе они будут воровать друг у друга в хаосе без пользы.

Локальная очередь, таким образом, — **MPSC** (single producer — только владелец кладёт; multi consumer — извлекают и владелец, и воры), поэтому на стороне извлечения **CAS**. Отсюда же требование указателей из A1.2.3: вор **читает** массив одновременно с записями владельца — атомарно это возможно только для указателей. По смыслу `memory_order` здесь не нужен (это «просто чтение»), но модель памяти C++ всё равно требует `atomic` (иначе data race) — в Go это незаметно из-за его рантайм-модели.

**ABA на индексах.** head/tail — **растущие** счётчики (модуль 256 берётся лишь при доступе), а не индексы по модулю; это защищает от ABA при `head += n` (в Tokio здесь был баг ABA, позже исправленный; uint32 всё же переполняется, но крайне редко).

## A1.8. Парковка и пробуждение — настоящая сложность

Когда работы нет нигде (локально, глобально, в netpoll, у соседей), воркер должен **запарковаться**. Но мы в **распределённом мире**: проверки **устаревают мгновенно** (через микросекунду в чужой локальной очереди может появиться работа), а атомарно «узнать, что работы нет нигде» нельзя. Это врождённая сложность, не имеющая простого решения.

- **Двухфазная парковка:** воркер сначала **объявляет** намерение запарковаться, затем **ещё раз перепроверяет** все источники (глобальная, чужие локальные, netpoll); только если по-прежнему пусто — засыпает. Симметрично тот, кто **добавляет** работу, обязан разбудить парковщика.
- **Минимизация записей в разделяемое состояние.** Положить задачу в локальную очередь — локальное действие, но оно меняет **глобальный предикат** «в пуле есть работа». Если на каждый `submit` писать в разделяемый атомик «я добавил», на нём возникнет контеншн — параллелизм сломан. На быстром пути (`submit` при раскрученном пуле) допустима запись только в **локальную** очередь и, может быть, чтение разделяемого (читать параллельно можно), но **не запись**.
- **Каскадное пробуждение.** Правило: если есть **spinning**-поток, который ищет задачу, он **обязан** её найти — тогда будить никого не нужно (записи нет). Если спиннера нет, будят **одного** (не всех на пачку из N задач) — и в таком состоянии, что, найдя работу, он разбудит **следующего**. Так пробуждение «расходится каскадом» под фактическую нагрузку, без массовых записей.

Именно это (без дедлоков и без контеншна одновременно) — основное содержание задачи; «танцы», которых Линус не видит.

## A1.9. Честность: магическая 61

Шардирование ломает **честность (fairness)** в смысле «eventually»: воркеры могут крутить только локальные задачи, а застрявшая в глобальной очереди задача никогда не исполнится. Лечение: каждая **61-я** итерация `findRunnable` идёт **сначала** в глобальную очередь. Это гарантирует, что любая задача когда-нибудь будет извлечена. Константа 61 — простое число (не степень двойки), чтобы не «резонировать» с пользовательскими константами (которые обычно степени двойки); никакого фундаментального объяснения у неё нет.

## A1.10. FIFO против LIFO: tail latency против throughput

Стратегия извлечения — это компромисс между двумя **противоположными** метриками:
- **FIFO** (очередь) оптимизирует **tail latency**: для независимых пользовательских запросов «кто раньше пришёл — раньше обслужен» (никто не ждёт пришедших позже).
- **LIFO** оптимизирует **throughput и горячий кэш**: при передаче по каналу продюсер записал данные в буфер (через кэш), и хорошо бы разбудить ждавшего получателя **немедленно на том же ядре**, пока строка не вымылась из кэша. Для примитивов синхронизации (канал, мьютекс) уместен LIFO; то же делает хороший мьютекс, сериализуя критические секции так, что данные предыдущей секции «под ногами» у следующей.

Go реализует это слотом **`runnext`** — одиночная LIFO «дорожка» перед FIFO-буфером. Флаг `next` у `runqput` (его ставит, например, канал, будящий получателя) кладёт горутину в `runnext`; если слот занят, прежний жилец вытесняется в хвост локальной очереди. Тот же приём — флаг `fair` в планировщике Kotlin. Подвох: «жадный» LIFO ломает честность (пинг-понг двух файберов по каналу может навсегда занять ядро) — отсюда снова нужна периодическая проверка глобальной очереди (A1.9). Поддержать `next` на уровне нашего планировщика непросто: в его модели нет «файберов», есть лишь задачи, поэтому `next` — это протекающая, но полезная **подсказка** планировщику использовать LIFO там, где это уместно (синхронизация), и не использовать для пользовательской логики.

## A1.11. Координатор и распределённый взгляд

Итоговый дизайн — буквально распределённая система: **воркеры** с локальным состоянием (минимум коммуникации, физический параллелизм) + **координатор** — центральный компонент с разделяемым состоянием, отвечающий за **глобальные инварианты** (есть ли где-то работа; кого будить). Как и в распределённых системах, координатор — точка контеншна, поэтому записи в его состояние минимизируют, держа их **вне** быстрого пути. Понимая распределённые системы, вы узнаёте здесь те же проблемы: локально вы знаете о глобальном лишь неточно, и это принципиально. Кстати, простаивающий воркер может помогать **сборке мусора** — а GC рантайму всё равно нужен (для рекультивации в lock-free структурах, см. соответствующий файл).

Слабые модели памяти и **store buffering** всплывают и здесь — не смешивайте `memory_order` бездумно (см. файлы про модель памяти).

## A1.12. Тестирование рантайма

Планировщик такой сложности **без специального инструмента написать корректно практически невозможно**: дистанция между «кодом, похожим на правильный» и кодом, который нигде не зависает, огромна. Нужна **детерминированная симуляция с fault injection** на уровне рантайма: рандомизированный `Yield`/выбор задач провоцирует редкие порядки и гонки (в Go — рандомизация планировщика; у нас — twist, где есть и демоны, проверяющие, например, корректность condition variable). Помогайте инструменту: сценарии должны быть **маленькими** (пара потоков, пара операций), а параметры — провокационными. Особенно влиятелен **размер локальной очереди**: для маленького теста его ставят крошечным (или в 0), чтобы задействовать переполнение, глобальную очередь и воровство — самые хитрые сценарии возникают, когда работают **все** элементы сразу.

- Дмитрий Вьюков, доклад про планировщик Go (2019) — основной источник.
- Планировщики **Go**, **Tokio**, **Kotlin**, **Scala** — для сравнения реализаций одной общей идеи (work-stealing + набор инженерных оптимизаций под конкретный язык/задачу).
- Статья про work-stealing deque со **слабой моделью памяти** (формально проверенный алгоритм) — для блочного воровства, где быстрый путь владельца обходится без CAS.

Главное: хороший рантайм — это распределённая система с шардированным состоянием и аккуратным координатором; общая стратегия (work-stealing, FIFO/LIFO, двухфазная парковка) проста на словах, но корректная и эффективная реализация — большая инженерная задача, которую невозможно довести без профилирования, метрик (счётчики: сколько задач прошло через LIFO/локальную/глобальную очередь) и детерминированного тестирования.
