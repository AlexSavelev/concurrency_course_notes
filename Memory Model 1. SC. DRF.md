# Модель памяти: sequential consistency для программ без гонок

Предыдущая тема показала, что за «разделяемой памятью» стоит распределённая система из ядер. Теперь мы увидим, что эта распределённость **ломает простую семантику** программы, и чтобы писать корректный переносимый код, нужна **модель памяти (memory consistency model)**.

## 1. Модель чередования и почему она перестаёт работать

До сих пор мы рассуждали в **модели чередования (interleaving model)**: будто все потоки исполняются на одном ядре, инструкции каждого потока идут в порядке текста программы, а планировщик непредсказуемо переключает потоки. Вся сложность сводилась к перебору точек переключения (так решались `mutex`, `cond_var`, wait-group). Эта модель **справедлива только для атомиков с дефолтным `memory_order`**; стоит расставить хотя бы один слабый порядок — и ею пользоваться уже нельзя. А промышленный код синхронизации без слабых порядков не пишут. Значит, модель чередования для реального кода неверна. Почему?

### 1.1. Компилятор

Компилятор переписывает ваш код. Простой пример (виден в godbolt): функция пишет сначала в `A`, потом в `B`, а в машинном коде записи идут в **обратном** порядке. Для однопоточной программы это допустимо — она не различает порядок двух записей в разные ячейки. Опаснее в многопоточном коде:

```cpp
// Поток-продюсер           // Поток-консюмер
data = 42;                  while (!ready) {}
ready = true;               assert(data == 42);   // ожидаем увидеть 42
```

Если компилятор переставит `data = 42` и `ready = true`, синхронизация сломается. Почему он вправе так сделать? Потому что, компилируя единицу трансляции, он **не знает**, что код исполнится в нескольких потоках, — и рассуждает как про однопоточную программу.

### 1.2. Процессор: store buffer

Даже без компилятора процессор ведёт себя «странно». Сценарий **store buffering** (две ячейки `x = y = 0`):

```cpp
// Ядро 1        // Ядро 2
x = 1;           y = 1;
a = y;           b = x;
```

В модели чередования исход `a == 0 && b == 0` невозможен (одна из записей идёт первой). Но на x86 он **наблюдается**. Причина: чтобы записать ячейку, ядру нужно получить линию в эксклюзив, а это инвалидация чужих копий по шине и ожидание подтверждений — долго. Инженеры ставят между ядром и кэшом **буфер записи (store buffer)**: запись кладётся туда и «считается сделанной», ядро идёт дальше. Своя запись видна себе через store buffer, но другим ядрам — ещё нет. Поэтому оба ядра пишут «к себе», а читают из памяти/кэша старое — и оба видят 0. Это буквально система контроля версий: локальный апдейт, о котором ещё никто не знает.

**Про слово «реордеринг».** На x86 две инструкции исполняются строго по порядку (`store x`, затем `load y`) — никакого переупорядочивания на самом деле нет; просто распределённая система экономит коммуникацию, и локальные представления участников расходятся. Поэтому слово «reordering» лучше держать в кавычках: оно описывает **наблюдаемое** поведение, а не реализацию. На x86 единственный возможный «реордеринг» — store→load. На ARM оптимизаций больше (есть пример с тремя ядрами, где результат удивит сильнее), а store-буферы там ещё и громоздятся в иерархии кэшей — это точно не назвать реордерингом.

Store buffer ломает не только игрушки: он разрушал сборку мусора в рантайме Go (корраптил кучу) и приводил к потерянному пробуждению в сценарии из документации futex; на x86 это же ломает **Peterson lock** (паттерн с флажками `victim`/`want` похож на store buffering, и исход 2-0 нарушает взаимное исключение).

**Мораль:** процессоры и компиляторы оптимизируют исполнение **ценой нарушения простой семантики**. Чтобы писать переносимый код, не держа в голове таблицы реордерингов каждой архитектуры, нужна модель памяти — рамка, в которую укладываются все исполнения. Программа будет вести себя **предсказуемо, но не одинаково** на разных процессорах.

## 2. Что такое модель памяти

Модель памяти — это **часть семантики языка**: она задаёт смысл многопоточной программы. До C11 формальной модели памяти в C не было; писали под конкретный набор архитектур. Модель памяти отвечает на один из трёх вопросов (в порядке возрастания практичности):

1. как описать все возможные **исполнения** многопоточной программы;
2. какую **запись увидит каждое чтение**;
3. как **гарантировать**, что данное чтение увидит нужную запись.

Третий вопрос — рабочий. Когда вы расставляете `memory_order`, вы делаете это не «глядя на атомик», а чтобы какое-то **неатомарное** чтение **за пределами** примитива увидело нужную неатомарную запись (например, критическая секция увидела записи предыдущей).

Разные языки акцентируют разные вопросы: Java (первый промышленный язык с моделью памяти) и Linux-kernel описывают «что увидит чтение»; Go — «как гарантировать видимость» (записал в канал → прочитал из канала). Модель памяти C — **передний край (frontier)**: даёт максимум возможностей для оптимизации, но изложена сложно, размазана по стандарту и формально **до конца не достроена** (её до сих пор «чинят», см. C26). Rust официальной модели не имеет — наследует C++20. И во всех языках действует послабление: если вы используете только мьютексы и **дефолтный `memory_order`**, можно рассуждать в модели чередования и не написать ни одного `memory_order`, не пожертвовав корректностью (это лучше, чем расставить их неправильно).

## 3. Три подхода к построению модели памяти

**Операционный (operational).** Дать абстрактную машину, неотличимую для наблюдателя от реального процессора, но проще. Так задают модели **на уровне железа** (и так же устроена однопоточная семантика C — стандартная «абстрактная машина»). Для x86 операционная модель проста: память, ядра и **store buffer** между ядром и памятью (кэши с протоколом когерентности — прозрачный слой, его можно опустить). Для ARM — дерево/иерархия буферов: запись путешествует от листа (ядра) к корню (памяти), застревая в буферах на стыках; чтение тоже движется наверх и может быть обслужено промежуточной записью на развилке — так объясняются «дикие» исходы. Минус для нас: операционная модель **своя у каждой архитектуры**, а мы хотим кросс-платформенный код.

**Декларативный / аксиоматический (declarative / axiomatic).** Не про механику исполнения, а про **порядки и отношения** — математический формализм. Исполнение — это **граф**: вершины — обращения к памяти, рёбра — частичные порядки и отношения. Главное отношение — **reads-from** (стрелка от записи к чтению, которое её прочитало). Сценарий store buffering с двумя нулями рисуется как граф с reads-from-стрелками к записям инициализации. Совет лектора: при работе с `memory_order` **перестать думать про чередования и представлять графы** — это единственный корректный взгляд (неинтуитивно, но так). Так устроены модели памяти C++ и Linux-kernel (в kernel порядков ещё больше). Сложность C++ в том, что в нём **сталкиваются два подхода**: однопоточная семантика операционная (абстрактная машина), а многопоточная — декларативная (аксиомы); сочетаются они тяжело.

**Трансформационный (transformational).** Третий подход — задавать модель через допустимые преобразования программы; упоминается «на сдачу».

## 4. Sequential consistency

На уровне языка обычно встречаешь приятную вещь — вариацию на **sequential consistency (SC)** Лесли Лэмпорта:

> Результат любого исполнения программы такой же, как при некотором **последовательном** исполнении, в котором обращения к памяти из каждого потока идут в **порядке текста программы**.

Это та самая модель чередования. Тонкости:
- SC — про **наблюдаемое** (результаты чтений), а не про то, как программа реально исполняется. «Sequentially consistent исполнение» не значит «исполняется последовательно» — значит «**можно так думать**».
- SC ≠ **линеризуемость (linearizability)**. SC ограничивает только относительный порядок внутри **каждого потока**; линеризуемость добавляет ограничения **между** потоками (реальное время). В процессоре разницу почувствовать трудно, но формально различать стоит.

Обеспечивается SC барьерами. На x86 после sequentially-consistent записи компилятор вставляет **`mfence`** — инструкцию класса **барьеров памяти (memory barriers / fences)**, которая (грубо) сбрасывает store buffer и тем «запрещает» опасный store→load «реордеринг». Раньше, до моделей памяти, люди расставляли барьеры вручную под конкретные архитектуры — это сложно (документ про барьеры в Linux-kernel — тысячи строк, «можно пугать детей»). Полный разбор барьеров, переупорядочиваний и того, как `memory_order` ложится на инструкции, — в §13.

## 5. DRF-контракт: чем жертвуем

Наивная реализация SC — поставить барьер (`mfence`) **после каждой инструкции**. Это убивает производительность. Возникает компромисс дизайнера языка: с одной стороны — простая семантика для программиста, с другой — свобода оптимизаций для процессора и компилятора. Всё сразу не получить.

Неожиданный ход: ради SC жертвуют **не производительностью, а программами**. Гарантируем SC не для произвольной программы, а только для **«разумных»** — формально, для программ **без гонок данных (data-race-free, DRF)**. Интуиция: у разумной (корректно синхронизированной) программы барьеры нужны лишь в **очень ограниченных контекстах** (вокруг синхронизации), так что компилятор может расставить их экономно, оставив остальной код свободным для оптимизаций. Это и есть теорема/гарантия **SC-DRF**: *корректно синхронизированные (свободные от гонок) программы исполняются так, как будто sequentially consistent* (Adve & Hill, 1990 — общий знаменатель моделей памяти Java, C++, Go; в каждой есть свои детали — слабые `memory_order` в C++, семантика гонок в Java).

Модель памяти — это **контракт между программистом, компилятором и процессором**: вы обязуетесь дать корректную (DRF) программу, они обязуются исполнить её неотличимо от последовательной. Нарушили свою половину (гонка) — получаете **undefined behavior** (в рантайме ничего не проверяется). Реализуется контракт **схемой компиляции**: программисту дают декларативную модель (порядки, гарантии видимости), а на каждой архитектуре спускают вниз **барьеры**.

Дальнейшее (раздел 6–7) — общий знаменатель, **приближение** к модели любого языка (для иллюстраций удобны Java с простой базовой моделью и C, на котором мы пишем); это уже точнее, чем «SC для дефолтных атомиков», но всё ещё не дословная модель C++20.

## 6. Строим декларативную модель: program order и modification order

Исполнение — граф; задача — задать **границы для reads-from** (какие стрелки возможны) и формализовать ожидания, на которые мы неявно опираемся. Все гарантии будут интуитивны — «вы бы придумали их сами»; нужно лишь явно перевести интуицию в формальные отношения, потому что у процессора/компилятора **правил нет** (что не запрещено — разрешено).

**Program order (PO) / sequenced-before.** В пределах одного потока инструкции идут последовательностью — это **program order** (в C++ — **sequenced-before**). PO существует только «в нашем уме» и **ничего не обязывает** напрямую. Связанная с ним гарантия проста: в однопоточной программе reads-from устроен так, что каждое чтение видит **последнюю предшествующую в PO запись**. Компилятор, переставив две записи в разные ячейки, эту гарантию **не нарушает** — он доказал, что программа не различит порядок (наблюдаемое поведение однопоточной программы сохранено). PO — это не порядок исполнения, а порядок в тексте; противоречия с реордерингом нет.

**Конфликт (conflict).** Два обращения к памяти **конфликтуют**, если идут к одной ячейке и хотя бы одно — запись (определения в Java и C++ одинаковы). Глядя на свои программы, ячейки можно разделить на два класса: **синхронизационные** (через них пишется синхронизация — например, `state` спинлока; на них конфликты **не упорядочены**) и **данные** (голова списка под спинлоком; конфликты на них есть, но **упорядочены** через синхронизационные ячейки). Для синхронизационных ячеек язык вводит аннотацию **`std::atomic`**. Важно: `atomic` нужен не только ради атомарных инструкций (`fetch_add`, `exchange`) — это ещё и **подсказка компилятору**: «эта ячейка используется для синхронизации и упорядочивает доступ к другим ячейкам». Вокруг атомиков и строятся порядки.

**Modification order (mo) и когерентность.** На каждом атомике все записи (обычные store и RMW) выстроены в **частичный порядок modification order** — для каждого атомика это **линейный** порядок записей, но **сквозного** общего порядка между разными атомиками нет. Связанная гарантия (это и есть **когерентность** на уровне языка): чтения атомика видят **подпоследовательность** его modification order. Это ровно та картинка Маккини из темы про кэши: у ячейки как будто много значений, соседние ядра видят похожие серии (иерархическая топология, записи проталкиваются вверх), но все серии — подпоследовательности одной общей (топологически сортируемой) — это и есть когерентность. (Грубо: каждый атомик ведёт себя как отдельная sequentially-consistent ячейка; в стандарте это записано эквивалентно, но сложнее.)

## 7. Happens-before: формализация «опубликовал → увидел»

Рассмотрим публикацию через флаг (тот же паттерн — в циклическом буфере single-producer/single-consumer и в спинлоке):

```cpp
// Поток T0 (продюсер)        // Поток T1 (консюмер)
data = 42;                    if (flag.load()) {         // увидели флаг
flag.store(true);                 use(data);             // обязаны увидеть 42
                              }
```

Ожидание: если `T1` увидел флаг взведённым, то запись `data = 42` (которая в тексте `T0` идёт **до** `flag.store`) ему уже **видна**. В спинлоке аналогично: взяв лок и записав список, поток делает `unlock` (store в `state`); другой поток, увидев освобождение через свой `exchange`, ожидает увидеть записи предыдущей критической секции.

Ключевое слово в этих рассуждениях — «**произошло до**». Это частичный порядок **happens-before (HB)**, и связанная гарантия такова: **если конфликтующая запись happens-before чтения, то чтение обязано её увидеть**.

**Лэмпорт: причинность, а не время.** Понятие восходит к статье Лесли Лэмпорта про порядок событий в распределённых системах. Система — это однопоточные **акторы (actors)**: актор может сделать локальный шаг либо отправить сообщение, которое другой актор когда-то получит. Глобального физического времени нет — идеальные синхронизированные часы в системе с задержками построить нельзя; каждый узел понимает лишь порядок **своих** событий. Поэтому Лэмпорт говорит о **логическом времени / причинности**. Определение HB из двух частей: (1) если на одном акторе событие A предшествует B, то A HB B; (2) если A — отправка сообщения, B — его получение, то A HB B («послать сообщение в прошлое нельзя»). Дальше — транзитивное замыкание. Ключевое: `A HB B` ⟹ A произошло раньше B, но **не наоборот** — два события могут быть во времени упорядочены, а по HB **не** связаны.

**Concurrency = ¬happens-before.** Отсюда буквальное определение: два события **конкурентны (concurrent)**, если между ними **нет** happens-before ни в одну сторону. (Та же «чередуемость», что у `co_await` в корутинах, — concurrency как отсутствие порядка.)

**Перенос на разделяемую память.** Узлы → потоки (последовательные акторы → даёт первую часть: program order ⟹ HB). Сообщения → атомики: запись — «отправка в провод», чтение — «получение». Это даёт вторую часть — **synchronizes-with (SW)**: если A — запись атомика в потоке T, B — чтение этого атомика в потоке T′≠T, и B **прочитало именно A**, то A synchronizes-with B (через границу потоков протягивается HB). Сценарий один и тот же везде — **message passing**: что-то сделали → опубликовали через атомик (флаг, `unlock` спинлока, `mutex.unlock`, зажгли event, отметили wait-group) → другой поток это увидел и пользуется результатом. RMW годится с **обеих** сторон SW (это и чтение, и запись): в спинлоке `unlock` пишет `state=false`, а `lock` через `exchange` это `false` **читает** — возникает SW между критическими секциями.

**Итоговое определение:** **happens-before = транзитивное замыкание (program order ∪ synchronizes-with)⁺.** Гарантия (как в Java, та же): **неатомарное чтение видит последнюю предшествующую в HB запись** — прямое продолжение однопоточной интуиции «чтение видит предыдущую запись», только «до/после» теперь включает межпотоковую передачу сообщений.

**Метафора моста.** Когда `lock` synchronizes-with `unlock`, между потоками протянулся «мостик», и **все** неатомарные записи предыдущей критической секции «перетекли» по нему и стали видны — в следующей секции вы наблюдаете их разом.

**HB ≠ физическое время.** Два события в HB не обязаны быть так же упорядочены во времени (компилятор переставляет записи). И обратно: два конфликтующих неатомарных обращения, разнесённые хоть на час, не обязаны быть в HB — HB про причинность, не про время.

## 8. Happens-before в Java и C++; баг с `consume`

Модель памяти **Java** проста: `x HB y`, если (1) x, y в одном потоке по program order, либо (2) `x synchronizes-with y`, плюс транзитивность — ровно наше определение.

В **C++** сложнее: в зависимости от стандарта в нём до 3–3.5 разных «happens-before». То, что мы построили, — это **simply-happens-before** (`sequenced-before` ∪ `synchronizes-with`, транзитивно). Беда была в `memory_order_consume`: «настоящий» happens-before включал **inter-thread-happens-before** с consume, который **не транзитивен** — нетранзитивная причинность крайне неудобна и странна. Это **починили в C++26**, запретив `consume`: теперь happens-before снова транзитивен и совпадает с simply-happens-before. (Отдельно остаётся **strongly-happens-before** — спецэффект слабых моделей, нужен для `seq_cst`; о нём — в файле про модель C++20.) Практический совет: всегда фиксируйте, **в каком стандарте** (C++11/20/26) вы читаете определения, иначе комбинаторный взрыв в документации сбивает с толку.

## 9. Гонка данных — строгое определение

Два обращения к памяти **конфликтуют (conflict)**, если идут к одной ячейке и хотя бы одно — запись. **Гонка данных (data race)** — два конфликтующих обращения, **не упорядоченные по HB**, причём (в формулировке через эту простую модель) хотя бы одно **не атомарное** и они на разных потоках. Гонка → **UB**.

Важное следствие: два **чтения** не конфликтуют — поэтому одновременные чтения из разных потоков **не образуют гонку**. На этом стоит RW-spinlock/RW-mutex: под write-локом пишем, под read-локом из нескольких потоков читаем одновременно — эти чтения по HB не упорядочены, но гонки нет. А две **записи** без HB между ними — гонка.

Как проверять отсутствие гонок (DRF): по каждой ячейке во **всех** исполнениях все **записи** в неё должны быть упорядочены по HB (чтения между собой упорядочивать не требуется). Именно это определение реализуют ThreadSanitizer и подобные инструменты — ищут конфликтующую пару без HB.

Этот «висящий» случай — две неупорядоченные по HB записи в одну ячейку, когда непонятно, что вернёт чтение, — мы и заметаем под ковёр, объявляя гонкой: гарантия HB для него просто **не определена**. Корректная синхронизация обязана его исключить.

## 10. Synchronization order и sequential consistency

Гарантий §7 **не хватает**, чтобы починить Peterson lock: в сценарии store buffering (два флага, каждый поток пишет свой и читает чужой) чтения читают инициализацию, SW не возникает, и исход «два нуля» (нарушение взаимного исключения) ничем не запрещён. Нужен ещё один порядок — и он откровенный «костыль»: **synchronization order S** — единый сквозной тотальный порядок на **всех** обращениях к атомикам (и чтениях, и записях), с требованием «чтение читает последнюю по S запись». Это эквивалентно тому, что **на seq_cst-атомиках действует sequential consistency** (чередование), а в чередовании «два нуля» невозможны — Peterson чинится. (В Java это буквально total order на synchronization actions; в C++ слова `synchronization order` нет — есть тотальный порядок S с более тонкими ограничениями, см. файл про C++20.)

**Набросок доказательства SC-DRF.** Исполнение — граф с порядками modification order, happens-before и synchronization order. Утверждается: из них можно собрать **единый** тотальный порядок T (топологическая сортировка `synchronization order ∪ happens-before`) такой, что в T **каждое чтение читает последнюю запись** — то есть программа выглядит sequentially consistent. Чтение атомика читает последнее по S (по построению T); для неатомарного чтения R надо показать, что «последняя в HB запись» совпадает с «последней в T». От противного: если между «правильной» записью W и R в T влезла другая запись W′ в ту же ячейку — W и W′ конфликтуют, и раз **гонок нет**, они упорядочены по HB; разбор направлений HB противоречит построению T. Значит, в DRF-программе видимость глобального порядка обеспечивается, хотя глобальный порядок на **всех** обращениях нигде не требовался.

## 11. Откуда берётся производительность

SC мы получили; обещали ещё и перформанс — вот откуда он. Пусть программа без гонок: поток делает неатомарные записи `W`, затем атомарную запись (например, `unlock`), синхронизирующуюся с потоком T′. Поскольку гонок нет, T′ может увидеть любую из `W` **только** после того, как между ним и `W` установился HB — а HB приходит «оптом» через атомик. Значит, T′ **не наблюдает относительный порядок** записей `W` — он видит их **все разом**, как при выходе из мьютекса. А раз относительный порядок между точками синхронизации не наблюдаем, **компилятор и процессор свободны переупорядочивать** инструкции внутри этого промежутка. Барьер ставится только в точке синхронизации — это «порог», который локальные оптимизации не пересекают. Итог парадоксально мощный: **локальные** оптимизации (компилятор/процессор переставляют соседние инструкции, не понимая глобальных инвариантов) дают **глобальную** гарантию SC. В этом вся затея.

## 12. Слабые модели памяти и `memory_order`

Модель памяти называется **слабой (weak)**, если допускает **не**-sequentially-consistent исполнения (не описываемые чередованием) — например, store buffering. Как только вы ставите **хотя бы один** `memory_order` слабее `seq_cst`, вы «проваливаетесь» в мир слабых моделей (а любая аппаратная модель слаба — SC для железа неестественна и неэффективна).

Как об этом думать: **каждый `memory_order` участвует в образовании определённых порядков.**
- `seq_cst` — участвует и в **S**, и в HB.
- `release`/`acquire` — образуют **synchronizes-with** и HB, но **не** попадают в S.
- `relaxed` — даёт только **modification order** (synchronizes-with не возникает: для SW нужны release на записи и acquire на чтении).

Поэтому Peterson на `release`-записях небезопасен: нет S → исход «два false» не запрещён. Оптимизировать код = **формулировать самые слабые порядки**, которые рантайм обязан обеспечить: нужен HB — оставляем release/acquire; не нужен S — убираем seq_cst. Меньше требуемых отношений (стрелок) → меньше ограничений компилятору/процессору → на целевой архитектуре получаются **оптимальные барьеры** → больше производительности. В этом и идея слабых декларативных моделей.

**Практическая мудрость (Go, Boehm).** Sequential consistency нужна редко. Go советует вместо разделяемой памяти и мьютексов — **каналы**: явная коммуникация = паттерн message passing, которому достаточно release/acquire (HB) и который хорошо ложится на аппаратные модели. Хансу Бойму (автору модели памяти C++) принадлежит первая рекомендация: «**пишите мьютексы, не умничайте**». Лучше корректный код, чем быстрый и неправильный.

(Сама же модель местами «сломана» — есть сценарии, которые она не может запретить формально и запрещает текстом-«костылём»: out-of-thin-air, а также рассогласование S и HB. Это — в файле про модель C++20.)

## 13. Барьеры памяти, переупорядочивания и `memory_order` на практике

Формальный аппарат (§6–§12) полезно «приземлить»: что реально вставляет компилятор и как выбрать `memory_order`. Барьеры уже мелькали (store buffer §1.2, `mfence` §4) — соберём всё вместе.

### 13.1. Четыре переупорядочивания и `mfence`

Все «реордеринги» (наблюдаемые, §1.2) — это перестановки соседних доступов к **разным** ячейкам, и их ровно четыре:

| Перестановка | x86 (TSO) | ARM/POWER |
|---|---|---|
| StoreStore (W→W) | нет | да |
| **StoreLoad (W→R)** | **да** | да |
| LoadLoad (R→R) | нет | да |
| LoadStore (R→W) | нет | да |

x86 (модель **TSO**, total store order) допускает **ровно одну** перестановку — **StoreLoad**: запись оседает в store buffer, а более поздний load к **другой** ячейке проскакивает вперёд (буфер ещё не слит в кэш). Это и порождает store buffering (§1.2). Полный барьер **`mfence`** **осушает store buffer**, не давая последующему load обогнать предыдущий store, — то есть запрещает StoreLoad. ARM/POWER допускают все четыре перестановки, поэтому барьеров там больше и они разных видов (`dmb ish`/`ishst`/`ishld`).

### 13.2. Как `memory_order` ложится на инструкции

Декларативные порядки (§12) компилятор спускает в инструкции по-разному на каждой архитектуре:

| Операция | x86 | ARMv8 |
|---|---|---|
| `relaxed` load/store | `mov` | `ldr`/`str` |
| `acquire` load | `mov` (бесплатно) | `ldar` |
| `release` store | `mov` (бесплатно) | `stlr` |
| `acq_rel` RMW | `lock`-инструкция (`xchg`/`lock add`/`cmpxchg`) | `ldaxr`/`stlxr` |
| `seq_cst` store | `mov` + `mfence` (или `xchg`) | `stlr` |
| `seq_cst` load | `mov` | `ldar` |

Панчлайн: на x86 `release`/`acquire` **бесплатны** (обычный `mov` — TSO и так запрещает StoreStore/LoadLoad/LoadStore), и платишь **только** за `seq_cst`-**запись** (`mfence`, чтобы убить StoreLoad). Поэтому «безопасный по умолчанию `seq_cst`» дорог именно на записях, а `release`/`acquire` для message passing почти бесплатны. На ARM, наоборот, и `acquire`/`release` требуют спец-инструкций (`ldar`/`stlr`).

### 13.3. `std::atomic_thread_fence` — отдельные барьеры

Барьер можно поставить не на операцию, а **отдельной инструкцией** — `std::atomic_thread_fence(order)`:
- `release`-fence: ни одна предыдущая запись/чтение не «перепрыгнет» вперёд через него (запрещает LoadStore + StoreStore);
- `acquire`-fence: ни одна последующая операция не «перепрыгнет» назад (LoadLoad + LoadStore);
- `seq_cst`-fence: полный барьер (на x86 — `mfence`).

Применяют, когда барьер нужен между **группой** операций, а не на каждой (например, один fence после серии relaxed-записей вместо release на каждой). Тонкости формализации (как fence достраивает порядок S) — в файле про C++20, §8.

### 13.4. Шпаргалка: какой `memory_order` и зачем (микропримеры)

**`relaxed` — только атомарность, порядок не нужен.** Счётчик, где важна лишь сумма:
```cpp
std::atomic<int> calls{0};
calls.fetch_add(1, std::memory_order_relaxed);   // RMW всегда видит последнее значение в MO
```
Годится для статистики; **не** годится, чтобы «сигналить» о готовности данных (нет HB).

**`release`/`acquire` — передать данные (один писатель → один читатель).**
```cpp
int data; std::atomic<bool> ready{false};
// писатель:                              // читатель:
data = 42;                                if (ready.load(acquire))   // увидел true ⇒
ready.store(true, release);               //     use(data);          //   гарантированно 42
```
`release`→`acquire` даёт SW и HB: при `true` все записи писателя до `store` видны читателю. Этого достаточно для «опубликовал → увидел».

**`acq_rel` — RMW, который одновременно «забирает» и «отдаёт».** Захват спинлока:
```cpp
while (locked.exchange(true, std::memory_order_acquire)) {}   // acquire при входе
// критическая секция
locked.store(false, std::memory_order_release);               // release при выходе
```
Здесь `exchange` для захвата достаточно `acquire`; когда же RMW должен и принять чужие записи, и опубликовать свои (например, счётчик ссылок), берут `acq_rel`.

**`seq_cst` — когда `acq_rel` мало: store buffering.** Запрещаем `a==0 && b==0`:
```cpp
std::atomic<int> x{0}, y{0};
// поток 1:                          // поток 2:
x.store(1, seq_cst);                 y.store(1, seq_cst);
int a = y.load(seq_cst);             int b = x.load(seq_cst);
```
На `release`/`acquire` исход `a==0 && b==0` **возможен**; на `seq_cst` — запрещён.

**Почему `seq_cst` сильнее `acq_rel`.** `release`/`acquire` упорядочивают операции лишь **относительно своей** синхронизирующей переменной и **не** запрещают StoreLoad-перестановку к **другой** ячейке. Выше каждый поток пишет свою ячейку, затем читает чужую — `acq_rel` не мешает обоим load'ам обогнать свои store, и оба видят `0`. `seq_cst` добавляет единый тотальный порядок **S** (§10) на все seq_cst-операции, в котором один store обязан стоять раньше парного load, — это и запрещает «два нуля». На x86 ровно это и есть `mfence` между store и load (§13.1). Канонические места, где `seq_cst` действительно нужен, — store-buffering/IRIW-паттерны (несколько открытых атомиков, читаемых перекрёстно); для одной синхронизирующей пары хватает release/acquire.

## 14. Итог

- Модель чередования верна лишь для дефолтных атомиков; компилятор (single-thread-эквивалентные перестановки) и процессор (store buffer → store buffering) её ломают; «реордеринг» — про наблюдаемое поведение, не про реализацию.
- **Модель памяти** — часть семантики языка; подходы: операционный (x86 store buffer, ARM-дерево) и декларативный (граф обращений с отношениями).
- Кирпичи: **program order**, **modification order** + когерентность, **synchronizes-with** (release→acquire через атомик-сообщение), **happens-before** = (PO ∪ SW)⁺ (причинность по Лэмпорту; concurrency = ¬HB), **synchronization order S** (чинит Peterson, даёт SC на seq_cst).
- Гарантия HB: чтение видит последнюю предшествующую в HB запись; неупорядоченные конфликтующие доступы = **гонка** = UB; два чтения не конфликтуют (RW-lock).
- **SC-DRF**: жертвуем не перформансом, а программами — SC только для **DRF**-программ; перформанс возвращается потому, что в DRF-программе записи видны «оптом» в точке синхронизации, а между точками компилятор/процессор свободны (локальные оптимизации → глобальная гарантия).
- Слабые модели: каждый `memory_order` образует свои порядки (seq_cst→S+HB; rel/acq→SW+HB; relaxed→MO); оптимизация = ослабление требуемых порядков → оптимальные барьеры. Совет: не умничать (мьютексы, каналы).
- Продолжение (файл про C++20): формальные 4 требования, `release sequence`, `reads-before`, SC через ацикличность, «SC fix», out-of-thin-air.
