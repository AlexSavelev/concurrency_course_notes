# Условные переменные, семафоры и пул потоков

Условная переменная (condition variable) — второй по значимости примитив после мьютекса. Она позволяет потоку **эффективно ждать** наступления условия и быть разбуженным в момент его изменения. На ней строятся семафоры, барьеры, блокирующие очереди и пулы потоков.

## 1. Модельная задача: счётный семафор

Будем разрабатывать **счётный семафор (counting semaphore)** — он хранит целочисленный счётчик разрешений. `acquire()` ждёт, пока счётчик не положителен, затем уменьшает его; `release()` увеличивает счётчик и будит ожидающего. Через эту задачу естественно вывести необходимость condition variable.

```cpp
class semaphore {
public:
    explicit semaphore(int initial = 1);
    void acquire();
    void release();
private:
    int count;
};
```

### 1.1. Наивно: активное ожидание

```cpp
void semaphore::acquire() {
    while (count == 0) std::this_thread::yield();   // крутимся, уступая процессор
    --count;
}
```

Две беды. **Гонка данных:** доступ к `count` не синхронизирован, два потока могут увидеть `count == 1` и оба сделать `--count`, уведя счётчик в минус (UB). **Неэффективность:** **активное ожидание (busy waiting)** жжёт процессор и на однопроцессорной системе может вовсе не дать продвинуться тому, кто увеличит счётчик.

### 1.2. Мьютекс плюс фиксированный сон

```cpp
void semaphore::acquire() {
    std::unique_lock<std::mutex> lock(mtx);
    while (count == 0) {
        lock.unlock();
        std::this_thread::sleep_for(std::chrono::milliseconds(10));   // угадываем время
        lock.lock();
    }
    --count;
}
```

Гонки нет, но мы **гадаем** интервал сна: мало — нагрузка на CPU, много — растёт задержка реакции. Нужен механизм, позволяющий **уснуть до явного пробуждения** в момент изменения условия. Это и есть condition variable.

## 2. Condition variable

**`std::condition_variable`** предоставляет:
- `wait(lock)` — **атомарно** освобождает мьютекс и паркует поток; при пробуждении снова захватывает мьютекс перед возвратом;
- `notify_one()` — будит один ожидающий поток (если есть);
- `notify_all()` — будит все.

Перед `wait` поток обязан владеть мьютексом — это и обеспечивает атомарность «проверить условие → уснуть».

### 2.1. Почему нужен мьютекс и почему атомарность критична

Если бы поток сначала отпустил мьютекс, а потом отдельно уснул, то между этими шагами другой поток успел бы изменить условие и послать `notify` — уведомление пришло бы в «пустоту», а наш поток уснул бы навсегда. Это **потерянное пробуждение (lost wakeup)**. `wait` устраняет его, выполняя «отпустить мьютекс и встать в очередь ожидания» неделимо. Поэтому написать `cv.wait()` без мьютекса нельзя.

### 2.2. Spurious wakeup и обязательный цикл `while`

Рассмотрим ошибочный вариант:

```cpp
void semaphore::acquire() {
    std::unique_lock<std::mutex> lock(mtx);
    if (count == 0) cv.wait(lock);   // ОШИБКА: if вместо while
    --count;
}
```

Здесь две проблемы сразу. Во-первых, между пробуждением и фактическим захватом мьютекса внутри `wait` другой поток может вклиниться, сделать свой `acquire` и снова обнулить счётчик; проснувшийся, не перепроверив условие, сделает `--count` в минус. Во-вторых, стандарт допускает **ложное пробуждение (spurious wakeup)**: `wait` может вернуться вообще без `notify` (это упрощает реализацию в ядре). Оба случая лечит перепроверка условия в цикле:

```cpp
void semaphore::acquire() {
    std::unique_lock<std::mutex> lock(mtx);
    while (count == 0) cv.wait(lock);   // выходим только когда условие реально верно
    --count;
}
```

Эквивалентная форма с предикатом (тот же `while` внутри):

```cpp
cv.wait(lock, [&] { return count > 0; });
```

### 2.3. Интерфейс полностью

- `wait(lock)`, `wait(lock, pred)` — ожидание (вторая форма = `while (!pred()) wait(lock);`).
- `wait_for(lock, dur[, pred])`, `wait_until(lock, tp[, pred])` — ожидание с таймаутом.
- `notify_one()`, `notify_all()`.
- `std::condition_variable_any` — работает с любым *Lockable* (например, `shared_mutex`), ценой небольших накладных расходов; обычный `condition_variable` привязан к `unique_lock<mutex>`.

### 2.4. Корректная реализация семафора

```cpp
class semaphore {
public:
    explicit semaphore(int initial = 1) : count(initial) {}

    void acquire() {
        std::unique_lock<std::mutex> lock(mtx);
        while (count == 0) cv.wait(lock);
        --count;
    }

    void release() {
        {
            std::unique_lock<std::mutex> lock(mtx);
            ++count;
        }                       // <-- отпускаем мьютекс ДО notify (см. §2.6)
        cv.notify_one();
    }
private:
    int count;
    std::mutex mtx;
    std::condition_variable cv;
};
```

### 2.5. `notify_one` против `notify_all`

`notify_one` будит один поток — эффективнее: остальные не просыпаются, чтобы тут же снова уснуть (**грохочущее стадо, thundering herd**). `notify_all` нужен, когда изменение может удовлетворить **сразу нескольких** ждущих, или когда они ждут **разных** условий на одной cv (в нашем семафоре каждый `release` добавляет ровно одно разрешение, поэтому хватает `notify_one`). С `notify_all` код тоже корректен — просто менее оптимален.

### 2.6. Тонкость: `notify` под мьютексом или после него

Менять предикат (`++count`) **необходимо под мьютексом** — иначе data race. А вот сам `notify_*` можно вызывать **после** освобождения мьютекса. Если будить, держа мьютекс, разбуженный поток немедленно упрётся в ещё занятый мьютекс и снова заснёт — лишнее переключение контекста («hurry up and wait»). Поэтому в `release` выше `notify_one` вынесен за пределы критической секции. Оба варианта корректны; вынос — микрооптимизация против wakeup-contention.

### 2.7. Интуиция и связь с futex

Картинка, которую трудно забыть: есть **комната с буфером**, попасть в неё можно только пройдя **периметр-мьютекс** (`lock`). Внутри вы в одиночестве трогаете буфер: продюсер кладёт элемент, консюмер забирает. Если консюмер вошёл и увидел пустой буфер, он уходит в **кладовку** (`cv.wait`): покидая периметр, он отпускает мьютекс. В кладовке может скопиться несколько ждущих. Когда продюсер берёт свободный мьютекс, кладёт элемент и говорит `notify_one`, один поток выходит из кладовки — но чтобы вернуться в комнату, ему снова нужно пересечь периметр (взять мьютекс). Поэтому `wait` на выходе обязан перезахватить мьютекс.

Эта же картинка объясняет **race condition «украденного» элемента**, из-за которого нужен `while`, а не `if`. Консюмер разбужен и идёт перезахватывать мьютекс. Но в этот момент мьютекс может перехватить **другой** поток, только что вошедший в `pop`: он увидит непустой буфер, заберёт элемент и уйдёт. Когда разбуженный наконец войдёт, буфер снова пуст — предикат опять ложен. Поэтому проверка обязана быть циклом: цикл заодно скрывает и spurious wakeups.

Наконец, condition variable и futex решают **одну задачу в разном масштабе**: futex ждёт, пока **ячейка памяти** примет нужное значение (этого хватает для мьютекса, где состояние — одно слово); condition variable ждёт **произвольный предикат на произвольном разделяемом состоянии**. Поэтому у обоих неинтуитивный API одного покроя. И тот, и другой — примитивы для **построения других** примитивов (семафоров, барьеров, очередей): их сложный API не должен торчать наружу к пользователю, который работает уже с конкретным сценарием (семафор выдаёт разрешения, барьер пропускает накопившихся). Реализация cv через futex (счётчик поколений) разобрана в файле про спинлок/атомик/мьютекс.

## 3. Стандартный `std::counting_semaphore` (C++20)

Свою реализацию полезно сопоставить со стандартной.

```cpp
template <std::ptrdiff_t LeastMaxValue = /* реализационно */>
class std::counting_semaphore;

using std::binary_semaphore = std::counting_semaphore<1>;
```

API: `acquire()`, `try_acquire()`, `try_acquire_for(dur)`, `try_acquire_until(tp)`, `release(update = 1)` (можно добавить сразу несколько разрешений), статический `max()`. Параметр шаблона `LeastMaxValue` — гарантированный потолок счётчика, известный компилятору (позволяет выбрать компактное внутреннее представление).

Два пункта, которые меняют картину по сравнению с мьютексом:

1. **`release` может вызывать другой поток**, не тот, что делал `acquire`. Семафор моделирует **передачу разрешения** между потоками (producer → consumer), тогда как мьютекс обязан освобождаться тем же потоком, что захватил. Поэтому семафор — естественный примитив для «сигналинга», а не только для взаимного исключения.
2. **Реализация легче, чем mutex + cv.** Стандарт разрешает строить семафор прямо на атомике с парковкой через `futex`/`std::atomic::wait`, без отдельной пары мьютекс+условная переменная. Наша учебная версия педагогична, но в проде стандартный семафор обычно дешевле.

### 3.1. Кирпич под капотом: `std::atomic::wait` / `notify` (C++20)

```cpp
std::atomic<int> a{0};
a.wait(0);                 // спать, пока значение == 0 (futex-подобная парковка по адресу)
// в другом потоке:
a.store(1); a.notify_one();
```

`std::atomic::wait/notify_one/notify_all` — низкоуровневый аналог condition variable прямо на атомиках, без явного мьютекса. Именно на нём (а в Linux — на `futex`) строятся стандартные семафоры и быстрые мьютексы. Подробное устройство `futex` и реализация cv через него — отдельная тема; здесь важно увидеть единую линию: cv, семафор, atomic wait — это варианты одного механизма «заснуть на адресе до уведомления».

## 4. Применение: пул потоков (thread pool)

Поток на клиента дорог (создание/уничтожение — тяжёлые операции, тысячи потоков перегружают планировщик). Решение — заранее создать фиксированное число **воркеров (workers)**, разбирающих задачи из общей **очереди задач (task queue)**. Воркер крутит бесконечный цикл: берёт задачу, если очередь пуста — спит на cv; при добавлении задачи один воркер просыпается.

### 4.0. Зачем пул и каким должен быть его API (дизайн)

Прежде чем писать пул, стоит понять, **зачем** он и почему его API именно такой — это не выводится из реализации, а берётся из опыта системного дизайна.

**Ключевое наблюдение: M:N.** Единица **конкуренции** на уровне нашей логики (запрос клиента, горутина, файбер, future-корутина) и единица **исполнения** ОС (поток) не сопоставимы один к одному: единиц конкуренции хотим иметь сколько угодно много (сотни тысяч, миллионы), а потоков — ограниченное число (примерно по числу ядер). Поэтому единицы конкуренции **мультиплексируют** и плотно пакуют в немного потоков — отношение «многие к одному» (M:N). Эхо-сервер «поток на клиента» нарушал это: ОС выдаёт потоки как виртуальные ядра, ожидая, что их **утилизируют**, а не блокируют. (Как из задач вырастают файберы/корутины — следующие темы.)

**Пул — это рантайм, «ОС для нашей программы».** В корне почти любой конкурентной программы лежит пул/рантайм, а весь полезный код — это задачи в нём. Задачи **сами сабмитят новые задачи** (так выражается, например, параллельный merge sort: он сложнее quicksort, потому что требует выстраивать **зависимости** между подзадачами — сначала собрать из частей). В Rust/Tokio это видно буквально: атрибут `#[tokio::main]` разворачивается в `main`, который строит `Runtime` и запускает в нём асинхронную функцию.

**Минимальный API как осознанный дизайн (negative space).** Сложность пула не в реализации, а в том, чего в нём **нет**. Достаточно одного метода `submit(task)` с предельно простой гарантией: «задача однажды исполнится одним из воркеров». Намеренно **отсутствуют**: возврат результата, возврат ошибки, ожидание конкретной задачи, построение зависимостей между задачами. Раздутые API (Java `ForkJoinPool`, многие C++-пулы — `submit`, возвращающий future, `detach`, `parallel-for`) — это, как правило, **лишнее**. Лучше принцип единственной ответственности (SOLID): у пула одна задача — исполнить код в воркере; а результат/ошибку/ожидание дают **ортогональные** инструменты, которые комбинируются с пулом (см. ниже WaitGroup, а также `future` в §4.3 и отдельную тему).

**WaitGroup** — простейший такой ортогональный инструмент: счётчик незавершённой работы, который умеет `add(n)`, `done()` (декремент) и `wait()` (ждать обнуления). Им дожидаются завершения **группы** задач, не усложняя API самого пула:

```cpp
WaitGroup wg;
wg.add(tasks.size());
for (auto& t : tasks) pool.submit([&wg, t] { t(); wg.done(); });
wg.wait();                        // блокируемся, пока все задачи не вызовут done()
```

**Гигиена: в задаче пула нельзя блокироваться.** Если задача заснёт на блокирующем вызове (сокет, futex, долгий мьютекс), она занимает **целый воркер**, то есть отнимает у всей программы виртуальное ядро. При `N` воркерах достаточно `N` заблокированных задач, чтобы пул встал. Ждать наш код будет (сокета, сообщения из канала, захвата мьютекса) — но не **блокируя поток**; именно отсюда растут неблокирующий I/O и файберы/корутины (см. §5.3 и соответствующие темы).

**Старт/стоп как явные методы, а не только конструктор/деструктор.** Тяжёлую работу (запуск потоков) удобно выносить из конструктора в метод `start()`: конструктор — особое место (что делать при исключении в нём?), и явный `start` даёт больше свободы конфигурации. Симметрично `stop()` лучше деструктора тем, что у него виден **precondition**: к моменту `stop()` все задачи в пуле должны завершиться. (В реализации ниже завершение сделано через RAII-деструктор — это тоже корректный выбор; здесь важно понимать предусловие остановки.)

### 4.1. Сначала — переиспользуемая блокирующая очередь

Полезно выделить **блокирующую очередь (blocking queue)** в самостоятельную, отдельно тестируемую абстракцию: пул тогда становится тонкой надстройкой над ней.

Несколько дизайн-решений ещё до кода. Во-первых, очередь — это **не контейнер для хранения данных, а инструмент коммуникации** между потоками, поэтому у неё **нет метода `empty()`**: его результат бессмыслен (через наносекунду очередь уже не пуста). Вместо «проверить и забрать» нужна осмысленная семантика `pop` — **блокирующая**: если элемента нет, поток паркуется до его появления. Во-вторых, у очереди есть параметры, которые стоит отразить **в самом имени**: сколько бывает отправителей/получателей (**SPSC / MPSC / MPMC** — single/multi producer/consumer) и ограничена ли ёмкость (bounded / unbounded). Для пула это **MPMC** (и сабмитить, и разбирать могут многие потоки) и, как обсудим, **unbounded** — то есть честное имя классу было бы `UnboundedBlockingMPMCQueue`.

Почему для пула очередь **неограниченная**? Нагрузку на пул трудно оценить заранее: задачи порождаются для каждого клиента независимо и неявно (одна высокоуровневая операция = много задач под капотом). А bounded-очередь вносит риск **дедлока**: задача делает `submit` подзадачи, но очередь полна, `submit` блокируется — а разгрести её некому, потому что все воркеры заняты, в том числе этой самой задачей. Но «неограниченная очередь» не означает «съедим всю память»: **обратное давление (backpressure) ставится выше по стеку**, на входе в систему. Так устроен, например, микросервисный фреймворк Finagle: перед пулом стоит асинхронный **семафор** (`ConcurrencyLimit`), пропускающий не более `K` клиентов одновременно, а лишних — отвергающий. Это сознательный принцип системного дизайна: обслужить ограниченное число клиентов **хорошо** лучше, чем всех плохо (качество сервиса деградирует, если пытаться обслужить всех). Тогда число задач в пуле ограничено сверху как (число допущенных клиентов) × (константа из вашей логики).

```cpp
template <typename T>
class blocking_queue {
public:
    void push(T value) {
        {
            std::lock_guard<std::mutex> lock(mtx);
            q.push(std::move(value));
        }
        cv.notify_one();
    }

    // Блокирующее извлечение. Возвращает false, если очередь закрыта и пуста.
    bool pop(T& out) {
        std::unique_lock<std::mutex> lock(mtx);
        cv.wait(lock, [&] { return closed || !q.empty(); });
        if (q.empty()) return false;          // closed && empty
        out = std::move(q.front());
        q.pop();
        return true;
    }

    void close() {
        {
            std::lock_guard<std::mutex> lock(mtx);
            closed = true;
        }
        cv.notify_all();                       // будим всех, чтобы вышли
    }
private:
    std::queue<T> q;
    std::mutex mtx;
    std::condition_variable cv;
    bool closed = false;
};
```

### 4.2. Пул потоков над очередью (обобщённый, exception-safe)

```cpp
class thread_pool {
public:
    explicit thread_pool(size_t n) {
        for (size_t i = 0; i < n; ++i)
            workers.emplace_back([this] { worker_loop(); });
    }

    // Возвращает false, если пул уже останавливается (политика отказа после stop).
    template <typename F>
    bool enqueue(F&& f) {
        if (stopping.load(std::memory_order_acquire)) return false;
        tasks.push(std::function<void()>(std::forward<F>(f)));
        return true;
    }

    ~thread_pool() {
        stopping.store(true, std::memory_order_release);
        tasks.close();                         // разбудит всех воркеров
        for (auto& w : workers) w.join();      // дренируем оставшиеся задачи
    }
private:
    void worker_loop() {
        std::function<void()> task;
        while (tasks.pop(task)) {              // false => очередь закрыта и пуста
            try {
                task();
            } catch (const std::exception& e) {
                std::cerr << "task exception: " << e.what() << '\n';
            } catch (...) {
                std::cerr << "task unknown exception\n";
            }
            // воркер НЕ умирает от исключения в задаче — иначе пул деградирует
        }
    }

    blocking_queue<std::function<void()>> tasks;
    std::vector<std::thread> workers;
    std::atomic<bool> stopping{false};
};
```

Ключевые решения:
- **Корректное завершение.** `close()` выставляет флаг и делает `notify_all`; воркеры, спящие в `pop`, просыпаются, видят «закрыто и пусто» и выходят. Без `notify_all` (только `notify_one`) проснулся бы один, остальные зависли бы навсегда, и `join` в деструкторе не вернулся бы.
- **Дренирование.** Оставшиеся в очереди задачи доисполняются до выхода (graceful shutdown). Если нужна немедленная остановка — добавляют отдельный флаг «бросить недоделанное».
- **Политика после остановки.** `enqueue` после начала завершения возвращает `false` — без этого судьба поздней задачи была бы неопределённой.
- **Exception-safety.** Исключение из задачи логируется, воркер продолжает работу; иначе пул терял бы воркеров по одному.

Адаптация сервера тривиальна: на подключении — `pool.enqueue([fd] { handle_client(fd); });`.

### 4.3. Возврат результатов: `packaged_task` / `future`

Голый пул выполняет `void()`-задачи и ничего не возвращает. Чтобы получать результат, задачу оборачивают в `std::packaged_task`, а вызывающий держит `std::future`:

```cpp
template <typename F>
auto submit(thread_pool& pool, F f) -> std::future<decltype(f())> {
    auto task = std::make_shared<std::packaged_task<decltype(f())()>>(std::move(f));
    std::future<decltype(f())> fut = task->get_future();
    pool.enqueue([task] { (*task)(); });
    return fut;
}
```

Полноценная работа с `future`/`promise`, continuations и проблема «callback hell» — отдельная тема; здесь это лишь точка соприкосновения.

## 5. Пределы и развитие конструкции

### 5.1. Единый мьютекс очереди — точка сериализации

Один `mutex` на всю очередь означает, что при высоком темпе постановки/выборки задач все воркеры конкурируют за него, и лок становится бутылочным горлышком: рост числа ядер перестаёт давать ускорение. Направления развития:
- **MPMC-очереди** (multi-producer multi-consumer) с тонкой блокировкой или **lock-free** (отдельная тема про стек Трайбера и очередь Майкла–Скотта);
- **воровство работы (work stealing):** у каждого воркера своя дека задач, простаивающий ворует из чужой — так устроены планировщики TBB, Cilk, Go и Tokio. Contention на общей очереди практически исчезает.

### 5.2. False sharing на горячих полях

Счётчики и узлы очереди, лежащие в одной **кэш-линии (cache line, ~64 байта)**, при записи с разных ядер вызывают **ложное разделение (false sharing)** и cache ping-pong: ядра постоянно инвалидируют друг другу кэш. Лечится выравниванием горячих полей на отдельные линии:

```cpp
struct alignas(std::hardware_destructive_interference_size) padded_counter {
    std::atomic<long long> value{0};
};
```

Механика когерентности кэшей (протокол MESI) — отдельная тема; здесь достаточно знать симптом и приём.

### 5.3. Потолок блокирующего пула и мостик к асинхронности

Главное концептуальное ограничение: если каждая задача `handle_client` **блокируется** на `read`/`write`, то пул из `N` воркеров обслуживает не более `N` клиентов одновременно — мы заново ввели потолок параллелизма, только меньшего размера. Увеличивать `N` до тысяч бессмысленно (вернёмся к C10k). Правильный выход — не блокировать воркеров на вводе-выводе: перевести сокеты в неблокирующий режим и обслуживать тысячи соединений малым числом потоков через мультиплексирование (`epoll`) или асинхронные операции (`io_uring`). Пул потоков и событийный цикл затем объединяют: воркеры заняты только готовой к исполнению работой, а ожиданием занимается ядро

Этот же пул становится фундаментом следующего шага — **файберов**. В декомпозиции «файбер = корутина + пул потоков» (см. файл про планировщик файберов) пул остаётся прежним и по-прежнему знает только про **задачи**, но теперь среди них — **служебные задачи файберов**: каждая делает `coroutine.resume()`, а сам файбер представлен **цепочкой** таких задач (после `yield`/ожидания планируется следующая `resume`-задача). Минимальный API пула (`submit` с гарантией «задача однажды выполнится») для этого достаточен — это и есть та ортогональность, ради которой пул держат «глупым».

### 5.4. Размер пула

Эвристики: для **CPU-bound** задач разумно число воркеров ≈ числу аппаратных потоков (`std::thread::hardware_concurrency()`) — больше лишь добавит переключений контекста. Для **IO-bound** задач (как блокирующий `handle_client`) воркеров берут больше, потому что они в основном спят на вводе-выводе; но это, как показано выше, паллиатив по сравнению с переходом на неблокирующую модель.

## 6. Резюме темы

- Condition variable даёт «уснуть до уведомления»; всегда: мьютекс + предикат + цикл `while` (защита от lost и spurious wakeup).
- Предикат меняем под мьютексом; `notify` можно вынести за критическую секцию.
- `std::counting_semaphore` — стандартный, лёгкий (на атомике/futex), `release` допускается из другого потока; `binary_semaphore = counting_semaphore<1>`.
- Пул потоков = блокирующая очередь + воркеры + корректное завершение (`close` + `notify_all` + `join`) + exception-safety.
- Пул — это рантайм («ОС для программы»), реализующий **M:N**: много единиц конкуренции на немного потоков. Его API намеренно минимален (один `submit`, negative space): результат/ошибку/ожидание дают ортогональные инструменты (WaitGroup, future). Гигиена: в задаче пула **нельзя блокироваться**. Очередь — инструмент коммуникации (MPMC, unbounded), backpressure ставится выше по стеку семафором.
- Единый мьютекс очереди и блокирующий ввод-вывод — два потолка масштабируемости; их снимают work stealing / lock-free и переход к `epoll`/`io_uring`.
