# Lock-free структуры данных

## 1. От разделяемого состояния к неблокирующим алгоритмам

Прежде чем строить неблокирующие структуры, полезно увидеть, **зачем** вообще нужна синхронизация и почему мьютекс — не единственный (и не всегда лучший) ответ. Начнём с самого частого носителя ошибок — разделяемого изменяемого состояния, а затем перейдём к гарантиям прогресса.

### 1.1. Разделяемое состояние и поломки связного списка

Разделяемое состояние повсюду, даже если вы его явно не заводили. Простейший пример — **аллокатор**: `new`/`malloc` внутри ведут список свободных блоков (**free-list**), общий для всех потоков; этот же приём вернётся у нас в §5.2 как пул узлов. Рантайм языка, кэши, счётчики — всё это разделяемое состояние.

Возьмём каноничный носитель: односвязный список с операциями `push` (вставка в голову) и `pop` (снятие с головы) — по сути это и есть стек, который ниже мы сделаем lock-free.

```cpp
struct Node { int value; Node* next; };
Node* head = nullptr;                       // разделяемая голова

void push(int v) {                          // вставка в голову
    Node* n = new Node{v, head};
    head = n;
}
Node* pop() {                               // снятие с головы
    Node* old = head;
    if (!old) return nullptr;
    head = old->next;
    return old;                             // вызывающий потом сделает delete
}
```

Однопоточно всё верно. Но если два потока зайдут в `pop` **одновременно**, возникает целый букет поломок (сценарий: оба видят `head == A`, `A->next == B`):

- **Потерянное обновление:** оба ставят `head = B`, но **оба** возвращают `A` — один узел «снят дважды», нарушен инвариант структуры. Это **race condition** (нарушение *вашего* инварианта; различение race condition / data race — в файле про многопоточный сервер).
- **Use-after-free:** один поток сделал `delete A`, другой в этот момент читает `A->next` — обращение к освобождённой памяти.
- **Double-free:** оба дошли до `delete old` с `old == A` — `A` освобождается дважды, разрушая структуры самого аллокатора.

Эти баги **недетерминированы** — проявляются раз в миллионы запусков, в зависимости от тайминга планировщика, и потому особенно коварны. Их ловит **AddressSanitizer (ASan)**, сообщая `heap-use-after-free` / `double-free`. Тонкий, но важный момент: ASan — инструмент про **память**, а вскрывает он ошибку **синхронизации**. Управление памятью и синхронизация — связанные задачи: безопасно освободить узел нельзя, не зная, что на него больше никто не ссылается. Та же связка видна в инварианте заимствования Rust (одна изменяемая ссылка либо много неизменяемых), который одновременно служит и памяти, и синхронизации.

Напрашивающийся ответ — обернуть список одним мьютексом. Это корректно, но один глобальный замок сериализует всю структуру и **убивает масштабируемость** (см. гранулярность блокировки в файле про многопоточный сервер). Желая и корректности, и масштабирования, приходим к **неблокирующим** структурам — где, как мы увидим, те же `use-after-free`, `double-free` и новая беда **ABA** возвращаются и требуют явного решения (рекультивация памяти, §5).

### 1.2. Мьютекс и его изъяны

Мьютекс — традиционный способ синхронизации, но у него есть фундаментальные изъяны: инверсия приоритетов (priority inversion), риск взаимоблокировок (deadlock) и — главное — **остановка прогресса всей системы при зависании владельца блокировки**. Если поток, захвативший мьютекс, завис навсегда (вытеснен, упал, бесконечно планируется), все ожидающие останавливаются тоже. В высоконадёжных системах нужна устойчивость к **асинхронным сбоям** — этого мьютекс не даёт.

Альтернатива — **неблокирующие (non-blocking)** алгоритмы на атомарном CAS (compare-and-swap).

**Неблокирующая синхронизация = отказоустойчивость.** Полезно смотреть на это через распределённые системы. Гарантии безопасности (mutual exclusion) держатся при **любом** планировщике, но гарантии прогресса мьютекса опираются на его **честность**: если владельца блокировки вытеснили в критической секции, система стоит, пока планировщик честно не вернёт его на ядро. Неблокирующая синхронизация **снимает** это предположение: мы требуем прогресса, даже если произвольный поток поставлен на паузу на **сколь угодно долгое, в пределе бесконечное, время** (вытеснение, page fault, промах кэша). Пауза потока — это «отказ узла» в распределённой системе; научившись переживать бесконечную паузу, мы переживём и любую конечную. Практическая мотивация — **масштабируемость** на многих ядрах: операции над общей структурой не должны зависеть от пауз операций в других потоках.

### 1.3. Гарантии прогресса

Пусть несколько потоков (или узлов) работают над общей структурой данных.

- **Lock-free (свобода от блокировок):** **хотя бы один** поток завершит свою операцию за конечное число шагов, **даже если любой другой остановлен навсегда**. Бесконечная остановка одного потока не останавливает систему.
- **Wait-free (свобода от ожидания):** **каждый** поток завершит свою операцию за ограниченное число шагов — строго сильнее lock-free.
- Существуют и более слабые классы (obstruction-free и т. д.); фокус — на lock-free.

**Практическая оговорка.** Большинство «lock-free» структур **не** wait-free: гарантия даётся системе в целом, а отдельный поток может буксовать на повторах CAS произвольно долго. Wait-free обычно требует механизма **helping (помощи)** и announcement-массивов, где потоки публикуют свои операции, чтобы другие могли их завершить (схема Когана–Петранка); это заметно дороже.

**Herlihy: универсальная конструкция и иерархия консенсуса.** Морис Херлихи (статья начала 1990-х, давшая само понятие wait-free) показал две вещи. Во-первых, существует **универсальная конструкция (universal construction):** имея достаточно сильную атомарную операцию, **любой** объект можно сделать wait-free — но на практике так не делают, реализация выходит слишком громоздкой и медленной. Во-вторых, атомарные операции можно сравнивать по **выразительности** (число консенсуса, consensus number): он перенёс распределённую задачу отказоустойчивого консенсуса на shared memory и выяснил, какие примитивы мощнее. Вывод для нас: `CAS` универсален (на нём строится что угодно), а гнаться за честной wait-free-реализацией обычно не нужно — на разумном планировщике **lock-free практически неотличим от wait-free**.

**Lock-free ≠ отсутствие спинлоков и ≠ «быстрее».** Lock-free **исключает** мьютексы и спинлоки, но обратное неверно: код без спинлока не обязан быть lock-free (это про **гарантию прогресса**, а не про наличие/отсутствие конкретной конструкции). И lock-free не выбирают потому, что «быстрее блокировок» — как `test-and-set` против `ticket lock`, выбор делается по нужному **свойству** (здесь — гарантии прогресса/масштабируемости), а сама lock-free-реализация бывает и медленнее.

**Плата за отсутствие критических секций — обозреваемость промежуточных состояний.** Под мьютексом сложную операцию (переставить несколько указателей) выполняют для других потоков **атомарно**: они не видят промежуточных состояний. Без критической секции другой поток наблюдает **все** промежуточные состояния структуры и обязан с ними корректно работать — отсюда вся сложность lock-free (и, как показано ниже, главная её часть — управление памятью).

### 1.4. Терминологическая заметка

`lock-free` иногда смешивают с `non-blocking`. Здесь следуем классическому определению: lock-free — системный прогресс при произвольных задержках/остановках потоков.

## 2. Атомарный фундамент: `compare_exchange`

CAS — основа lock-free. `compare_exchange` атомарно сверяет значение с `expected` и при равенстве пишет `desired`, иначе обновляет `expected` текущим значением.

Различие `weak`/`strong` и аппаратная подоплёка (x86 `CMPXCHG`; ARM LL/SC: `LDREX`/`STREX`, ложные срывы `weak`) подробно разобраны в файле про спинлок и атомики; здесь — кратко: `weak` может дать ложный отказ и потому применяется **в циклах**, `strong` — для одиночной попытки.

```cpp
void increment(std::atomic<int>& a) {
    int x = a.load(std::memory_order_relaxed);
    while (!a.compare_exchange_weak(x, x + 1,
               std::memory_order_release, std::memory_order_relaxed)) {
        // x автоматически обновляется текущим значением a — повторяем
    }
}
```

Это lock-free: завис один поток в цикле — другие продолжают менять `a`, и кто-то сделает прогресс.

**CAS-loop — канонический шаблон lock-free.** Почти любой вводный lock-free-алгоритм устроен одинаково, в три шага: (1) **снапшот** — атомарно прочитать текущее состояние структуры; (2) **локальная модификация** — построить новое состояние по снапшоту (этот шаг не виден другим потокам); (3) **commit** — попытаться зафиксировать изменение через CAS, **только если** с момента снапшота состояние не менялось. Провал CAS означает, что другой поток успел закоммитить своё изменение (то есть достиг прогресса) — повторяем с шага 1. Здесь снапшот тривиален (значение одной ячейки); в стеке/очереди ниже это будет указатель на вершину/хвост, но скелет тот же.

## 3. Lock-free стек (стек Трайбера)

Стек Трайбера (Treiber, 1986) — односвязный список, голова которого обновляется через CAS.

```cpp
template <typename T>
struct Node { T value; Node* next; };

template <typename T>
class TreiberStack {
    std::atomic<Node<T>*> head{nullptr};
public:
    void push(T value) {
        Node<T>* new_node = new Node<T>{std::move(value), nullptr};
        Node<T>* old_head = head.load(std::memory_order_acquire);
        do {
            new_node->next = old_head;            // CAS обновит old_head при неудаче → перечитываем next
        } while (!head.compare_exchange_weak(old_head, new_node,
                     std::memory_order_release, std::memory_order_acquire));
    }

    std::optional<T> pop() {                       // наивная версия — см. проблемы ниже
        Node<T>* old_head = head.load(std::memory_order_acquire);
        while (old_head && !head.compare_exchange_weak(old_head, old_head->next,
                   std::memory_order_release, std::memory_order_acquire))
            ;
        if (!old_head) return std::nullopt;
        T result = std::move(old_head->value);
        delete old_head;                           // ОПАСНО: другой поток мог ещё держать old_head
        return result;
    }
};
```

`push` корректен и прост. У наивного `pop` сразу **две** беды, ведущие к остальным разделам: (1) он разыменовывает `old_head->next` — но между загрузкой и CAS другой поток мог `pop`-нуть и `delete`-нуть этот узел (use-after-free); (2) даже без падения возможна **ABA**.

## 4. Проблема ABA

### 4.1. Описание

1. Поток P1 читает `head = A` и вычисляет `A->next = B`.
2. P1 вытеснен.
3. Поток P2 снимает A (голова → B), затем снимает B (голова → C), затем добавляет новый узел **по тому же адресу A** (из пула освобождённых), причём теперь `A->next = C`.
4. P1 просыпается, делает CAS: видит `head == A` (значение совпало!) и ставит `head = B`. Но `B` уже не актуальная вершина — структура разрушена.

**Суть ABA:** указатель вернулся к прежнему значению, но смысл изменился; CAS, сравнивающий только значение, этого не замечает.

### 4.2. Методы решения

1. **Tagged pointers (указатель + счётчик/тег):** хранить пару (указатель, тег), каждое изменение головы инкрементирует тег. CAS — над двойным словом; ABA исключается, пока тег не переполнится.
2. **Hazard pointers (защитные указатели):** поток перед доступом помечает узел как используемый; освобождение откладывается, пока на узел кто-то ссылается.
3. **RCU (Read-Copy-Update):** безопасное удаление после того, как все читатели вышли из своих критических секций.
4. **Бессчётное переиспользование без возврата адресов** (пул фиксированного размера с индексами вместо указателей) — адреса не переиспользуются «чужими», ABA не возникает.

### 4.3. Tagged pointer на практике

```cpp
struct TaggedPtr { Node* ptr; uint64_t tag; };
std::atomic<TaggedPtr> head;

void push(T value) {
    TaggedPtr old_head = head.load();
    Node* new_node = new Node{...};
    TaggedPtr desired;
    do {
        new_node->next = old_head.ptr;
        desired = {new_node, old_head.tag + 1};
    } while (!head.compare_exchange_weak(old_head, desired));
}
```

На 64-битной архитектуре часто упаковывают всё в **одно** 64-битное слово: 48 бит указателя (реально используемая ширина виртуального адреса) + 16 бит тега, через битовые сдвиги — тогда CAS обычный, 8-байтный.

### 4.4. Двойное-широкое CAS (DCAS) и `cmpxchg16b`

Если упаковать в 64 бита нельзя (нужны полный указатель + полноценный тег), требуется **128-битный CAS**. На x86-64 это инструкция **`cmpxchg16b`**. Важная практическая деталь: GCC/Clang эмитят её инлайном только с флагом **`-mcx16`**; без него 16-байтные `std::atomic` операции маршрутизируются через libatomic, которая может использовать **замок** — тогда `is_lock_free()` вернёт `false`, и «lock-free» структура на деле блокирующая. Всегда проверяйте `obj.is_lock_free()`.

DCAS — частный случай более общего желания работать атомарно **сразу с несколькими ячейками**. В эту же сторону смотрят **транзакционная память** (идея Херлихи: протокол когерентности кэшей уже умеет детектировать конфликты записей, а значит, годится как механизм транзакций — начатую «транзакцию» в кэше инвалидация чужой записи прерывает) и **аппаратная транзакционная память (HTM)**, например Intel **TSX**. На практике HTM не взлетела (ранние реализации содержали ошибки и были отозваны/работали плохо), да и ассоциативность кэша ограничивает размер транзакции; есть также программные multi-word-CAS. Кроссплатформенно надёжен лишь одиночный CAS, поэтому обычно «выкручиваются» им (см. ниже).

### 4.5. LL/SC естественно иммунен к ABA

Полезный контраст: на архитектурах с LL/SC (ARM, POWER) store-conditional срывается при **любой** записи в зарезервированную линию между `LDREX` и `STREX` — даже если значение в итоге то же (A→B→A). Поэтому LL/SC **не страдает ABA** по построению, в отличие от CAS, сравнивающего лишь итоговое значение. Оговорки: реальный LL/SC даёт ложные срывы, а гранула резервирования (reservation granule) может быть шире самой переменной, провоцируя лишние повторы.

## 5. Управление памятью в lock-free структурах

### 5.1. Почему `new`/`delete` мешают

- Стандартный `operator new` (ptmalloc в glibc) внутри берёт мьютексы — его вызов нарушает lock-free.
- `delete` в `pop` опасен: другой поток мог сохранить указатель на узел до его удаления → use-after-free. Это и есть фундаментальная **проблема рекультивации (reclamation)**: когда физически безопасно освободить узел, логически снятый из структуры.

### 5.2. Free-list (ограниченный пул)

Заранее выделенный пул узлов; узлы не возвращаются ОС, а переиспользуются. Выделение/освобождение — lock-free операции над стеком свободных узлов.

```cpp
class NodePool {
    std::atomic<Node*> free_head;
public:
    Node* acquire() {
        Node* old = free_head.load();
        while (old && !free_head.compare_exchange_weak(old, old->next)) ;
        return old ? old : new Node;      // расширение пула — однократно не lock-free, допустимо как резерв
    }
    void release(Node* node) {
        Node* old = free_head.load();
        do { node->next = old; } while (!free_head.compare_exchange_weak(old, node));
    }
};
```

> **Важная оговорка (исправление).** Сам этот пул — стек Трайбера, и потому **тоже подвержен ABA**: между загрузкой `old = free_head` и CAS другой поток может снять `old`, вернуть его обратно, и `old->next` будет уже не тем. Если решать проблему рекультивации пулом, его `acquire`/`release` нужно защищать тем же приёмом, что и основную структуру: **tagged pointer** на `free_head` (указатель + счётчик в одном двойном слове, §4.3–4.4) либо DCAS. Иначе мы заменили одну гонку (use-after-free в `pop`) на другую (ABA в пуле). На практике поэтому пул узлов либо строят на tagged-pointer-стеке, либо делают per-thread (тогда у `free_head` один владелец и гонок нет вовсе), а общий пул используют лишь как редкий резерв.

### 5.3. Hazard pointers, EBR/QSBR и стандартизация

- **Hazard pointers** — каждый поток публикует указатели, которые сейчас читает; узел освобождается, только когда его нет ни в одном hazard-слоте. Накладные расходы на публикацию, но верхняя граница памяти не фиксируется.
- **Epoch-based reclamation (EBR) / QSBR** — узлы складываются в «отложенные» по эпохам и освобождаются, когда все потоки прошли quiescent-точку; дешевле hazard pointers, но «застрявший» поток задерживает освобождение.
- Эти схемы **движутся в стандарт** (hazard pointers и RCU, ориентир — C++26: `std::hazard_pointer`, RCU-домены). До тех пор — Boost, libcds, folly.

### 5.4. `std::atomic_shared_ptr`

`shared_ptr` сам по себе уже даёт безопасную рекультивацию через счётчик ссылок — соблазнительно строить lock-free структуры на нём. Но возникает тонкость с **атомарностью операций над самим указателем**.

**Отличие от обычного `shared_ptr`.** У обычного `shared_ptr` атомарен только **счётчик в control block** — поэтому копировать *разные экземпляры*, ссылающиеся на один объект, из разных потоков безопасно. А вот одновременный доступ к **одному и тому же экземпляру**, где хотя бы один поток пишет (`reset`, присваивание), — это **data race** и UB. `std::atomic<std::shared_ptr<T>>` (C++20; ранее — свободные `std::atomic_load/store(shared_ptr*)`, ныне deprecated) делает атомарными `load`/`store`/`exchange`/`compare_exchange` над самим экземпляром.

**Идея реализации.** Трудность в том, что `shared_ptr` — это **два слова** (указатель на объект + указатель на control block), а атомарная загрузка обязана за один неделимый шаг *и* прочитать указатель на control block, *и* инкрементировать его счётчик — но это **две разные ячейки памяти**. Подходы:
- **Внешний замок** — пул спинлоков, индексируемый по адресу атомика. Так делают libstdc++ и libc++, поэтому у них `std::atomic<shared_ptr>::is_lock_free()` обычно `false`.
- **Split reference counting (разделённый счётчик)** — рядом с указателем в **одном двойном слове** держат «внешний» счётчик незавершённых загрузок; загрузка атомарно (DCAS) забирает указатель и инкрементирует внешний счётчик, а при разрушении локальной копии внешний счётчик «сливается» во внутренний счётчик control block. Это и есть путь к lock-free.

**Можно ли сделать lock-free?** Да. Lock-free `atomic_shared_ptr` реализуем через split counting + `cmpxchg16b` (реализации: `folly::atomic_shared_ptr`, версия Энтони Уильямса в just::thread). Стандарт **разрешает**, но **не требует** lock-free; mainstream-реализации пока берут замок. Связь с темой рекультивации прямая: `atomic_shared_ptr` — это, по сути, рекультивация на счётчиках ссылок, которой можно безопасно освобождать узлы lock-free структур, не вводя hazard pointers, — ценой трафика атомарных счётчиков (тот самый contention, от которого lock-free как раз и страдает под нагрузкой).

## 6. Lock-free очередь (очередь Майкла–Скотта)

Очередь Майкла–Скотта (Michael & Scott, 1996) — классический lock-free FIFO. Два указателя: `head` (откуда снимаем) и `tail` (куда добавляем). Всегда есть **фиктивный узел (dummy node)**, чтобы пустая очередь не была особым случаем.

```cpp
template <typename T>
struct MSQueue {
    struct Node { std::optional<T> value; std::atomic<Node*> next; };
    std::atomic<Node*> head;
    std::atomic<Node*> tail;
    MSQueue() {
        Node* dummy = new Node{std::nullopt, nullptr};
        head.store(dummy); tail.store(dummy);
    }
};
```

**`push`:**
1. Создать `new_node` со значением и `next = nullptr`.
2. В цикле: загрузить `tail` и `tail->next`. Если `tail->next != nullptr` — `tail` отстаёт: **помочь** (help) продвинуть его (CAS) и повторить. Если `tail->next == nullptr` — попытаться `tail->next.compare_exchange(nullptr, new_node)`; успех → выйти, иначе повтор.
3. Попытаться сдвинуть `tail` на `new_node` (CAS). Даже при неудаче операция завершена — узел уже в очереди.

**`pop`:**
1. Загрузить `head`, затем `head->next` (реальный первый элемент после фиктивного). Если `head->next == nullptr` — очередь пуста.
2. CAS сдвинуть `head` на `head->next`; неудача — повтор.
3. Успех — забрать значение из нового `head` (фиктивный данных не несёт), старый `head` освободить **с учётом рекультивации** (§5).

```cpp
void push(T value) {
    Node* node = new Node{std::move(value), nullptr};
    while (true) {
        Node* t    = tail.load(std::memory_order_acquire);
        Node* next = t->next.load(std::memory_order_acquire);
        if (t != tail.load(std::memory_order_acquire)) continue;   // снимок устарел — перечитать
        if (next == nullptr) {                                     // t — действительно последний
            if (t->next.compare_exchange_weak(next, node,
                    std::memory_order_release, std::memory_order_relaxed)) {
                tail.compare_exchange_strong(t, node, std::memory_order_release); // продвинуть tail (не критично)
                return;
            }
        } else {                                                   // tail отстаёт
            tail.compare_exchange_strong(t, next, std::memory_order_release);     // помочь и повторить
        }
    }
}

std::optional<T> pop() {
    while (true) {
        Node* h    = head.load(std::memory_order_acquire);
        Node* t    = tail.load(std::memory_order_acquire);
        Node* next = h->next.load(std::memory_order_acquire);
        if (h != head.load(std::memory_order_acquire)) continue;   // снимок устарел
        if (h == t) {                                              // голова == хвост
            if (next == nullptr) return std::nullopt;              // очередь пуста
            tail.compare_exchange_strong(t, next, std::memory_order_release);     // tail отстаёт — помочь
        } else {
            T value = std::move(*next->value);                     // данные лежат в next (после dummy)
            if (head.compare_exchange_weak(h, next,
                    std::memory_order_release, std::memory_order_relaxed)) {
                retire(h);                                         // старый dummy — на рекультивацию (§5)
                return value;
            }
        }
    }
}
```

Тонкость порядка в `pop`: значение читают из `next` **до** успешного CAS `head`, иначе другой поток мог бы снять и удалить узел между CAS и чтением. И `value` забирают из `next` (он становится новым фиктивным узлом), а освобождают **старый** `head`.

**Helping и отставание `tail`.** Любой поток, заметив `tail->next != nullptr`, сам двигает `tail`. Это и обеспечивает lock-free: даже если добавивший узел поток застыл между записью `next` и обновлением `tail`, другие «помогут» завершить операцию.

### 6.1. False sharing на `head` и `tail`

Производители долбят `tail`, потребители — `head`. Если эти атомики лежат в одной **кэш-линии (cache line, ~64 байта)**, возникает cache ping-pong: запись одного ядра инвалидирует линию у других. Лечится разнесением по разным линиям (мостик к теме про когерентность кэшей):

```cpp
struct alignas(std::hardware_destructive_interference_size) PadHead { std::atomic<Node*> head; };
struct alignas(std::hardware_destructive_interference_size) PadTail { std::atomic<Node*> tail; };
```

## 7. Memory ordering и производительность

В примерах для простоты подразумевается `seq_cst`. В производительных реализациях:
- `memory_order_acquire` — на загрузках, от которых зависят последующие операции (чтение `head`/`tail`);
- `memory_order_release` — на завершающих записях (успешный CAS в `push`);
- `memory_order_relaxed` — для счётчиков и операций, ничего не синхронизирующих.

Неверный порядок ведёт к инверсии видимости (читатель видит новый `head`, но не обновлённый `head->next`). Полный разбор `memory_order`, happens-before и барьеров — в теме про модель памяти.

**«Lock-free ≠ быстро».** Под высокой конкуренцией lock-free может **уступать** хорошему мьютексу: повторы CAS и трафик когерентности съедают выигрыш. Ценность lock-free — гарантия прогресса и устойчивость **хвостовой задержки (tail latency)**, а не пиковая пропускная способность. Под нагрузкой помогает **экспоненциальный backoff** на неудаче CAS.

## 8. Практические замечания

- `std::atomic<T>` для типов шире 64 бит может использовать внутренний замок — проверяйте `is_lock_free()`; для пары (указатель+тег) либо упаковка в 64 бита, либо `std::atomic<__int128>` с `-mcx16` (§4.4).
- **Boost.Lockfree** даёт готовые Treiber stack (фиксированного размера) и Michael–Scott queue; **Intel TBB**, **libcds**, **folly** — более широкий набор с hazard pointers/EBR.
- Динамическое расширение пула нарушает lock-free, но в системах мягкого реального времени часто допустимо с оговорками.

## 9. Заключение

Lock-free алгоритмы устойчивы к неограниченным задержкам отдельных потоков; строятся на CAS и требуют решения ABA и рекультивации памяти. Сложность растёт для структур с несколькими указателями (очередь), где нужно помогать незавершённым операциям. `std::atomic_shared_ptr` даёт рекультивацию на счётчиках ссылок и может быть lock-free через split counting + DCAS. Для промышленного применения опираются на проверенные библиотеки (Boost, TBB, folly), а не на собственные реализации — если нет глубокого понимания архитектуры и модели памяти C++. Даже простой стек Трайбера может превосходить блокирующие аналоги по масштабируемости, особенно на NUMA, — но именно по устойчивости задержки, а не всегда по средней пропускной способности.
