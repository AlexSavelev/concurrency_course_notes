# Futures, Promise, Executors и асинхронная композиция

## 1. Где мы и зачем

Эволюция нашего сервера проверки простоты чисел:

1. **Thread pool + блокирующий I/O.** Пропускная способность ограничена числом воркеров: клиентов больше потоков — часть ждёт; воркеры залипают на медленном `read`/`write` (см. файл про IO multiplexing).
2. **Однопоточный epoll** снимает ограничение на число соединений (предел — лимит дескрипторов), поток не блокируется на I/O.

```cpp
while (true) {
    int n = epoll_wait(epfd, events, MAX_EVENTS, -1);
    for (int i = 0; i < n; ++i)
        events[i].data.fd == server_socket ? accept_client() : handle_client(events[i].data.fd);
}
```

Но у однопоточного epoll своя беда — следующий раздел.

## 2. Проблема CPU-heavy задач в однопоточной модели

Если обработчик делает **CPU-bound** работу (проверка очень большого числа, сжатие), единственный поток на это время занят, и **все** остальные клиенты ждут — задержка (latency) для всех растёт.

- Приходит тяжёлый запрос → поток считает несколько секунд.
- Лёгкие запросы других клиентов не начинают обрабатываться до конца тяжёлого.

В многопоточной блокирующей модели при достатке потоков лёгкие запросы шли бы параллельно с тяжёлым; в однопоточной — нет.

**Вывод:** надо совместить достоинства обоих подходов — неблокирующий I/O (epoll) для масштабирования по соединениям **плюс** вынос CPU-heavy работы в пул потоков, чтобы I/O-поток не блокировался.

## 3. epoll в многопоточной среде: ET vs LT

Режимы edge-triggered (ET) и level-triggered (LT), их семантика, многопоточные схемы (шардинг по `SO_REUSEPORT`, `EPOLLEXCLUSIVE`, безопасная передача fd через `EPOLLONESHOT`) подробно разобраны в файле про IO multiplexing — здесь не дублируем. Важное уточнение, которое там же исправлено: пробуждение **ровно одного** потока на общем epoll-инстансе гарантирует не `EPOLLET` сам по себе, а флаг `EPOLLEXCLUSIVE`; для эксклюзивной передачи дескриптора воркеру используется `EPOLLONESHOT`. В ET читать/писать нужно циклом до `EAGAIN`:

```cpp
void handle_read(int fd) {
    char buf[4096]; ssize_t n;
    while ((n = read(fd, buf, sizeof(buf))) > 0) process_data(buf, n);
    if (n == -1 && errno != EAGAIN) { /* ошибка */ }
}
```

Альтернатива общему epoll — несколько инстансов (sharding), по одному на поток, каждый дескриптор привязан к ровно одному инстансу; конкуренции нет, поэтому там обычно используют LT.

## 4. Гибридная архитектура: I/O-поток + thread pool для CPU-heavy

Идея: I/O-поток регистрирует клиентов в epoll и читает данные; получив полную строку с числом, он **не считает сам**, а **делегирует** вычисление в пул потоков. Результат потом надо отправить клиенту — но отправка тоже должна быть асинхронной (медленный клиент не должен блокировать I/O-поток на `write`). Значит, нужен механизм уведомить I/O-поток о готовности результата и отложенно записать ответ через `EPOLLOUT`.

**Наивная версия с опросом (polling) не работает.** Если хранить `std::future` от вычислений и каждую итерацию проверять их готовность в `check_pending()`, возникает тупик: когда новых событий нет (все клиенты прислали данные и ждут ответов, новых подключений нет), `epoll_wait` спит, `check_pending()` не вызывается — а результаты, возможно, уже готовы. Вечная блокировка.

**Решение — асинхронное уведомление через `eventfd`.** `eventfd` — специальный дескриптор-счётчик, который можно добавить в epoll. Пул потоков по завершении вычисления **пишет** в `eventfd` (инкремент счётчика), это будит I/O-поток в `epoll_wait`; проснувшись, I/O-поток разбирает готовые результаты и инициирует запись. Так опрос заменяется событием.

## 5. Future и Promise

- **Future** — представление результата, который станет доступен в будущем: можно проверить готовность, синхронно дождаться (`wait`), забрать значение (`get`).
- **Promise** — «продюсер»: устанавливает значение (`set_value`) или исключение (`set_exception`) в общее состояние (shared state). Пара создаётся как `promise.get_future()`.

Это **one-shot**: значение передаётся ровно один раз на пару.

### 5.1. Применение для асинхронного выполнения

Future/Promise развязывают «кто запускает работу» и «кто ждёт результат». Задача кладётся в пул, вызывающему сразу отдаётся future; продюсер (воркер) по завершении делает `set_value`. Это разобрано в файле про пул потоков (обёртка через `std::packaged_task`): `packaged_task` упаковывает вызываемый объект, его `get_future()` отдаёт future, а вызов `(*task)()` исполняет и наполняет shared state.

## 6. Реализация `std::future`/`std::promise` и их неудобства

**Устройство (упрощённо).** Future и promise делят **shared state** — объект в куче, содержащий:
- `std::mutex` для синхронизации;
- `std::condition_variable` для блокировки ожидающих;
- `std::variant<std::monostate, T, std::exception_ptr>` (значение или исключение) + флаг готовности.

`get()` под мьютексом ждёт на condition variable, пока не выставлен флаг готовности, затем возвращает значение или перебрасывает исключение. `wait_for(0)` просто проверяет флаг.

**Неудобства `std::future`:**
- Только **блокирующие** `wait`/`get`. Нельзя «подписаться» на готовность, чтобы выполнить код без блокировки потока.
- Требует **динамической аллокации** shared state.
- Нет удобной **композиции**: ни `then` (continuation), ни комбинаторов.
- Нельзя задать, **в каком потоке** выполнять продолжение.
- **Деструктор future от `std::async` блокирует** (launch::async). Это известная ловушка: временный объект `std::async(f);` без присваивания исполняется фактически синхронно, потому что его деструктор ждёт завершения задачи. Аналогично цепочка `std::async(...).get()` не даёт параллелизма, если future немедленно разрушается.
- Один результат — один потребитель. Нескольким ждущим нужен **`std::shared_future`** (его можно копировать, и `get()` зовут многократно из разных потоков).

**Чего хочется:** `future.Subscribe(callback)` — callback выполнится, когда результат будет готов. Это открывает путь к асинхронным цепочкам без блокировки.

## 7. Continuation (`Subscribe`) и её реализация

**Желаемый интерфейс:**
```cpp
template <typename T>
class MyFuture {
public:
    void Subscribe(std::function<void(T)> callback);
};
```

**Состояния общего состояния:**
- `Empty` — ни результата, ни callback;
- `OnlyResult` — результат пришёл, callback ещё не установлен;
- `OnlyCallback` — callback установлен, результат ещё не пришёл;
- `Done` — callback вызван.

**Суть реализации — атомарная гонка `Subscribe` против `set_value`.** Оба пытаются перевести состояние из `Empty` в «своё»; кто первым сделал CAS — кладёт свою часть и уходит, проигравший видит чужой тег и **сам исполняет callback**. Это снимает гонку «результат пришёл ровно в момент подписки».

```cpp
enum Tag { EMPTY, ONLY_RESULT, ONLY_CALLBACK, DONE };

template <typename T>
struct SharedState {
    std::atomic<int> tag{EMPTY};
    std::optional<T> result;                 // пишется до CAS, читается после
    std::function<void(T)> callback;         // пишется до CAS, читается после
};

template <typename T>
class MyFuture {
    std::shared_ptr<SharedState<T>> s;
public:
    void Subscribe(std::function<void(T)> cb) {
        s->callback = std::move(cb);
        int expected = EMPTY;
        if (s->tag.compare_exchange_strong(expected, ONLY_CALLBACK))
            return;                          // результата ещё нет — его поставит продюсер
        // expected == ONLY_RESULT: результат уже есть — исполняем callback сами
        s->callback(std::move(*s->result));
        s->tag.store(DONE);
    }
};

template <typename T>
class MyPromise {
    std::shared_ptr<SharedState<T>> s;
public:
    void set_value(T v) {
        s->result = std::move(v);
        int expected = EMPTY;
        if (s->tag.compare_exchange_strong(expected, ONLY_RESULT))
            return;                          // callback ещё не подписан — его исполнит Subscribe
        // expected == ONLY_CALLBACK: callback уже есть — исполняем его сами
        s->callback(std::move(*s->result));
        s->tag.store(DONE);
    }
};
```

Тонкость памяти: запись `result`/`callback` должна быть видна до смены тега — на практике CAS делают с `release`, а чтение проигравшей стороны — с `acquire` (здесь для ясности оставлен `seq_cst`). Кто именно исполняет callback (поток подписчика или поток продюсера) — недетерминированно; это и мотивирует executors (§10).

## 8. Callback hell и комбинаторы (chaining)

Только с `Subscribe` последовательность асинхронных шагов A → B → C превращается во вложенные колбэки — **callback hell**:

```cpp
FooAsync(input).Subscribe([=](Output o) {
    AsyncA(o).Subscribe([=](OutputA a) {
        AsyncB(a).Subscribe([=](OutputB b) {
            AsyncC(b).Subscribe([=](OutputC c) { /* ... */ });
        });
    });
});
```

Лечится **комбинаторами (combinators)**:
- **`thenValue` (sync)** — принимает `U(T)`, возвращает `Future<U>`.
- **`thenValue` (async)** — принимает `Future<U>(T)`, возвращает «развёрнутую» future (future-future flatten — склейка вложенных future в одну).
- **`thenError`** — обработка исключений (две аналогичные формы).

Код становится линейным:

```cpp
Future<OutputA> AsyncA(Output);
Future<OutputB> AsyncB(OutputA);
Future<OutputC> AsyncC(OutputB);

FooFuture(input)
    .thenValue(AsyncA)        // -> Future<OutputA>
    .thenValue(AsyncB)        // -> Future<OutputB>
    .thenValue(AsyncC)        // -> Future<OutputC>
    .thenValue([](OutputC c) { return process(c); });
```

**Реализация `thenValue`:** внутри создаётся новая `Promise`, и текущая future подписывается через `Subscribe`. При готовности исходной вызывается переданная функция, а её результат (значение или future) проталкивается в новую promise — ровно тот же механизм состояний, что в §7.

## 9. Комбинаторы для параллельной композиции

- **`CollectAll`** — принимает несколько future, возвращает future от кортежа результатов (или ошибок); ждёт завершения всех.
- **`CollectAny`** — первая завершившаяся (успех или ошибка).
- **`CollectAnyWithoutException`** — первая **успешная**.

`CollectAll` — для нескольких независимых асинхронных операций параллельно:

```cpp
auto f1 = Rpc1();   // RPC = Remote Procedure Call
auto f2 = Rpc2();
auto f3 = Rpc3();
auto [r1, r2, r3] = collectAll(f1, f2, f3).get();   // блокирует, пока все не готовы
```

## 10. Executors (экзекьюторы)

**Проблема (из §7):** мы не контролируем, **в каком потоке** исполнится callback. Если результат уже готов на момент `Subscribe`, callback выполнится в потоке подписчика (например, I/O-потоке); если позже — в потоке, вызвавшем `set_value` (воркере пула). Недетерминизм опасен: тяжёлый callback может «сесть» на I/O-поток, либо возникнут гонки данных.

**Решение — executor**: абстракция «**где и как** выполнить переданный код».

```cpp
struct IExecutor { virtual void Execute(Func f) = 0; };
```

**Типы:**
- **InlineExecutor** — немедленно в текущем потоке;
- **ThreadPoolExecutor** — задача в очередь пула;
- **SerializedExecutor (Strand)** — гарантирует последовательное исполнение задач (декоратор над другим executor'ом; снимает гонки без мьютексов);
- **ManualExecutor** — ручной прогон (тесты, детерминизм).

Future получает метод `via(executor)`: все последующие continuations исполняются на указанном executor'е. Это позволяет **изолировать** виды нагрузки (I/O и CPU):

```cpp
Future<Output> f = SomeRpc(input)
    .via(&cpuExecutor)                                   // CPU-heavy на пуле
    .thenValue([](auto v) { return heavyComputation(v); })
    .via(&ioExecutor)                                    // I/O на I/O-потоке
    .thenValue([](auto res) { writeResponse(res); });
```

## 11. Сборка гибрида на folly

- **CpuExecutor** — обёртка над thread pool, реализует `folly::Executor`.
- **IoExecutor** — кладёт задачи в очередь и будит I/O-поток через `eventfd`; метод `flush()` вызывается I/O-потоком по событию на `eventfd` и прогоняет накопленные задачи.

Алгоритм:
1. Серверный сокет и `eventfd` добавлены в epoll.
2. Получив строку с числом, строим цепочку:
   ```cpp
   folly::makeFuture(number)
       .via(&cpu_executor)
       .thenValue(is_prime)                              // CPU-heavy — на пуле
       .via(&io_executor)
       .thenValue([fd, this](bool prime) {
           enqueue_write(fd, prime ? "prime\n" : "not prime\n");
       });
   ```
3. `enqueue_write` кладёт данные в буфер записи сокета и добавляет интерес `EPOLLOUT`.
4. Когда сокет готов к записи, `handle_write` пишет сколько может; записав всё — снимает `EPOLLOUT`.
5. `IoExecutor::add` ставит задачу в очередь и пишет в `eventfd` → epoll просыпается → `flush()` прогоняет задачи в I/O-потоке.

**Что достигнуто:** I/O-поток не блокируется на `write` (асинхронно через `EPOLLOUT`); CPU-heavy работа — на пуле; результаты передаются через continuations без опроса; executors дают чёткий контроль над тем, где исполняется код.

## 12. Средства выразительности: futures, fibers, coroutines

- **Futures** — сильны в **параллельной композиции** (`collectAll`/`collectAny`), но последовательный код выглядит как функциональные цепочки `thenValue`.
- **Файберы (fibers) и stackless-корутины** позволяют писать асинхронный код в **синхронном стиле** (C++20):
  ```cpp
  co_await SomeRpc(input);
  auto a = co_await AsyncA(output);
  auto b = co_await AsyncB(a);
  ```
  Устройство корутин и `co_await` — отдельная тема.
- Модели **дополняют** друг друга: корутины — для последовательной логики, futures — для параллельных вызовов; executors управляют местом исполнения в обеих.

**Куда движется индустрия (forward-ссылка).** Современный стандартный путь — модель **senders/receivers** (`std::execution`, P2300): асинхронная операция описывается тремя каналами — **value / error / stopped (отмена)**, — а композиция (`then`, `when_all`, `let_value`) строится как ленивый граф, привязываемый к scheduler'у (тот же executor). Это даёт **структурированную конкурентность (structured concurrency)** и кооперативную **отмену** через `std::stop_token`/`std::stop_source` (C++20). Инфраструктура всё чаще строится на этой модели; futures — её частный, «нетерпеливый» (eager) случай.

## 13. Функциональный взгляд: future как значение, язык в языке

Всё выше — инженерная реализация. Но есть другой, более глубокий способ **думать** про futures, ради которого их и стоит изучать. Этот раздел — про модель мышления, а не про реализацию.

### 13.0. Concurrency ≡ Go?

Файберы, каналы, `select` (модель горутин Go) — естественная и доступная точка входа в concurrency, но это лишь **одно** решение задачи, не единственное и не обязательно лучшее. Concurrency — повод переосмыслить программирование для распределённого мира; futures предлагают принципиально иной угол зрения. Дальше мы намеренно «переворачиваем» взгляд.

### 13.1. Минимальный контракт и зачем выносить блокировку

Автомат из четырёх состояний (§7) — это не просто реализация, а **минимальный дизайн** контракта. Из него следует: `shared_ptr` не нужен (счётчик ссылок подразумевается самими состояниями: 2 при старте, 1 после прихода одной стороны, 0 в rendezvous → тогда и разрушаем shared state), `mutex`/`condvar` в shared state не нужны — весь контракт кодируется в **одном атомике (2 бита)**. Значение и callback кладут «руками» до CAS и читают после (паттерн manual/`MonoStorage`: само состояние автомата уже говорит, есть ли значение, поэтому `optional`-флаг избыточен).

Ключевая мысль: блокирующий `get` **выносится** из shared state наружу, во `Future` (где он реализован через `Event` = atomic+futex), а в shared state остаётся лишь произвольный callback. **Зачем?** Потому что блокировка — лишь **один** сценарий из многих. Если consumer ждёт не одну future, а **первую из двух**, продюсер, выполняя свою future, должен сделать другое (разбудить или промолчать — он первый или второй?). Эту логику нельзя зашить в shared state — её определяет consumer. Вынеся ожидание, мы отделяем **синхронизацию** (автомат) от **механизма ожидания** (блокировка/первый-из-N/что угодно) — и открываем дорогу комбинаторам (§8–§9). Это та же мысль, что «в рантайме не блокируемся» из файла про пул потоков.

### 13.2. Линейность и future как значение

Аккуратный API: `contract()` возвращает пару `{future, promise}` сразу (канал логично имеет два конца с рождения); `get` — **свободная функция**, а не метод, и `set`/`get`/`detach` потребляют объект через `std::move`. Это намёк на **линейные типы (linear types)**: future нужно использовать **ровно один раз**. Линейность сильнее **аффинности (affine types**, использовать **не более** одного раза — это система типов Rust): линейные типы заставляют ресурс быть употреблённым (открыл файл/сокет — обязан закрыть) и моделируют **type-state** (нельзя `accept` до `bind`). В C++ нет ни того, ни другого — есть лишь `move`, «кривой костыль» (к moved-from-объекту всё ещё можно обратиться, хотя смысла нет). Поэтому future делают некопируемыми и запрещают даже move-assign, приближаясь к линейности как могут.

Главный сдвиг: **future — это иммутабельное будущее ЗНАЧЕНИЕ**, а не «механизм подписки». У `int` нет метода `.get()` — значит и у `future<int>` его «по-настоящему» нет; `get` — лишь один из способов распорядиться значением (как и `detach`, который его выбрасывает). Значения **передают в функции**, а не вызывают на них методы. Из этого угла «контракт», «callback», «синхронизация» — слова из другого, низкоуровневого словаря, и в модель «future = значение» они просто не вписываются.

### 13.3. Функциональный словарь: конструкторы, комбинаторы, терминаторы

Раз future — значение, операции над ними естественно делятся на три класса:
- **конструкторы** строят future из ничего/из значения: `value(x)` (готовое значение как future), `run`/`spawn` (запустить лямбду в рантайме; `spawn` подчёркивает асинхронность, ср. `tokio::spawn`);
- **комбинаторы** превращают future в future: главный — `map`, передающий будущее значение в обычную функцию. Его сигнатура `future<T> → (T → U) → future<U>` записана **каррированно** (как в Haskell — потому что функциональное программирование стоит знать);
- **терминаторы** пожирают future: `get` (дождаться) и `detach` (выбросить).

Передавать значения по цепочке функций удобно **pipeline-оператором `|`** (`value | map(f) | map(g)`), знакомым по OCaml, Rust, C++ Ranges; идея «читать слева направо, а не из середины наружу» настолько универсальна, что её предлагают добавить даже в SQL (pipeline-синтаксис Google) и в C++ (proposal pipeline-оператора). Совет лектора: выучить Haskell и λ-исчисление — «множество мыслей, выразимых на C, не исчерпывает мыслимое».

Тонкость композиции: функция, возвращающая `void`, ломает конвейер (нечего передавать дальше). В функциональной модели её возврат — это **`unit`** (тип с единственным значением, в Haskell `()`); поэтому есть конструктор `future<unit>`, а `void` всюду конвертируется в `unit`. (Спец-перегрузка для `void` в folly — ошибка дизайна.) А **`via`** (§10), если смотреть функционально, — это императивный «set» сквозной переменной (на каком executor’е/рантайме идут дальнейшие шаги) внутри функционального конвейера: им управляют, чтобы тяжёлый шаг не сел на единственный epoll-поток; `run`/`spawn` выразимы через `via`.

### 13.4. Монадический слой: flatMap, result

Если очередная функция в цепочке сама асинхронна (возвращает `future<U>`), `map` дал бы `future<future<U>>`. Лишнюю вложенность снимает **`flatten`** (`future<future<T>> → future<T>`), а их композиция — **`flatMap`** (`future<T> → (T → future<U>) → future<U>`). Это ровно `thenValue`-async из §8, нашедший «правильное» имя: `flatMap` — монадический **bind**.

Вычисления бывают сбойными, поэтому будущее значение — это часто будущий **`result<T, E>`** (= `expected`: значение или ошибка; ср. `Result` в Rust, монадический API `std::expected`/`std::optional`). Над `result` есть свои `map` (по успешному пути), **`andThen`** (следующий успешный шаг, который сам может сбоить) и **`orElse`** (обработчик ошибки). Композиция асинхронности и сбойности даёт `future<result<T>>` и **комбинаторный взрыв** (нужны `try`-версии комбинаторов). Замечание лектора: `map` на future и `map` на result — «один и тот же» `map` (functor; теория категорий), просто в одном меняется асинхронность, в другом — сбойность; монады пока вводить рано — пусть «прорастут» из примеров.

### 13.5. Язык в языке: data flow против control flow

Собрав конструкторы/комбинаторы/терминаторы, мы построили внутри C++ **отдельный функциональный асинхронный язык**: есть значения, вызовы функций, и две управляющие конструкции в новом обличье — **`flatMap` = асинхронная `;`** (следующий шаг цепочки) и **`andThen`/`orElse` = асинхронные исключения** (успешный путь и обработчик; где файберы разматывают стек, futures используют комбинаторы). «Поэзия внутри языка». Можно изобретать и **новые** управляющие структуры, которых в базовом языке нет, — например `first` (§13.6).

Отсюда главное противопоставление: программируя на потоках/файберах/корутинах, вы думаете про **control flow** (поток управления); программируя на futures — про **data flow** (как логически текут данные), а низкоуровневую синхронизацию (callback’и, атомики, memory order) прячет реализация. Для большого класса задач это шаг вперёд: вы декларируете **намерение**, а эффективное исполнение — забота рантайма (который оказывается **виртуальной машиной**, исполняющей язык futures).

### 13.6. Server as a function: почему futures хороши для распределённых систем

В распределённой системе каждый узел — **и сервер, и клиент**. Серверный обработчик удобно писать последовательно (файбер/корутина: цикл read/write) — здесь control flow хорош. Но **клиентский** вызов другого сервиса — это RPC, который может сбоить или **не вернуться никогда** (машина отказала); синхронный вызов тут не годится. Естественное представление — **future**, а сам удалённый сервис — **функция `request → future<response>`**. Это идея статьи **Marius Eriksson «Your Server as a Function»** (Twitter Finagle), которую лектор называет обязательной к прочтению.

Почему это мощно: клиент в распределённой системе сложен (нужны timeout, retry, load balancing, circuit breaker, fault detection). Представив сервис функцией, возвращающей future, каждую стратегию пишут **независимым декоратором** и свободно комбинируют. Timeout выражается **конкурентной композицией**: `timeout = first(requestFuture, timerFuture)`, где **`first`/`CollectAny`** (§9) — комбинатор, возвращающий первую завершившуюся future. Именно это **файберы/последовательный код выразить не могут** (concurrency = отсутствие happens-before между двумя «гонками»); в Go вместо него `select` — «`first` для бедных». Клиент Finagle — это **дерево декораторов** над листьями-репликами (сокетами): балансировка → fault detection → timeout → tracing → сокет.

Красивый пример — **хеджирование (hedging)**: отправить запрос на реплику, а при приближении к таймауту, не дождавшись ответа, послать второй запрос на другую реплику и взять первый пришедший ответ; на futures это пара строк (декоратор `first`), на императивном синхронном коде — почти невозможно. Futures **моделируют** распределённый мир: дерево future ↔ дерево физических действий по сети; файберы/потоки распределённого смысла не имеют. Та же идея масштабируется и в обратную сторону — **MapReduce**: пользователь пишет чистые функциональные трансформации, а рантайм строит отказоустойчивый граф (упавший шаг перезапускается, т. к. ничего не мутирует) и прячет отказы и перемещение данных — ровно как futures прячут синхронизацию.

И ещё наблюдение, замыкающее курс: WaitGroup/мьютекс для потоков, для файберов и для futures отличаются **только механизмом усыпления/пробуждения**, а сама синхронизация (атомики, memory order) одна и та же — то есть синхронизацию стоит **отделять** от механизма ожидания, и future — инструмент именно этого отделения.

### 13.7. Литература

«Your Server as a Function» (M. Eriksson) — обязательно; Haskell и λ-исчисление — как язык мышления; `std::execution` senders/receivers (§12) — «неудачная лексика, но полезный набор комбинаторов, который придётся определить любому дизайну futures»; каталоги комбинаторов folly / Twitter Finagle / Rust.

> Этот функциональный взгляд получает эффективное воплощение в **ленивой** реализации futures: вынос блокировки наружу (§13.1) доводится до полной ленивости — future ничего не делает до форсирования, а планированием и выбором storage занимается терминатор. Так futures становятся ровно моделью **senders/receivers**, исполняемой zero-cost, и объединяются с файберами/корутинами в едином рантайме. Подробный разбор — в приложении «A2. Lazy Futures».

## 14. Итоговые выводы

- **Thread pool + блокирующий I/O** ограничен числом потоков.
- **Однопоточный epoll** масштабируется по соединениям, но CPU-heavy задача блокирует всех.
- **Гибрид** (I/O-поток + пул + futures + `eventfd`) совмещает масштабируемость и параллельную обработку тяжёлых задач.
- **Future/Promise** реализуются через shared state (mutex+cv+результат); их неудобства — только блокирующее ожидание, аллокация, отсутствие композиции и контроля потока, блокирующий деструктор у `std::async`.
- **Subscribe + комбинаторы** дают неблокирующую композицию; ядро реализации — атомарная гонка состояний между подпиской и установкой результата.
- **Executors** убирают недетерминизм потока исполнения continuations и изолируют нагрузку (I/O vs CPU).
- **folly** — зрелая production-реализация futures с executors; **корутины** и модель **senders/receivers** — современное продолжение этой линии.
- **Функциональный взгляд (§13):** future = иммутабельное будущее **значение**; контракт сводится к автомату из 4 состояний (один атомик), а блокировка выносится наружу, открывая комбинаторы; конструкторы/комбинаторы (`map`, `flatMap`)/терминаторы образуют **язык в языке** (`flatMap` = асинхронная `;`, `andThen`/`orElse` = асинхронные исключения; data flow вместо control flow). Futures моделируют распределённый мир («server as a function», Finagle): клиентские декораторы + конкурентная композиция `first` (timeout, hedging), которую файберы выразить не могут.
