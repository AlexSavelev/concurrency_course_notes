# Когерентность кэшей: иерархия памяти, MESI, false sharing

Этот блок отвечает на вопрос: как написать примитивы синхронизации не просто **корректно**, а **эффективно**. Ключевая идея, к которой мы придём: за фасадом «разделяемой памяти» прячется маленькая распределённая система из ядер, и оптимизировать синхронизацию — значит **оптимизировать коммуникацию** между ними.

## 1. Зачем нужны кэши: модель стоимостей

**Кэш (cache)** в общем смысле — небольшое быстрое хранилище ответов перед медленным большим хранилищем. Запрос сначала идёт в кэш: **попадание (cache hit)** — ответ сразу; **промах (cache miss)** — проваливаемся в медленное хранилище, обслуживаемся и кладём ответ в кэш на будущее. Кэш ограничен по ёмкости, при переполнении элемент **вытесняется (eviction)**.

В процессоре та же конструкция между **быстрым ядром** и **медленной памятью**. Транзисторы перестали ускоряться, но ядро над регистрами делает миллиарды операций в секунду — простая инструкция стоит меньше наносекунды. А обращение к памяти на порядок дороже. Полезно держать в голове таблицу «latency numbers every programmer should know» (Дин/Норвиг) и её метафору — **пивная (или водяная) иерархия**:

- регистр — бутылка уже в руке (доли наносекунды);
- L1-кэш — взять со стола, протянув руку (~1 нс);
- L2-кэш — дойти до холодильника;
- L3-кэш / оперативная память — спуститься в погреб (~100 нс);
- диск — поехать в другую страну (миллисекунды, «бесконечно долго»).

Эта грубая метафора уже достаточна, чтобы принимать решения об оптимизации: важны не точные числа, а **порядки**.

## 2. Как устроен кэш

В отличие от абстрактного кэша, процессорный кэш хранит не отдельные ячейки, а целые блоки — **кэш-линии (cache lines)**, типичный размер **64 байта**. При промахе по чтению из памяти подтягивается вся линия; при записи линия меняется в кэше, а в память сбрасывается позже, асинхронно.

Аппаратно кэш — это таблица с фиксированным числом **бакетов (sets)**, каждый из фиксированного числа **слотов (ways)**. Например, **8-way set associative** кэш: у каждой 64-байтной линии всего 8 позиций, куда она может лечь (бакет выбирается по части физического адреса). Если все слоты бакета заняты, при вставке что-то вытесняется.

Кэш не один — это **иерархия (L1 / L2 / L3)**: каждый следующий уровень дальше от ядра, больше и медленнее (память дешевле). L1 нередко разделён на кэш инструкций и кэш данных. Типичные размеры — десятки КБ (L1), единицы МБ (L2), десятки МБ (L3) — на порядки меньше оперативной памяти (сотни ГБ). Почему такие маленькие кэши помогают? Потому что программы обращаются к памяти не произвольно — у них есть **локальность**.

## 3. Локальность и cache-oblivious алгоритмы

Стандартная **RAM-модель** считает любое обращение к памяти единицей стоимости, не различая близкие и далёкие ячейки. С кэшами эта модель неточна — нужна модель, учитывающая локальность двух сортов.

**Пространственная локальность (spatial locality):** обратившись к ячейке, программа скоро обратится к соседним. Классический вопрос — `std::vector` против `std::list` при обходе: в RAM-модели обход линеен у обоих, но при обходе вектора первый промах подтягивает целую линию, и следующие несколько элементов читаются из кэша (в ~100 раз быстрее); у списка с произвольно разбросанными узлами почти каждый шаг — промах. Другой пример — **умножение матриц**: идя по `A` построчно (хороший паттерн, строки лежат подряд) и по `B` по столбцам (каждый следующий элемент далеко), мы прыгаем нелокально; простое **транспонирование `B`** делает оба обхода построчными и заметно ускоряет код — оптимизация «даром», за счёт более точной модели стоимости, нетипичная для алгоритмов, но типичная для промышленного кода.

```cpp
// Наивно: B обходится по столбцам — каждый B[k][j] далеко в памяти → промах на каждом шаге
for (int i = 0; i < N; ++i)
  for (int j = 0; j < N; ++j) {
    double s = 0;
    for (int k = 0; k < N; ++k) s += A[i][k] * B[k][j];   // B[k][j]: шаг N*sizeof(double)
    C[i][j] = s;
  }

// С транспонированием: оба обхода построчные (A[i][k] и Bt[j][k] идут подряд) → попадания в кэш
for (int i = 0; i < N; ++i)
  for (int k = 0; k < N; ++k) Bt[i][k] = B[k][i];          // транспонируем один раз
for (int i = 0; i < N; ++i)
  for (int j = 0; j < N; ++j) {
    double s = 0;
    for (int k = 0; k < N; ++k) s += A[i][k] * Bt[j][k];   // оба указателя движутся по линии
    C[i][j] = s;
  }
```

**Временная локальность (temporal locality):** обратившись к ячейке, программа скоро обратится к ней повторно. Пример — `std::set` (сбалансированное дерево): даже при поиске разных элементов проход всегда идёт через верхушку дерева, и закэшированная верхушка ускоряет все поиски.

Класс алгоритмов, спроектированных под иерархию памяти, называется **cache-oblivious / cache-aware алгоритмами** (алгоритм может знать или не знать размер линии/кэша). Красивый пример — бинарный поиск, который наивно прыгает нелокально (середина → четверть → …): рекурсивная **фрактальная укладка массива (van-Emde-Boas layout)** заставляет поиск двигаться по статическому дереву локально, не зная даже размера линии. (Курсы: Erik Demaine, MIT, «Advanced Algorithms»; Максим Бабенко, ШАД.)

Это всё про однопоточный код. А при чём тут многопоточность?

## 4. Многоядерность: проблема согласованности копий

Если добавить ядра, у каждого окажется **свой локальный кэш**. Тогда одна логическая ячейка разделяемой памяти распадается на **много копий**: версия в оперативной памяти плюс копии в кэшах отдельных ядер. И эти копии нужно держать согласованными.

Иллюстрация (из книги Пола Маккини): запускаем потоки, каждый в начале пишет в общую ячейку свой номер, потом в цикле читает её. История наблюдаемых значений показывает, что у одной ячейки как будто **несколько значений одновременно** — разные ядра видят разное.

Это в точности задача **распределённых систем**: там ради отказоустойчивости данные **реплицируют**, и реплики должны быть согласованы, хотя физически одновременно одинаковыми быть не могут — у пользователя при этом должна сохраняться иллюзия одного атомарного хранилища. В процессоре задача проще: ядра, в отличие от узлов сети, не отказывают. Поэтому поверх иерархии кэшей по **шине/интерконнекту** реализуется протокол вроде **atomic broadcast**, упорядочивающий все события (чтения и записи).

Главное, что нам нужно от процессора, — **гарантии**. Сформулируем два инварианта когерентности (coherence invariants):

1. Если у одной кэш-линии есть несколько копий в кэшах, то **все они совпадают** между собой и с памятью.
2. Если копия линии в кэше **расходится** с памятью (грязная), то эта копия — **единственная** (других копий нет).

Это ровно семантика **readers–writer lock** на уровне линии: либо несколько ядер читают чистую копию (shared), либо одно ядро эксклюзивно владеет грязной (exclusive write). Благодаря этим инвариантам мы можем **не думать о кэшах, рассуждая о корректности** — абстракция единой ячейки памяти сохраняется. Думать о кэшах нужно, когда нас волнует **производительность**.

## 5. Протокол когерентности: MSI / MESI / MOESI

Инварианты обеспечивает **протокол когерентности**, реализующий для каждой линии в каждом кэше маленький автомат.

**MSI** — три состояния линии:
- **M (Modified)** — грязная, отличается от памяти, существует только в этом кэше;
- **S (Shared)** — чистая, совпадает с памятью, **может** находиться в нескольких кэшах;
- **I (Invalid)** — слот пуст.

Переходы — это чтения и записи ядра, превращающиеся в сообщения на шине (**write-invalidate** протокол):
- Чтение из `I`: отправляем «читаю» на шину; если у кого-то линия в `M`, он сбрасывает её в память; наша линия становится `S`.
- Запись: отправляем «инвалидируйте»; чистые копии у других дропаются, грязная сбрасывается; наша линия → `M`, у остальных → `I`.

**MESI** добавляет состояние **E (Exclusive)** — чистая линия, но **строго в одном кэше**. Это оптимизация однопоточного паттерна «прочитал → записал»: запись из `E` переводит линию в `M` **без коммуникации** (мы и так знаем, что других копий нет). При появлении второго читателя `E` переходит в `S`. Важно: `S` не утверждает, что копия есть в нескольких кэшах, — лишь что она **может** быть и точно совпадает с памятью.

**MOESI** добавляет **O (Owned)** — грязная копия, которая при этом не инвалидирует другие (оптимизация чтений). В реальных процессорах состояний бывает больше десятка.

Здесь работает принцип «**все модели неправильные, но некоторые полезные**»: реальный протокол сложнее (как и инструкция `mov` внутри — не одна операция), и наш симулятор может отличаться от железа. Но для оптимизации это неважно. Важно одно: **когда происходит коммуникация между ядрами, а когда нет**. Локальная запись/чтение в линию, которой мы эксклюзивно владеем, — бесплатны; запись в чужую/общую линию требует инвалидации и сообщений по шине.

## 6. Стоимость = коммуникация. CAS — всегда запись

Современный процессор — большая распределённая система: на 64-ядерном чипе есть целая **матрица стоимостей коммуникации** между ядрами (как NUMA). Поэтому **оптимизировать синхронизацию = оптимизировать коммуникацию**: избавляться от избыточных инвалидаций и перечитываний. Стоимость атомарной операции зависит от пути: быстрый путь пишет в локальный кэш, медленный требует инвалидации всех копий.

Когда несколько ядер наперебой пишут в одну кэш-линию, она безостановочно «летает» между их кэшами: запись на ядре A инвалидирует копию на B (`M` у A), чтение/запись на B тянет линию к себе и инвалидирует A, и так по кругу. Это **cache ping-pong** — главный источник деградации под contention. Он возникает и при *настоящем* разделении (горячий счётчик/мьютекс, который дёргают все), и при *ложном* (false sharing, §7), когда в одну линию случайно попали логически независимые данные.

Отдельно про **CAS / `compare_exchange`**: семантически это **условная** запись (может записать, а может нет), но на уровне протокола когерентности это **всегда запись** — ядро пессимистично инвалидирует все копии заранее, не зная, удастся ли обмен. В модели стоимости CAS считаем записью всегда.

Для построения интуиции достаточно даже простого MSI (без `E`): надо лишь понимать, в каких сценариях нужна коммуникация. Модель будет неправильной, но полезной — оптимизируем в модели, проверяем на реальном железе.

## 7. Приложение 1: счётчик метрик и false sharing

**Наблюдаемость (observability)** системы стоит на трёх китах: **логи (logs)**, **трейсы (traces)**, **метрики (metrics)**. Метрики — это счётчики (сколько задач выполнено, сколько файберов заснуло и т. д.). Вопрос: как реализовать счётчик, который не станет узким местом?

Наивный **атомарный счётчик** корректен, но не масштабируется: инструкция с префиксом `lock` — это, по сути, маленький мьютекс на шине памяти; на каждый инкремент со многих ядер он сериализует доступ и создаёт **bottleneck в месте, где мы всего лишь наблюдаем за системой** (и тем самым искажаем её исполнение — наблюдение влияет на наблюдаемое).

Идея — **шардировать** счётчик: завести несколько компонент (по хешу от thread-id попадаем в свой шард), инкрементировать свою, а при чтении (`get`, происходит редко) обойти все и просуммировать. Несколько атомиков → несколько независимых «мьютексов» → физический параллелизм.

Но в этой идее скрыта **ловушка**: 8 шардов по 8 байт = ровно **64 байта = одна кэш-линия**. Тогда инкремент в *разные* шарды с разных ядер — всё равно запись в **одну линию**, то есть `M` + инвалидация чужих копий. Получается даже **медленнее** атомика: последовательно плюс коммуникация плюс задержка шины. Это и есть **false sharing (ложное разделение)**: логически независимые ячейки физически слиплись в одну линию, а гранулярность протокола — линия.

Лечение — **паддинг / выравнивание**, разносящее горячие ячейки по разным линиям, окружая каждую «буферной зоной»:

```cpp
#include <new>
struct alignas(std::hardware_destructive_interference_size) Shard {
    std::atomic<long long> value{0};   // каждый шард — в своей кэш-линии
};
Shard shards[NUM_SHARDS];
```

Три версии для сравнения — наивная, шардированная (с ловушкой) и выровненная:

```cpp
// (1) Наивный атомик: bottleneck, lock на каждый ++ со всех ядер
struct NaiveCounter {
    std::atomic<long long> value{0};
    void inc()        { value.fetch_add(1, std::memory_order_relaxed); }
    long long get()   { return value.load(std::memory_order_relaxed); }
};

// (2) Шардированный БЕЗ выравнивания: 8*8 = 64 байта = одна линия → FALSE SHARING (может быть медленнее (1))
struct ShardedBad {
    std::atomic<long long> shards[NUM_SHARDS]{};                 // лежат подряд → одна кэш-линия
    void inc()      { shards[hash_tid() % NUM_SHARDS].fetch_add(1, std::memory_order_relaxed); }
    long long get() {                                            // читается редко
        long long s = 0;
        for (auto& sh : shards) s += sh.load(std::memory_order_relaxed);
        return s;
    }
};

// (3) Шардированный С выравниванием: каждый шард в своей линии → масштабируется
struct ShardedPadded {
    Shard shards[NUM_SHARDS];                                    // alignas(destructive size)
    void inc()      { shards[hash_tid() % NUM_SHARDS].value.fetch_add(1, std::memory_order_relaxed); }
    long long get() {
        long long s = 0;
        for (auto& sh : shards) s += sh.value.load(std::memory_order_relaxed);
        return s;
    }
};
```

Константа `std::hardware_destructive_interference_size` (C++17) — это и есть «минимальное расстояние, разрушающее ложное разделение» (есть и парная `constructive_interference_size` — наоборот, чтобы что-то держать в одной линии). Магическую `64` лучше не хардкодить. После выравнивания счётчик масштабируется.

Оговорки честности: идеального ускорения не гарантируется — мы лишь **даём процессору подсказку** и извлекаем параллелизм; коллизии шардов (два потока в один шард) возвращают коммуникацию, и чем больше ядер, тем заметнее. Цель — получить параллелизм **в модели**, а дальше он ляжет на несовершенства реального железа. Шардирование можно делать и через `thread_local` (но обращение к нему само чего-то стоит), и через статический массив со случайным выбором — суть одна: разбить целое на изолированные компоненты.

## 8. Приложение 2: эффективный спинлок

Базовый test-and-set спинлок:

```cpp
void lock()   { while (state.exchange(true)) ; }   // плохо: каждый виток — запись
void unlock() { state.store(false); }
```

Сценарий под конкуренцией: владелец держит лок, а десятки претендентов в цикле делают `exchange`. Каждый `exchange` — это **запись**, то есть переход в `M` и **инвалидация** линии у всех остальных. Полезной работы ноль, но ядра гоняют линию с единичкой друг другу — это **cache ping-pong**, процессор греется впустую.

Лечение — **TTAS (test-and-test-and-set)**: крутиться на **чтении** (`load`, линия остаётся в `S`, никто никого не инвалидирует) и пробовать `exchange` только увидев «свободно»:

```cpp
void lock() {
    while (true) {
        while (state.load(std::memory_order_relaxed)) ;     // спин на чтении — без коммуникации
        if (!state.exchange(true, std::memory_order_acquire)) return;
    }
}
```

Тогда владелец один раз записал свою линию, она разошлась как `S`, и все ожидающие крутятся на локальных чистых копиях — коммуникация исчезает, пока лок не освободится. Реальные реализации (libstdc++ `__spin_lock` и т. п.) именно так и устроены. **Цикл с `load` в спинлоке обязателен** — без него это игрушка; неважно, пишете вы `load` отдельным циклом или внутри, суть одна.

Что остаётся неоптимального даже в TTAS-спинлоке — **грохочущее стадо (thundering herd)** (название из вестерна). Когда лок освобождается, владелец инвалидирует линию у всех ожидающих; те перечитывают, видят ноль и **все разом** делают попытку `exchange` — снова шторм и коммуникация, хотя захватит один. Тот же эффект — у `condition_variable::notify_all` (все потоки просыпаются и сталкиваются на мьютексе) и у любой реализации мьютекса/кондвара.

Ещё пример false sharing — **ticket lock**: если `owner_ticket` (на котором крутятся ожидающие) и `next_free_ticket` (который инкрементирует входящий) лежат в одной линии, то приход нового потока (`fetch_add` по `next`) инвалидирует линию с `owner` у всех ожидающих, и они зря перечитывают. Разнести по линиям можно, но это замедлит быстрый путь (две линии вместо одной для свободного лока) — компромисс. А запись `unlock` в `owner_ticket` в любом случае сбивает линию у всех — лишняя работа для процессора.

Далее спинлоки улучшают вплоть до **очередных (queue-based) блокировок** — обширная тема (обзорный доклад Нира Шавита на ~197 слайдов). Затейливый спинлок с **явной очередью ожидающих потоков** — это **MCS-lock** (Mellor-Crummey & Scott): каждый поток крутится на **собственном** локальном флаге, поэтому при освобождении владелец будит ровно одного преемника, без грохочущего стада и без общей горячей линии, — и на большом числе ядер такой лок масштабируется лучше ticket lock. Это продолжение темы справедливых масштабируемых блокировок.

## 9. Итог

- Память на порядок медленнее ядра; спасают кэши, работающие на **локальности** (пространственной и временной), с гранулярностью **кэш-линии** (64 байта).
- На многих ядрах одна логическая ячейка = много копий; **протокол когерентности** (MSI/MESI/MOESI) поддерживает два инварианта (копии равны и равны памяти, либо грязная копия единственна) через write-invalidate по шине.
- Модель неправильная, но полезная: важно лишь, **когда нужна коммуникация**. Оптимизировать синхронизацию = минимизировать коммуникацию; CAS в этой модели — всегда запись.
- **False sharing** — независимые ячейки в одной линии; решается выравниванием на `std::hardware_destructive_interference_size`.
- В спинлоке крутимся на `load` (TTAS), чтобы убрать **cache ping-pong**; остаётся **thundering herd** при освобождении — общий сюжет для спинлока, мьютекса и кондвара.

Но даже с правильной работой с кэшами остаётся следующий уровень сложности: компилятор и процессор **переупорядочивают** обращения к памяти, и наша простая «модель чередования» перестаёт работать. Но это уже совсем другая история.
