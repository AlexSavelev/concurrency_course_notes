# Файберы и переключение контекста (context switch)

## 1. Синхронный эхо-сервер (наивно)

Простейший сервер — поток на клиента:

```cpp
void session(Socket client) {
    char buf[1024];
    while (true) {
        ssize_t n = read(client, buf, sizeof(buf));
        if (n <= 0) break;                 // EOF или ошибка
        write(client, buf, n);
    }
}
// while (true) std::thread(session, accept(server)).detach();
```

Проблема (подробно — в файлах про многопоточный сервер и IO multiplexing): поток ОС на каждого клиента дорог — стек ~8 МБ, переключения контекста через ядро; десятки тысяч соединений система не выдержит (C10k).

## 2. Асинхронный сервер на epoll (эффективно, но сложно)

Эффективная обработка тысяч соединений — неблокирующий I/O + мультиплексирование. Рассмотрим Boost.Asio, инкапсулирующий `epoll` внутри `io_context`.

### 2.1. Класс `session`

```cpp
class session : public std::enable_shared_from_this<session> {
public:
    session(tcp::socket socket) : socket_(std::move(socket)) {}
    void start() { do_read(); }
private:
    void do_read() {
        auto self(shared_from_this());
        socket_.async_read_some(boost::asio::buffer(data_, max_length),
            [this, self](boost::system::error_code ec, std::size_t length) {
                if (!ec) do_write(length);
                // ec != 0 → лямбда завершается, self (shared_ptr) разрушается → session удаляется
            });
    }
    void do_write(std::size_t length) {
        auto self(shared_from_this());
        boost::asio::async_write(socket_, boost::asio::buffer(data_, length),
            [this, self](boost::system::error_code ec, std::size_t) {
                if (!ec) do_read();
            });
    }
    tcp::socket socket_;
    enum { max_length = 1024 };
    char data_[max_length];
};
```

**Важное:**
1. `std::enable_shared_from_this` даёт `shared_from_this()` — продлевает жизнь `session` после выхода из `start()`. Без этого объект удалился бы, а колбэк обращался бы к невалидной памяти.
2. **Цепочка асинхронных операций:** `start()` → `do_read()` (регистрирует `async_read_some` + колбэк) → по готовности данных колбэк зовёт `do_write()` → по завершении записи снова `do_read()`.
3. **Обработка ошибок:** при ошибке колбэк не входит в `if (!ec)`, лямбда завершается, захваченный `self` разрушается, счётчик ссылок обнуляется — `session` удаляется автоматически.

### 2.2. Класс `server` и `main`

```cpp
class server {
public:
    server(boost::asio::io_context& io, short port)
        : acceptor_(io, tcp::endpoint(tcp::v4(), port)), socket_(io) { do_accept(); }
private:
    void do_accept() {
        acceptor_.async_accept(socket_, [this](boost::system::error_code ec) {
            if (!ec) std::make_shared<session>(std::move(socket_))->start();
            do_accept();                    // снова принимаем следующего
        });
    }
    tcp::acceptor acceptor_;
    tcp::socket socket_;
};

int main(int argc, char* argv[]) {
    boost::asio::io_context io_context;
    server s(io_context, std::atoi(argv[1]));
    io_context.run();                       // event loop (внутри — epoll_wait + диспетчеризация колбэков)
    return 0;
}
```

### 2.3. Callback hell

Код эффективен (один поток — тысячи соединений), но: логика «читать → писать» разорвана на функции и лямбды; время жизни объектов вручную через `shared_ptr`; усложнение логики (параллельные запросы, ретраи, таймауты) даёт экспоненциальный рост вложенности — **callback hell**. (Эскейп через futures/continuations — в файле про futures.)

Полезно увидеть, что именно здесь произошло (одна и та же трансформация — в файле про IO multiplexing и stackless-корутины). Вызовы стали **асинхронными**: возврат из `async_read_some` **не означает**, что чтение завершилось (определение sync/async — в файле про IO multiplexing). Раз блокировать единственный поток нельзя, естественный цикл `while (read; write)` приходится **разрезать** в точках ввода-вывода: всё, что идёт после операции и до следующей, превращается в **колбэк**. Цикл исчезает как явная конструкция — остаётся **автомат**, подчинённый одному циклу `epoll`: `session` стала классом, локальный `buffer` — полем, позиция в коде (старт / после `read` / после `write`) — состоянием. Это та же «лапша», что у `yield` в файберах (см. файл про планировщик), только разрезает не планировщик, а вы сами руками. Лекарство — **корутина**: она делает эти разрезы за вас, и колбэк превращается в `coro.resume()`, а пользовательский код снова выглядит синхронным (§8.2).

## 3. Идея: писать синхронно, исполнять асинхронно

Хочется простоту блокирующего кода и эффективность `epoll`. Решение — **кооперативная многозадачность в пространстве пользователя**: user-space threads, они же зелёные потоки (green threads), они же **файберы (fibers)**.

### 3.1. Принцип

- Каждый файбер — лёгкий поток со своим стеком.
- Исполняется последовательно, пока сам не решит «уснуть» (например, на I/O, когда данных нет).
- В функции I/O файбер сохраняет состояние (регистры, `RSP`), регистрирует интерес в `epoll` и отдаёт управление планировщику.
- Планировщик выбирает другой готовый файбер и переключает контекст.
- Когда `epoll` сообщит о готовности, планировщик возобновляет спящий файбер — тот продолжает с того же места, будто I/O наконец вернул данные.

```cpp
void echo_client(Socket socket) {
    char buffer[1024];
    while (true) {
        size_t n = async_read(socket, buffer);  // здесь файбер может уснуть
        if (n == 0) break;
        async_write(socket, buffer, n);
    }
}
```

Внешне — обычный блокирующий код; внутри `async_read`/`async_write` — `epoll` + переключение контекстов.

## 4. Что нужно для файбера

1. **Стек** — локальные переменные, адреса возврата, сохранённые регистры.
2. **Набор регистров:** `RIP` (instruction pointer), `RSP` (stack pointer), callee-saved регистры общего назначения (`RBP`, `RBX`, `R12`–`R15`).
3. **Состояние** (running / runnable / waiting) — для планировщика.

В отличие от потоков ОС, вытесняемых (preempted) по таймеру в любой момент, файберы **кооперативны** — отдают управление только явно (`yield` или ожидание I/O). Это и позволяет контролировать точки сохранения контекста.

### 4.1. Стек файбера: guard page и пул

- **Guard page.** Под маленьким стеком файбера размещают страницу с `mprotect(PROT_NONE)`: переполнение даёт детерминированный `SIGSEGV` вместо тихой порчи памяти соседнего файбера. Это смягчает дилемму размера стека (которая в пределе и мотивирует stackless-корутины).
- **Пул стеков.** `mmap` на каждый файбер дорог; стеки переиспользуют из пула — критично при миллионах короткоживущих файберов.
- **Red zone (128 байт System V ABI).** Тонкость при ручном переключении и обработке сигналов на стеке файбера: leaf-функции используют 128 байт ниже `RSP` без коррекции указателя; под сигналы выделяют отдельный стек (`sigaltstack`).

### 4.2. ExecutionContext против MachineContext

Полезное разграничение. Низкоуровневый **MachineContext** — это про **регистры** процессора (`RSP` + callee-saved + неявный `RIP`); именно его переключает `SwitchContext` (§6). Но «состояние исполнения» шире регистров, поэтому поверх него вводят **ExecutionContext** — он про **исполнение**, а не про файбер, и не знает о файберах ничего. Помимо регистров в него входит то, что нужно сохранять/восстанавливать при смене исполнения: состояние **санитайзеров** (ASan/TSan ведут свои теневые данные на каждый стек, см. §6.3), состояние раскрутки **исключений** и прочее, что потребуется. Раз контекст — про абстрактное «исполнение», им единообразно переключаются между **потоком и файбером**, между **файбером и файбером**: с точки зрения ядра и поток, и файбер выглядят одинаково (исполнение на регистрах поверх стека). Это и позволяет планировщику (отдельный файл) прыгать из `main`-потока в файбер и обратно одним и тем же механизмом.

## 5. Calling convention x86-64 (System V AMD64 ABI)

Чтобы переключать контекст, надо знать, как вызываются функции и какие регистры сохраняются.

### 5.1. Классификация регистров

- **Caller-saved (временные):** вызывающий сохраняет их перед вызовом, если нужны после; вызываемый волен перезаписывать. Это `RAX` (возврат), `RCX`, `RDX`, `RSI`, `RDI`, `R8`–`R11`.
- **Callee-saved (сохраняемые):** вызываемый обязан сохранить (обычно в прологе на стек) и восстановить перед возвратом. Это `RBX`, `RBP`, `R12`–`R15`, а также `RSP` и `RIP` (управляются `call`/`ret`).

### 5.2. Передача аргументов

Первые 6 целочисленных — в `RDI`, `RSI`, `RDX`, `RCX`, `R8`, `R9`; остальные — на стек (в обратном порядке); возврат (целый) — в `RAX`.

### 5.3. Стек, пролог и эпилог

Стек растёт вниз. При вызове: caller кладёт на стек аргументы, не вместившиеся в регистры; `call` делает `push RIP` + `jmp`. Пролог callee: `push RBP` → `mov RBP, RSP` → `sub RSP, N` (локальные) → сохранение нужных callee-saved. Эпилог: восстановление callee-saved → `mov RSP, RBP` → `pop RBP` → `ret`.

```
[ аргументы 7,8,...  ]  ← если есть
[   RIP возврата     ]
[   старый RBP       ]
[ локальные переменные ]
[ callee-saved regs  ]  ← RSP указывает сюда
```

### 5.4. Какие регистры сохранять при переключении

Переключение происходит внутри некоторой функции (например, `read`). Caller-saved уже сохранены вызывающим или не важны; callee-saved могли использоваться компилятором в теле и должны быть сохранены для корректного возобновления. Итого состояние файбера = `RSP` + все callee-saved (`RBX`, `RBP`, `R12`–`R15`) + адрес возврата `RIP` (неявно лежит на стеке). Остальное (caller-saved, локальные) уже на стеке и восстановится по цепочке вызовов.

**Почему это так дёшево: переключение контекста — это вызов функции.** Файбер уступает управление **добровольно**, вызывая `SwitchContext`. А раз это обычный вызов, компилятор в точке вызова по calling convention **уже не рассчитывает** на сохранность caller-saved регистров — он сам позаботился о нужных ему значениях. Поэтому переключателю достаточно сохранить **только callee-saved**. Сравните с **вытеснением потока по таймеру**: прерывание приходит в **произвольной** точке, где никаких соглашений о вызове не действует, поэтому ядру приходится сохранять **полный** набор регистров (включая SIMD/флаги). Кооперативность файберов и есть то, что делает их переключение лёгким.

## 6. Переключение контекста: `SwitchContext`

`SwitchContext` сохраняет текущее состояние в `from` и загружает состояние из `to` (ассемблер, файл `ctx.S`).

### 6.1. Сигнатура и идея

```c
void SwitchContext(void** from_rsp, void* to_rsp);
```

- `from_rsp` — адрес переменной, **куда** сохранить текущий `RSP` (поэтому `void**`).
- `to_rsp` — новый `RSP`, на который переключаемся.

Callee-saved регистры хранятся **на самом стеке**. При переключении: (1) push callee-saved на текущий стек; (2) записать `RSP` по `*from_rsp`; (3) `RSP := to_rsp`; (4) pop callee-saved с нового стека; (5) `ret` — снимет адрес возврата с вершины нового стека.

**Трюк с `RIP`.** Прямого доступа к `RIP` (instruction pointer) из кода нет — его нельзя ни прочитать, ни записать инструкцией `mov`. Но он и не нужен явно: `SwitchContext` — обычная функция, и компилятор вызывает её инструкцией `call`, которая **сама кладёт `RIP` возврата на стек** при входе. Симметрично `ret` в конце **снимает** этот адрес со стека нового контекста и переходит по нему. Так `call`/`ret` бесплатно делают за нас сохранение/восстановление точки исполнения: контекст возобновляется ровно с инструкции, следующей за тем `SwitchContext`, которым его когда-то усыпили.

### 6.2. Ассемблер (x86-64, System V)

```asm
FUNCTION_NAME(SwitchContext):
    # Сохраняем callee-saved на текущем стеке
    pushq %r15
    pushq %r14
    pushq %r13
    pushq %r12
    pushq %rbx
    pushq %rbp

    movq %rsp, (%rdi)   # *from_rsp = RSP   (rdi = from_rsp)
    movq (%rsi), %rsp   # RSP = to_rsp      (rsi = to_rsp)

    # Восстанавливаем callee-saved с нового стека
    popq %rbp
    popq %rbx
    popq %r12
    popq %r13
    popq %r14
    popq %r15

    retq                # снимет RIP с нового стека и перейдёт по нему
```

После восстановления регистров на вершине нового стека лежит адрес возврата, помещённый туда при последнем сохранении этого контекста; `ret` переходит по нему — файбер возобновляется ровно с места сохранения.

> Замечание: рукописный asm здесь учебный. В production контекст переключают через `ucontext` (`makecontext`/`swapcontext`) или **Boost.Context** (`fcontext`, быстрее ucontext, так как не трогает сигнальную маску). Идея та же.

### 6.3. Аннотации санитайзеров

Переключение стеков «из-под» санитайзеров их сбивает: и ASan, и TSan ведут на каждое исполнение **теневое состояние** (ASan — границы стека для детекции переполнений, TSan — историю happens-before на потоке), и при ручной смене стека их надо уведомлять. Перед/после `SwitchContext` зовут `__sanitizer_start_switch_fiber` / `__sanitizer_finish_switch_fiber` (ASan) и `__tsan_switch_to_fiber` (TSan) — иначе ASan ложно ругается на «переполнение», а TSan путает границы исполнений. Это часть **ExecutionContext** (§4.2): состояние санитайзера — такая же часть исполнения, как регистры. Та же машинерия нужна и для многопоточных файберов (см. файл про планировщик, fault injection).

## 7. Создание начального контекста: `SetupContext`

Чтобы новый файбер при первом `SwitchContext` начал с заданной функции (трамплина), нужно сформировать на пустом стеке структуру, имитирующую сохранённый контекст.

### 7.1. Проблема виртуальных функций

Хотим, чтобы файбер стартовал с `Run()` интерфейса `ITrampoline`. Но адрес виртуальной функции определяется через vtable в рантайме — его нельзя просто записать на стек. Решение — **статическая** функция-трамплин `StaticTrampoline` с фиксированным адресом, принимающая указатель на `ITrampoline`.

```cpp
struct ITrampoline { virtual void Run() = 0; };

static void StaticTrampoline(void*, void*, void*, void*, void*, void*, void* arg) {
    static_cast<ITrampoline*>(arg)->Run();
}
```

Первые 6 аргументов передаются в регистрах, седьмой — на стеке; `StaticTrampoline` объявлена с семью параметрами, чтобы `arg` оказался на стеке в ожидаемом месте.

### 7.2. Ассемблер `SetupContext`

```asm
FUNCTION_NAME(SetupContext):
    # %rdi - stack (нижняя граница), %rsi - StaticTrampoline, %rdx - ITrampoline*
    movq %rsp, %r11        # сохранить текущий RSP
    movq %rdi, %rsp        # переключиться на новый стек

    subq $64, %rsp         # выравнивание по 16 байт (требование ABI)
    andq $-16, %rsp
    addq $8, %rsp

    movq %rdx, 8(%rsp)     # ITrampoline* — будущий 7-й аргумент
    pushq %rsi             # адрес StaticTrampoline — будущий адрес возврата

    pushq $0  # r15        # имитируем сохранённые callee-saved (нули — контекст новый)
    pushq $0  # r14
    pushq $0  # r13
    pushq $0  # r12
    pushq $0  # rbx
    pushq $0  # rbp

    movq %rsp, %rax        # вернуть указатель на вершину искусственного стека
    movq %r11, %rsp        # восстановить исходный стек
    retq
```

### 7.3. Как это работает

При первом `SwitchContext` в новый контекст: сохраняются callee-saved текущего файбера; `RSP` переключается на `rsp_`; с вершины восстанавливаются `rbp,rbx,r12–r15` (нули — допустимо); `ret` извлекает адрес `StaticTrampoline` и передаёт ему управление; `StaticTrampoline` снимает со стека 7-й аргумент (`arg`) и вызывает `arg->Run()` — стартует пользовательская логика.

Важно: `Run()` **никогда не должен завершаться обычным `return`**. Любая функция в C++ компилируется так, что заканчивается инструкцией `ret`, которая снимает адрес возврата со стека и прыгает по нему. Но пользовательская процедура лежит **на дне** стека файбера — выше неё ничего нет, снимать нечего: `ret` «пробьёт дно» и прыгнет по мусору, программа развалится. Поэтому на дне стека файбера лежит не пользовательская лямбда, а **трамплин**: завершив `routine_()`, он покидает обречённый контекст через `SwitchLast`, передавая управление планировщику с намерением **никогда сюда не возвращаться** (см. файл про планировщик; там же — почему это к тому же корректно для санитайзеров).

## 8. Связь с планировщиком и `epoll`

Файберы дают лишь механизм переключения. Для полноценного асинхронного сервера нужен **планировщик** (подробно — в файле про планировщик), который: управляет очередью готовых файберов; интегрируется с `epoll` (регистрирует fd и ожидающие файберы); при событии переводит файбер из ожидания в очередь готовых.

`async_read`/`async_write` на деле: (1) регистрируют текущий файбер в `epoll` на нужное событие; (2) сохраняют контекст (`SwitchContext` в планировщик); (3) планировщик выбирает другой файбер; (4) по сигналу `epoll` планировщик возобновляет файбер. Пользователь пишет линейный синхронный код — под капотом асинхронная обработка.

### 8.1. База индукции: контекст `main` создаёт ОС

Переключения контекста индуктивны: чтобы прыгнуть в файбер и вернуться, планировщик сохраняет «откуда» и восстанавливает «куда». Но у индукции нужна **база** — самый первый контекст, в который никто не «сохранялся». Его создаёт **операционная система**: запуская процесс, она заводит поток `main` и аллоцирует ему стек. Планировщик исполняется в этом потоке; первый `SwitchContext` фиксирует контекст `main` и активирует файбер. Поэтому «контекст планировщика», в который файбер возвращается через `SwitchLast`/`SwitchToSched`, всегда валиден — мы в него **попали** через сохранение, прежде чем уйти в файбер.

### 8.2. Файбер-IO через корутину: колбэк становится `resume`

Связь с callback hell (§2.3) замыкается так. Асинхронный сервер на Asio резал цикл `read→write` на колбэки руками. Файбер делает это автоматически: операция `async_read` внутри регистрирует сокет в `epoll` и **останавливает корутину** файбера (через `SwitchContext` в планировщик); в качестве «колбэка готовности» планировщику передаётся продолжение, которое по событию `epoll` сделает `coro.resume()`. Для рантайма (event loop Asio/epoll) это выглядит как та же **цепочка колбэков**, а для пользователя `read` становится **синхронным**: возврат из него означает, что данные уже в буфере. То есть колбэк, который в §2 писали вручную, теперь генерирует переключение контекста (для stackless-корутин — компилятор, см. файл про stackless). Это ровно декомпозиция «файбер = корутина + рантайм»: корутина прячет разрезы, рантайм (здесь — event loop, а не просто пул) планирует продолжения (см. файлы про планировщик и IO multiplexing).

## 9. Файберы против корутин (coroutines)

| Характеристика | Файбер (stackful) | Корутина C++20 (stackless) |
|---|---|---|
| Стек | собственный (stackful) | нет собственного (stackless) |
| Сохранение состояния | полный контекст процессора | в объекте-обещании (promise) во frame |
| Переключение | дорогое (регистры + стек) | дешёвое (переход по состояниям) |
| Глубина вызовов | не ограничена, любые функции | требует `co_await` на каждом уровне |
| Поддержка в C++ | нужен ассемблер/сисколлы | встроена с C++20 (`co_await`/`co_yield`) |

Корутины C++20 (stackless) — компилятор превращает функцию в автомат состояний; приостановка сохраняет локальные переменные во frame, без переключения стека, но нельзя приостанавливаться из вложенных вызовов, не разметив их. Файберы — полноценные user-space потоки: тяжелее, но позволяют обычный императивный код без модификации сигнатур. Подробно stackless-корутины — в отдельном файле.
